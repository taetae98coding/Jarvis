상태 조회 규칙

플랫폼 상태를 Flow로 노출하는 방식을 하나로 정한다. 시스템이 변경을 알려주면 콜백으로, 알려주지 않으면 일정 간격마다 다시 읽는다.

사용자 지시

Flow 형식 조회도 System에서 callback을 주면 callback을 받아서 상태 업데이트, callback을 주지 않으면 N초마다 새로 조회해서 상태 업데이트 하는 방식으로 문제 해결해줘.

2026-09-22 대화.

이 규칙 전에는 방식이 상태마다 흩어져 있었다. 설정은 콜백만 쓰고(SettingsStore.observeBoolean), 에뮬레이터 개수는 폴링만 썼고(pollingEmulatorProbe), 첫 값을 읽는 방법과 중복을 걸러내는 방법이 각자 구현되어 있었다.

요구사항

  1. R1. 시스템이 변경 콜백을 주는 상태는 콜백이 올 때마다 다시 읽는다. 폴링을 함께 돌리지 않는다.
  2. R2. 콜백이 없는 상태는 정해진 간격마다 다시 읽는다.
  3. R3. 어느 쪽이든 구독 즉시 첫 값을 읽는다. 첫 콜백이나 첫 간격을 기다리지 않는다.
  4. R4. 값이 이전과 같으면 방출하지 않는다.
  5. R5. 구독자는 상태가 콜백으로 오는지 폴링으로 오는지 알 수 없다. 둘 다 Flow<T>다.
  6. R6. 콜백 유무가 플랫폼마다 갈리는 상태는 한 호출로 두 경우를 모두 처리한다.

화면·동작

해당 없음. 화면에 직접 드러나지 않는 구현 규약이다. 이 규칙이 만족되면 설정과 에뮬레이터 개수, 전역 화면 유지의 권한 상태가 앱 밖에서 바뀌어도 화면이 따라간다.

결정: 신호에 값을 담지 않고 매번 다시 읽는다 플랫폼 콜백은 "무엇이 바뀌었는지" 알려주지 않는 경우가 많다. iOS NSUserDefaultsDidChangeNotification은 바뀐 키를 주지 않고, Android ContentObserver도 URI만 준다. 신호를 "무언가 바뀌었다"로만 쓰고 값은 다시 읽으면 네 플랫폼에 같은 계약을 줄 수 있다. 대신 R4의 중복 제거가 필수가 된다.
결정: 함수를 셋으로 나눈다 하나로 합쳐 signals를 nullable로만 두면 콜백만 쓰는 호출부가 의미 없는 interval을 넘겨야 하고, 폴링만 쓰는 호출부가 signals = null을 적어야 한다. 호출부에서 어느 쪽인지 이름으로 드러나는 편을 택했다. 플랫폼마다 갈리는 경우만 세 번째 함수를 쓴다.

SettingsStore.changes는 Flow<Unit>?다. 변경을 알려주지 않는 저장소는 null을 두고 폴링으로 대체한다는 계약을 타입에 적어 둔 것이다. 지금 네 플랫폼은 모두 콜백을 제공한다.

한계

  • 폴링은 간격만큼 늦는다. 최악의 경우 간격 전체를 기다린다. 즉시성이 필요하면 간격을 줄이는 것 말고는 방법이 없다.
  • 중간 값은 건너뛴다. 신호는 conflate되고 읽기는 순차적이라, 읽는 동안 두 번 바뀌면 마지막 값만 본다. 상태의 현재 값만 쓰는 화면에는 문제가 없지만 변경 이력이 필요한 기능에는 맞지 않는다.
  • 읽기 실패를 구분하지 않는다. read()가 실패를 값으로 표현해야 한다. 에뮬레이터 개수가 null 요약으로 "셀 수 없음"을 나타내는 것이 그 예다.
  • 구독자가 없으면 아무것도 돌지 않는다. Flow가 차가워서, 화면이 보고 있지 않은 상태는 갱신되지 않는다. JVM 에뮬레이터 프로브만 shareIn으로 예외를 둔다.
