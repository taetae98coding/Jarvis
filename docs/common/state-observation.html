상태 조회 규칙

플랫폼 상태를 받아오는 방식을 하나로 정한다. 상태는 suspend 가 아니라 cold Flow 로 받는다. 시스템이 변경을 알려주면 콜백으로, 알려주지 않으면 일정 간격마다 다시 읽는다. 아무도 수집하지 않으면 콜백을 해제하고 폴링을 멈춘다.

사용자 지시

Flow 형식 조회도 System에서 callback을 주면 callback을 받아서 상태 업데이트, callback을 주지 않으면 N초마다 새로 조회해서 상태 업데이트 하는 방식으로 문제 해결해줘.

2026-09-22 대화.

지금 상태를 받아오는 것은 전부 suspend가 아니라 Flow로 받아오도록 Rule 작성됐는지 확인해줘. 안됐으면 작성해줘. 그리고 상태 받아오는 코드 전부 확인해서 기본적으로 System이나 Sdk가 제공하는 callback or Coroutine기반 기능 사용하도록 하고, 불가능한 경우 일정 ms 기다리면서 주기적으로 조회하도록 구현했는지 확인해줘. 이것도 룰에 적어줘. 그리고 Flow는 항상 coldFlow로 제공해서 collect 하는 코드가 없으면 자동으로 callback 해제 및 주기적으로 조회하는 것 중단하도록 구현됐는지 검토해줘.

2026-09-24 대화.

첫 지시 전에는 방식이 상태마다 흩어져 있었다. 설정은 콜백만 쓰고(SettingsStore.observeBoolean), 에뮬레이터 개수는 폴링만 썼고(pollingEmulatorProbe), 첫 값을 읽는 방법과 중복을 걸러내는 방법이 각자 구현되어 있었다.

두 번째 지시 때 검토한 결과, suspend 로 상태를 한 번 읽어 주는 API 는 없었지만 규칙으로 적혀 있지 않았다. 콜백·폴링 선택은 R1–R6 대로였으나 Android WRITE_SETTINGS 권한은 콜백이 있는데도 폴링했다. cold 규칙은 없어서 설정 리포지토리가 앱 수명 스코프에 Eagerly 로 리스너를 붙잡고 있었고, 회전·전역 화면 유지 리포지토리와 도메인이 StateFlow 를 내놓았으며, 에뮬레이터 개수 ViewModel 은 화면이 보지 않아도 폴링했고, 화면은 collectAsState 로 모아서 앱이 백그라운드에 있어도 수집을 이어 갔다. 지원하지 않는 플랫폼의 데이터 소스는 emptyFlow() 라 R3 을 어겼다. 전부 아래 규칙대로 고쳤다.

요구사항

콜백과 폴링

  1. R1. 시스템이 변경 콜백을 주는 상태는 콜백이 올 때마다 다시 읽는다. 폴링을 함께 돌리지 않는다.
  2. R2. 콜백이 없는 상태는 정해진 간격마다 다시 읽는다.
  3. R3. 어느 쪽이든 구독 즉시 첫 값을 읽는다. 첫 콜백이나 첫 간격을 기다리지 않는다. 바뀔 일이 없는 상태(지원하지 않는 플랫폼)도 첫 값 하나는 흘린다.
  4. R4. 값이 이전과 같으면 방출하지 않는다.
  5. R5. 구독자는 상태가 콜백으로 오는지 폴링으로 오는지 알 수 없다. 둘 다 Flow<T>다.
  6. R6. 콜백 유무가 플랫폼마다 갈리는 상태는 한 호출로 두 경우를 모두 처리한다.
  7. R7. 콜백부터 찾는다. System·SDK 가 주는 리스너·알림·콜백·코루틴 API 가 있으면 그것을 쓰고(R1), 정말 없을 때만 폴링한다(R2). 폴링 간격은 이름 붙은 Duration 상수로 두고, 콜백이 왜 없는지와 조사하고 버린 후보를 플랫폼 스펙에 남긴다.

Flow 로만 받는다

  1. R8. 바뀔 수 있는 상태는 Flow<T> 로 받는다. 한 번 읽고 끝나는 suspend fun getX(): T 조회 API 를 만들지 않는다. suspend 는 명령(쓰기·요청)과 그 결과에만 쓴다(pair, launch, open).
  2. R9. 첫 프레임에 보일 초기값만 예외로 동기 스냅샷 readX() 를 둔다. 이 값은 stateIn 의 초기값으로만 쓰고, 상태를 따라가는 데 쓰지 않는다. 명령이 지금 값을 알아야 하면 observeX().first() 로 읽는다.
  3. R10. 실행 중에 바뀌지 않는 값(플랫폼 이름, 기능 지원 여부)은 상태가 아니다. 일반 값으로 둔다.

cold Flow 와 해제

  1. R11. data·domain 이 내놓는 상태 Flow 는 cold 다. 수집이 시작될 때 콜백을 등록하거나 폴링을 시작하고, 수집이 끝나면 콜백을 해제하고 폴링을 멈춘다.
  2. R12. data·domain 은 StateFlow·SharedFlow 를 노출하지 않고, 앱 수명 스코프로 stateIn·shareIn 하지 않는다. 비싼 조회를 동시 구독자가 나눠야 할 때만 shareIn(WhileSubscribed(replayExpirationMillis = 0)) 로 묶고 타입은 Flow 로 노출한다.
  3. R13. 화면 상태로 바꾸는 곳은 ViewModel 이다. stateIn(viewModelScope, WhileSubscribed(), 초기값) 을 쓴다. Eagerly·Lazily 는 구독과 무관하게 이어져야 하는 작업에만, 이유를 주석으로 적고 쓴다.
  4. R14. 화면은 상태를 collectAsStateWithLifecycle 로 모은다. 앱이 백그라운드로 가면 수집이 끊기고, R11 에 따라 콜백과 폴링도 멈춘다.

화면·동작

화면에 직접 드러나지 않는 구현 규약이다. 이 규칙이 만족되면 설정과 에뮬레이터 개수, 전역 화면 유지·화면 회전의 권한 상태가 앱 밖에서 바뀌어도 화면이 따라가고, 화면을 떠나거나 앱을 내리면 그 상태를 보던 리스너와 폴링이 멈춘다.

콜백은 callbackFlow { register(); awaitClose { unregister() } } 로 감싸 signals 로 넘긴다. 폴링은 flow { while (true) { delay(interval); emit(Unit) } } 다. 둘 다 수집이 취소되면 awaitClose 와 delay 에서 끝나므로 R11 을 따로 구현할 필요가 없다. 규칙을 어기는 길은 이 Flow 를 누군가 영원히 수집하게 만드는 것뿐이고, R12–R14 가 그 길을 막는다.

결정: 신호에 값을 담지 않고 매번 다시 읽는다 플랫폼 콜백은 "무엇이 바뀌었는지" 알려주지 않는 경우가 많다. iOS NSUserDefaultsDidChangeNotification은 바뀐 키를 주지 않고, Android ContentObserver도 URI만 준다. 신호를 "무언가 바뀌었다"로만 쓰고 값은 다시 읽으면 네 플랫폼에 같은 계약을 줄 수 있다. 대신 R4의 중복 제거가 필수가 된다.
결정: 함수를 셋으로 나눈다 하나로 합쳐 signals를 nullable로만 두면 콜백만 쓰는 호출부가 의미 없는 interval을 넘겨야 하고, 폴링만 쓰는 호출부가 signals = null을 적어야 한다. 호출부에서 어느 쪽인지 이름으로 드러나는 편을 택했다. 플랫폼마다 갈리는 경우만 세 번째 함수를 쓴다.

SettingsStore.changes는 Flow<Unit>?다. 변경을 알려주지 않는 저장소는 null을 두고 폴링으로 대체한다는 계약을 타입에 적어 둔 것이다. 지금 네 플랫폼은 모두 콜백을 제공한다.

결정: 리포지토리가 상태를 공유하지 않는다 (R12) 예전에는 리포지토리가 앱 수명 스코프로 stateIn 해서 "구독자가 여럿이어도 리스너는 한 벌" 을 지켰다. 대가로 리포지토리가 StateFlow 를 노출했고, 구독이 끊긴 동안의 .value 는 오래된 값이었으며, 설정은 Eagerly 라 리스너가 영영 풀리지 않았다. 리스너 등록은 싸다(ContentObserver, NSNotificationCenter). 구독자마다 한 벌씩 붙이고 수집이 끝나면 떼는 편을 택했다. 등록이 비싼 조회 — 외부 프로세스를 띄우는 JVM 에뮬레이터 프로브 — 만 R12 의 예외로 묶는다.

전부 runTest의 가상 시간으로 돈다. 실제 시간을 기다리지 않는다. R14 는 화면 테스트가 collectAsStateWithLifecycle 로 도는 것까지만 확인한다. 앱이 백그라운드로 갈 때 수집이 끊기는 것은 기기에서만 볼 수 있어 미검증이다.

한계

  • 폴링은 간격만큼 늦는다. 최악의 경우 간격 전체를 기다린다. 즉시성이 필요하면 간격을 줄이는 것 말고는 방법이 없다.
  • 중간 값은 건너뛴다. 신호는 conflate되고 읽기는 순차적이라, 읽는 동안 두 번 바뀌면 마지막 값만 본다. 상태의 현재 값만 쓰는 화면에는 문제가 없지만 변경 이력이 필요한 기능에는 맞지 않는다.
  • 읽기 실패를 구분하지 않는다. read()가 실패를 값으로 표현해야 한다. 에뮬레이터 개수가 null 요약으로 "셀 수 없음"을 나타내는 것이 그 예다.
  • 구독자마다 리스너가 한 벌씩 붙는다. R12 의 대가다. 전역 화면 유지 상태는 카드와 효과가 따로 구독해서 ContentObserver 가 두 벌이다. 비싼 조회가 겹치면 R12 의 예외로 묶는다.
  • 데스크톱의 에뮬레이터 프로브는 앱이 떠 있는 동안 계속 돈다. 로컬 에이전트가 앱 수명 동안 수집하기 때문이다. Flow 는 cold 이고 WhileSubscribed 라서 에이전트를 띄우지 않으면 멈춘다. 요청이 올 때만 세도록 바꾸면 쉬고 난 뒤 첫 요청이 세는 시간(수 초)을 기다려야 하는데, 클라이언트 타임아웃이 2초다.
  • 화면이 보고 있지 않은 상태는 갱신되지 않는다. 다시 모으기 시작하면 R3 에 따라 곧바로 새로 읽으므로, 그 사이의 변화는 마지막 값만 보인다.
