용어

코드 파일
이름이 .kt·.kts(Kotlin) 또는 .swift(Swift)로 끝나는 파일. 이 기능은 코드 파일 탭에만 있다
코드 분석
언어 서버(LSP)가 프로젝트를 읽고 주는 정확한 결과. Kotlin 은 JetBrains kotlin-lsp, Swift 는 Apple sourcekit-lsp
텍스트 검색
코드 분석이 없거나 결과가 비었을 때 쓰는 대체 방식. 같은 언어 파일에서 이름을 글자로 찾는다. 이름이 같은 다른 심볼도 섞인다
프로젝트 루트
분석과 텍스트 검색이 볼 폴더. N3 으로 정한다
식별자
글자·숫자·_(Swift 는 $ 도)가 이어진 한 덩어리. 커서가 식별자 끝 바로 뒤에 있어도 그 식별자로 본다
선언으로 가기
지시의 "Command + B". 커서의 식별자가 선언된 자리로 옮긴다. 커서가 이미 선언 위에 있으면 사용하는 곳 목록을 연다(Android Studio 의 동작)

요구사항

코드 분석과 루트

  1. N1. 작업 트리 파일 탭(커밋 파일 탭이 아닌 것)이 코드 파일이고 보이고 있으면, 그 파일의 (언어, 프로젝트 루트)에 해당하는 언어 서버를 띄운다. 같은 (언어, 루트)의 탭은 서버 하나를 같이 쓴다.
  2. N2. 그 서버를 쓰는 탭이 하나도 보이지 않은 지 CodeAnalysisIdleTimeout(60초)이 지나면 서버를 끈다. 그 안에 다시 보이면 이어서 쓴다. 앱을 끄면 서버도 끈다.
  3. N3. 프로젝트 루트는 파일의 폴더부터 위로 올라가며 찾는다. Kotlin: settings.gradle.kts·settings.gradle 이 있는 가장 가까운 폴더. 없으면 build.gradle.kts·build.gradle 이 있는 가장 위 폴더, 그것도 없으면 .git 이 있는 폴더, 그것도 없으면 파일의 폴더. Swift: Package.swift 가 있는 가장 가까운 폴더. 없으면 *.xcodeproj 를 가진 가장 가까운 폴더, 없으면 .git 이 있는 폴더, 없으면 파일의 폴더.
  4. N4. 도구 줄에 분석 상태를 보인다. 준비 중이면 "Kotlin 분석 준비 중…"(서버가 진행률을 주면 " 42%" 를 붙인다), 서버를 찾지 못했거나 띄우지 못했거나 멈췄으면 "텍스트 검색만 — <이유>" 이고, 준비되면 아무것도 보이지 않는다. 코드 분석이 없는 플랫폼은 늘 아무것도 보이지 않고 텍스트 검색만 쓴다.
  5. N5. 서버가 도중에 멈추면 상태를 "텍스트 검색만 — <이유>" 로 바꾼다. 이유는 서버가 stderr 에 남긴 마지막 줄이고, 없으면 "분석 서버가 멈췄습니다" 다. 그 서버를 쓰는 탭이 모두 가려져 N2 로 정리된 뒤 다시 보이면 다시 띄운다.

자동완성 (편집 보기)

  1. C1. 코드 파일의 편집 보기(E2)에서, 커서 앞에 식별자 글자를 치거나 . 을 치면 CompletionDebounce(120ms) 뒤 커서 아래에 자동완성 목록을 띄운다. Ctrl+Space 는 식별자를 치지 않아도 곧장 띄운다. 고른 범위가 있으면 띄우지 않는다.
  2. C2. 목록 줄마다 종류 글자(함수 f, 변수·속성 v, 타입 T, 키워드 k, 그 밖 ·), 이름, 오른쪽에 흐린 설명(반환 타입·패키지)을 보인다. 순서는 서버가 준 sortText 순이고, 커서 앞 식별자(접두사)로 시작하지 않는 항목은 뺀다(대소문자 무시). 많아야 CompletionMaxItems(50)개, 보이는 줄은 8줄이고 나머지는 목록 안에서 스크롤한다.
  3. C3. 목록이 떠 있는 동안 ↑·↓ 는 고른 줄을 옮기고, Enter·Tab 은 고른 항목을 넣고, Esc 는 목록만 닫는다(편집 보기는 닫지 않는다). 줄을 눌러도 넣는다. 식별자 글자를 더 치거나 지우면 목록을 다시 받는다. 식별자가 아닌 글자를 치거나 커서가 접두사 밖으로 나가면 닫는다.
  4. C4. 항목을 넣으면 접두사를 항목의 글로 바꾸고 커서를 넣은 글 끝(서버가 커서 자리를 알려 주면 그 자리)에 둔다. 서버가 넣기에 딸린 다른 수정(Kotlin 의 import 줄 추가 등)을 주면 같은 파일 안의 것은 함께 넣는다.
  5. C5. 코드 분석이 준비되지 않았거나 빈 목록을 주면 텍스트 검색으로 채운다. 이 파일에 나온 식별자 가운데 접두사로 시작하고 접두사보다 긴 것을, 커서에 가까운 순으로. 이때 목록 위에 "텍스트" 라고 적는다.

선언·사용처 이동 (읽기 보기·편집 보기)

  1. G1. 편집 보기에서 ⌘B(Ctrl+B)는 커서의 식별자에서 선언으로 가기, ⌥F7 은 사용하는 곳 찾기다. 읽기 보기·편집 보기에서 ⌘(Ctrl)를 누른 채 식별자를 누르면 그 식별자에서 선언으로 가기다. 커서·누른 자리에 식별자가 없으면 아무 일도 하지 않는다.
  2. G2. 선언으로 가기의 결과가 커서의 식별자 자신이면(선언 위에서 불렀으면) 사용하는 곳 찾기로 바꾼다.
  3. G3. 결과가 한 곳이면 곧장 그 자리로 간다. 여러 곳이면 목록 창을 띄운다: 제목("선언 N곳" 또는 "사용하는 곳 N곳", 텍스트 검색이면 " · 텍스트 검색" 을 붙인다)과 줄마다 "파일이름:줄번호" 와 그 줄의 글(앞뒤 공백을 뗀 것). ↑·↓·Enter 나 누르기로 골라 가고, Esc 나 창 밖을 누르면 닫는다. 많아야 NavigationMaxResults(200)곳이다.
  4. G4. "그 자리로 간다" 는: 같은 파일이면 이 탭에서, 다른 파일이면 R9 처럼 그 파일의 파일 탭을 열거나 고른 뒤, 그 줄이 보이게 스크롤한다. 읽기 보기는 그 줄 바탕을 RevealHighlight(1.5초) 동안 칠하고, 편집 보기는 커서를 그 자리에 둔다. 가는 탭이 편집 중이면 편집 보기에서 옮긴다.
  5. G5. 결과가 없으면 도구 줄에 "선언을 찾지 못했습니다" 또는 "사용하는 곳이 없습니다" 를 3초 보인다. 결과가 라이브러리 안(jar: 처럼 파일이 아닌 주소)뿐이면 "라이브러리 안의 선언이라 열 수 없습니다" 다.
  6. G6. 코드 분석이 준비되지 않았거나 빈 결과를 주면 텍스트 검색으로 찾는다. 프로젝트 루트 아래 같은 언어 파일에서, 선언은 선언 키워드(Kotlin fun val var class interface object typealias, Swift func var let class struct enum protocol extension actor typealias case) 바로 뒤의 그 이름, 사용처는 단어 전체가 같은 자리 가운데 선언이 아닌 것. 주석·문자열 안도 찾는다. build·.build·.gradle·.git·.idea·node_modules·DerivedData·Pods 폴더와 1 MiB 넘는 파일은 보지 않고, 파일은 많아야 TextSearchMaxFiles(20,000)개 본다.
  7. G7. 찾는 동안 도구 줄에 "찾는 중…" 을 보이고, 새로 부르면 앞의 찾기를 버린다.
스코프에서 뺀 것 Kotlin·Swift 밖의 언어(지시가 두 언어로 한정했다), 마우스를 올려 설명 보기(hover), 오류 밑줄(diagnostics), 이름 바꾸기·서식·코드 액션, 매개변수 힌트, 뒤로 가기(⌘[), ⌘ 를 누른 채 올렸을 때의 밑줄, 커밋 파일 탭, 라이브러리·SDK 소스 열기. 자동완성의 스니펫 자리 채우기($1)는 받지 않는다(snippetSupport: false).

CodeLanguage(Kotlin·Swift)와 codeLanguageOf(path), codeProjectRoot(path, language, exists)(N3, 파일 있는지 묻는 함수를 받는 순수 함수). CodeIntelRepository: observeAnalysis(path): Flow<CodeAnalysisStatus>(cold. 수집하는 동안 그 파일의 서버를 붙잡고 문서를 연다 — N1·N2), suspend complete(path, text, offset): CodeCompletions, suspend applyCompletion(path, text, item): CodeEdit(C4), suspend definition(path, text, offset)·suspend usages(path, text, offset): CodeLocations. 요청마다 지금 글 전체를 넘겨서 서버 문서와 어긋나지 않게 한다. 결과에는 출처(CodeSource.Analysis·TextSearch)가 붙는다. 순수 함수: identifierAt·completionPrefix, offsetOf(text, line, column)·positionOf(text, offset)(줄 나누기는 String.lines() 와 같다), applyTextEdits, filterCompletions(C2), 텍스트 검색 wordCompletions(C5)·findDeclarations·findUsages(G6)

결정: 정확한 결과는 언어 서버(LSP)에 맡긴다. Kotlin·Swift 의 타입 추론·import·확장 함수를 직접 풀 수는 없다. 두 언어 다 공식 언어 서버가 있다(JetBrains kotlin-lsp, Apple sourcekit-lsp). 둘 다 stdio JSON-RPC 이고, LSP 의 위치 단위(UTF-16)가 Kotlin String 인덱스와 같아서 변환이 줄·칸 계산뿐이다. Android Studio·IntelliJ 를 원격으로 부리는 방식은 IDE 가 떠 있어야 하고 프로젝트마다 창이 열려야 해서 버렸다.
결정: 코드 분석이 비면 텍스트 검색으로 채운다. 2026-09-25 에 이 저장소(KMP, AGP com.android.kotlin.multiplatform.library)에서 kotlin-lsp 263.4702 을 돌려 보니 같은 모듈 안의 심볼은 선언·사용처·자동완성이 다 되지만, 다른 모듈(:feature:terminal:domain)과 라이브러리(remember) 심볼은 빈 결과였다. Xcode 프로젝트의 Swift 는 인덱스가 없어 사용처가 늘 비었다(JVM 스펙). 빈 결과를 그대로 보이면 이 저장소에서 ⌘B 가 대부분 아무 일도 하지 않으므로, 부정확하더라도 텍스트 검색으로 채우고 출처를 목록 제목에 적는다.
결정: 서버는 마지막 탭이 가려진 뒤 60초 더 붙잡는다. Kotlin 서버는 Gradle 임포트에 캐시 없이 약 20초, 캐시가 있어도 몇 초가 걸린다. 탭을 오갈 때마다 끄고 켜면 매번 기다린다. 그래서 상태 조회 규약(state-observation)의 "비싼 조회는 shareIn(WhileSubscribed)" 에 stopTimeoutMillis 60초를 더한다. 앱 수명 동안 붙잡지 않는다 — 서버 하나가 메모리 2 GiB 까지 쓴다.
결정: 자동완성 목록은 입력 칸의 포커스를 뺏지 않는 Popup 으로 띄운다. 목록이 포커스를 가져가면 이어 치는 글자와 한글 조합이 입력 칸으로 가지 않는다. 방향키·Enter·Tab·Esc 는 입력 칸의 onPreviewKeyEvent 가 먼저 받아 목록에 쓴다. 위치는 TextLayoutResult.getCursorRect 로 잡는다. 문법 색의 VisualTransformation 은 글자를 바꾸지 않는 항등 매핑이라 원문 위치가 그대로 화면 위치다.

한계

  • 텍스트 검색은 이름만 본다. 같은 이름의 다른 함수·지역 변수·주석 속 단어가 섞이고, 오버로드를 가리지 못한다.
  • KMP 프로젝트에서 kotlin-lsp 는 다른 모듈·라이브러리 심볼을 풀지 못해(결정 참고) 그런 심볼은 텍스트 검색으로 간다. kotlin-lsp 가 나아지면 저절로 코드 분석 결과가 나온다.
  • Kotlin 서버는 첫 임포트에 Gradle 을 돌린다. 임포트가 실패하는 프로젝트(Android SDK 를 못 찾는 등)는 파일 하나 안의 심볼만 안다.
  • 편집 보기가 아닌 읽기 보기에는 커서가 없어 ⌘B·⌥F7 이 없다. ⌘클릭만 된다.
  • 라이브러리·SDK 안의 선언은 열지 않는다(G5).
  • macOS 에서 Ctrl+Space 를 입력 소스 전환에 쓰고 있으면 시스템이 먼저 가져가 C1 의 즉시 띄우기가 오지 않는다. 글자를 치면 뜨는 자동 띄우기는 그대로다.
  • 서버는 저장하지 않은 편집 중인 글을 알지만, 다른 탭에서 편집 중인 저장하지 않은 글은 모른다(그 파일은 디스크 내용으로 본다).
