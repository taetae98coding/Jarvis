모듈 구조

공용 코드를 :domain · :data · :ui 세 계층 모듈로 나누고, :shared는 그 셋을 조립해 앱 진입점만 내놓는다. 기능이 늘어도 :shared는 커지지 않는다.

사용자 지시

지금 구조는 모듈이 커지면 shared에 집중적으로 추가되는 구조잖아. clean architecture 맞춰서 모듈화 진행하자. ui 모듈 domain 모듈 data 모듈이 크게 있어야 할 것 같은데 검토해줘. 각각 모듈 책임에 맞게 구현하고 모듈 분리 후 각 모듈에 package 수정도 필요한지 검토해줘.

2026-09-22 대화.

요구사항

  1. R1. 공용 코드는 :domain, :data, :ui 세 Gradle 모듈에 나뉘어 있고, :shared에는 조립 코드와 플랫폼 진입점만 남는다.
  2. R2. 모듈 의존은 한 방향이다. :ui → :domain, :data → :domain, :shared → :domain, :data, :ui. :ui는 :data를, :data는 :ui를 컴파일 타임에 볼 수 없다.
  3. R3. :domain은 Compose와 플랫폼 API에 의존하지 않는다. 의존성은 kotlinx-coroutines-core뿐이고, expect 선언이 없다.
  4. R4. 플랫폼 API 호출(expect/actual)은 전부 :data에 있다. 단 Compose가 대신 불러 주는 것(Modifier.keepScreenOn())과 Compose 트리에서만 얻을 수 있는 것(Android Context)은 예외이며 아래 예외 표에 적는다.
  5. R5. :ui는 Compose API만 부른다. :domain의 모델·유스케이스로만 상태를 읽고 쓴다.
  6. R6. 패키지 루트는 모듈마다 다르다. …jarvis.domain / …jarvis.data / …jarvis.ui / …jarvis.shared. 그 아래는 계층이 아니라 기능으로 나눈다(appinfo, emulator, screen, settings).
  7. R7. 사용자에게 보이는 동작은 바뀌지 않는다. 분리 전 테스트가 검증하던 내용은 분리 후에도 전부 검증된다.
  8. R8. 기능을 하나 더할 때 :shared에 파일을 더하지 않는다. 세 모듈의 같은 기능 패키지에 더하고, 조립 한 줄만 :shared에 추가한다.
스코프에서 뺀 것
  • 기능별 모듈(:feature:emulator 같은 세로 분리). 기능이 셋뿐이라 지금은 계층 분리만으로 충분하다. 기능 패키지를 모듈 경계와 같은 이름으로 맞춰 두었으므로 나중에 잘라내기만 하면 된다.
  • DI 프레임워크. 생성자 주입과 :shared의 조립 클래스 하나로 충분하다. Koin·Hilt는 넣지 않았다.
  • 빌드 컨벤션 플러그인(build-logic). 아래 결정 참조.
  • 모듈 이름 변경. :shared와 iOS 프레임워크 이름 Shared는 그대로 둔다. Xcode 프로젝트가 :shared:embedAndSignAppleFrameworkForXcode를 직접 부르고, 이름을 바꿔도 얻는 것이 없다.

화면·동작

화면에 보이는 변화는 없다. 이 문서는 사용자에게 보이지 않는 구조에 대한 스펙이고, 그래서 검증도 화면이 아니라 "기존 테스트가 새 자리에서 같은 것을 검증하는가"로 한다.

공통 구현

모듈

모듈책임의존쓸 수 있는 것
:domain 모델과 규칙. 리포지토리 인터페이스와 유스케이스 없음 Kotlin, kotlinx-coroutines-core
:data 리포지토리 구현. 플랫폼 API 호출, 저장소, 직렬화, 프로세스·HTTP :domain 플랫폼 API(expect/actual), kotlinx-serialization
:ui Compose 화면과 화면 상태. 유스케이스만 부른다 :domain Compose Multiplatform
:shared 조립(composition root)과 플랫폼 진입점. App(), MainViewController() :domain, :data, :ui 위 셋 전부 
:androidApp   :iosApp(Xcode)   :desktopApp   :webApp
      └──────────────┴──────────────┴─────────┘
                       :shared          ← 조립. 기능이 늘어도 커지지 않는다
             ┌───────────┼───────────┐
           :ui         :data         │
             └───────────┴───────── :domain   ← 아무것도 의존하지 않는다

의존 방향은 Gradle이 강제한다. :ui의 빌드 파일에 :data가 없으므로 화면에서 SharedPreferences나 HttpURLConnection을 부르려면 컴파일이 깨진다. 반대로 :data에는 Compose 플러그인 자체가 없어서 @Composable을 쓸 수 없다.

패키지

모듈마다 패키지 루트가 다르다. 같은 기능은 세 모듈에서 같은 마지막 이름을 쓴다. 기능을 찾을 때 emulator로 grep하면 세 계층이 함께 나온다.

결정: 패키지는 계층이 아니라 기능으로 나눈다 모듈 이름이 이미 계층이므로 data.repository, ui.screen.component 같은 계층 패키지를 또 두지 않는다. 기능 패키지가 곧 미래의 기능 모듈 경계다. 예전 shared.platform은 계층도 기능도 아닌 "플랫폼에 닿는 것 전부"라 기능이 늘수록 커지기만 했다. 그 패키지는 사라지고 내용은 data의 기능 패키지로 흩어진다.

계층별 규칙

domain
아무 API도 부르지 않는다. 상태는 Flow로 받고 정책만 적는다. 예: "설정이 켜져 있고 권한이 허용된 동안에만 시스템 전역 효과를 적용한다"는 ApplySystemScreenAwakeUseCase에 있다. 리포지토리는 인터페이스만 있다.
data
리포지토리를 구현하고 플랫폼 API를 부른다. 모든 expect 선언이 여기 있다. 바깥 세계의 표현(JSON DTO, SharedPreferences 키, adb 출력)은 여기서 도메인 모델로 바꾼다. 도메인 모델에는 @Serializable을 붙이지 않는다.
ui
Compose만 부른다. 화면 상태는 JarvisAppState가 유스케이스로부터 만들고, 카드는 값과 콜백만 받는다. 저장·권한·프로세스는 모르고, "권한이 없으면 설정 화면을 연다" 같은 판단도 유스케이스가 한다.
shared
JarvisContainer가 DataModule → 유스케이스 → JarvisAppState를 잇는다. App()은 컨테이너를 만들어 JarvisApp()에 넘기는 것이 전부다. 기능이 늘면 컨테이너에 줄이 늘 뿐 파일은 늘지 않는다.

계층 규칙의 예외

플랫폼에 닿는데 :data에 둘 수 없는 것이 둘 있다. 예외를 만드는 대신 감추면 다음 사람이 규칙을 잘못 읽는다.

무엇어디왜 data에 못 두나
Modifier.keepScreenAwake(enabled) :ui ui/screen Compose의 Modifier.keepScreenOn()이 플랫폼 API를 대신 부른다. Modifier 형태로만 존재하므로 Compose 밖으로 꺼낼 수 없다. 이 modifier가 커버하지 못하는 JVM은 :data의 IdleInhibitor가 맡는다
rememberPlatformContext() :shared Android Context는 LocalContext로만 얻을 수 있다. :data에 Compose를 들이지 않으려고, 컨텍스트를 PlatformContext로 감싸 넘기는 일만 조립 모듈이 한다

PlatformContext

:data의 expect class PlatformContext는 플랫폼 핸들을 담는 상자다. Android에서만 Context를 들고 있고 나머지 셋에서는 빈 클래스다. Android 저장소와 시스템 설정 접근이 Context를 요구하는데, 그것을 :data가 전역으로 들고 있게 하지 않으려는 선택이다.

// :data
expect class PlatformContext

class DataModule(context: PlatformContext, scope: CoroutineScope) { … }

// :shared
@Composable
internal expect fun rememberPlatformContext(): PlatformContext
결정: 전역 Context 대신 PlatformContext를 넘긴다 androidx.startup이나 ContentProvider로 애플리케이션 컨텍스트를 몰래 잡아 두는 방법도 있다. 의존성이 늘고, :data가 초기화 순서에 의존하게 되고, 테스트에서 갈아끼울 수 없어서 버렸다. 지금은 컨텍스트가 필요한 곳이 생성자 하나뿐이라 무엇이 무엇을 요구하는지 코드에 드러난다.
결정: 빌드 컨벤션 플러그인을 넣지 않는다 모듈 넷이 타깃 선언(android/jvm/ios/wasmJs)을 각자 반복한다. build-logic 포함 빌드로 묶는 안을 검토했지만, 실제로 겹치는 것은 20줄 남짓이고 모듈마다 다른 부분(iOS 프레임워크는 :shared만, binaries.executable()은 :ui와 :webApp만, 직렬화는 :data만, Compose는 :ui·:shared만)이 그보다 많다. 포함 빌드와 버전 카탈로그 연결이 늘리는 고장 지점이 지금은 이득보다 크다. 모듈이 여섯을 넘거나 같은 설정을 세 번째로 복사하게 되면 그때 도입한다.

검증

구조 자체를 검증하는 테스트는 없다. 대신 분리 전 테스트가 전부 새 모듈로 옮겨 가 같은 것을 검증하고(R7), 의존 방향(R2)은 Gradle이 컴파일 단계에서 강제한다.

한계

  • expect/actual은 한 모듈 안에서만 짝이 맞는다. 그래서 플랫폼 구현이 필요한 기능은 반드시 :data(또는 :shared)를 거친다. :ui에 플랫폼 분기가 필요한 경우는 예외 표의 둘뿐이고, 늘어난다면 규칙이 아니라 이 표를 고쳐야 한다.
  • 모듈 경계를 넘는 선언은 public이 된다. :data의 DataModule은 앱 코드에서도 보인다. Kotlin에 "이 모듈에게만 공개"가 없어서 규약으로만 막는다.
  • 빌드 파일이 넷으로 늘어 타깃 선언이 반복된다. 결정에 적은 조건이 되면 컨벤션 플러그인으로 걷어낸다.
  • 모듈 경계를 넘는 테스트가 없다. 실제 플랫폼 저장소와 화면을 함께 도는 테스트는 분리 전에도 없었고(공통 한계) 지금도 없다. :shared의 조립이 틀리면 컴파일은 통과하고 앱에서만 드러난다.
