모듈 구조

기능 하나가 domain · data · ui 세 모듈을 갖는다. 계층은 그 셋의 의존 방향으로, 기능은 모듈 묶음으로 갈린다. :shared는 기능들의 Koin 모듈을 나열하고 진입점만 내놓는다.

사용자 지시

지금 구조는 모듈이 커지면 shared에 집중적으로 추가되는 구조잖아. clean architecture 맞춰서 모듈화 진행하자. ui 모듈 domain 모듈 data 모듈이 크게 있어야 할 것 같은데 검토해줘. 각각 모듈 책임에 맞게 구현하고 모듈 분리 후 각 모듈에 package 수정도 필요한지 검토해줘.

2026-09-22 대화. 계층 모듈 셋(:domain·:data·:ui)이 이 지시에서 나왔다.

feature:emulator 이런 식으로 모듈을 분리하는게 좋지 않아?

2026-09-22 대화. 아래 기능 모듈 결정이 이 지시의 답이고, 예전 스펙이 "스코프에서 뺀 것" 으로 적어 두었던 항목 둘(기능별 모듈, 빌드 컨벤션 플러그인)을 뒤집는다.

요구사항

  1. R1. 공용 코드는 기능마다 :feature:<기능>:domain · :feature:<기능>:data · :feature:<기능>:ui 셋으로 나뉜다. 기능은 appinfo, emulator, screen, rotation, terminal, theme(2026-09-25, 화면 테마), profiling(2026-09-25, 프로파일링), focus(2026-09-26, 집중 타이머) 여덟이다.
  2. R2. 계층 의존은 기능 안에서 한 방향이다. ui → domain, data → domain. 어느 기능에서도 ui가 data를, data가 ui를 컴파일 타임에 볼 수 없다.
  3. R3. 기능은 서로를 의존하지 않는다. 기능 사이에 필요한 것은 :core:*로 내려가고, 기능 하나가 다른 기능의 타입을 import 하면 그 구조는 틀린 것이다.
  4. R4. :core:*에는 두 기능 이상이 쓰는 것만 둔다. 한 기능만 쓰는 것은 그 기능이 갖는다.
  5. R5. :domain은 Compose와 플랫폼 API에 의존하지 않는다. 의존성은 kotlinx-coroutines-core와 koin-core뿐이고 expect 선언이 없다. 플랫폼 API 호출은 data 모듈에 있다(UI 타입에 묶인 것은 예외).
  6. R6. 기능 모듈은 자기 조립을 스스로 들고 있다. domain은 유스케이스를, data는 리포지토리를, ui는 ViewModel·화면·라우트를 각각 자기 Koin 모듈에 등록한다.
  7. R7. 앱 셸(:app:ui)은 어떤 화면이 있는지 모른다. 라우트는 각 기능의 Koin 모듈이 등록하고, 백스택 키의 직렬화 등록도 기능이 함께 낸다.
  8. R8. 기능을 하나 더할 때 고치는 기존 파일은 settings.gradle.kts와 :shared의 모듈 목록, 그리고 HomeFeature 를 놓는 FeatureGrid 뿐이다. (2026-09-26) 기능이 홈에 내놓는 것은 인자 없는 카드가 아니라 카드·타일 정보·지원 여부·화면 라우트를 묶은 HomeFeature 하나다(홈 적응형 배치).
  9. R12. (2026-09-24, 2026-09-25 범위 확장) Android 시스템 표면 컨트롤(홈 화면 위젯, 알림, 빠른 설정 타일)이 있는 기능은 :feature:<기능>:widget을 하나 더 갖는다. Android 전용 com.android.library 모듈이고, ui와 같은 방향(widget → domain)만 의존한다. 두 기능이 함께 쓰는 갱신 장치·권한 중계·알림 채널·타일 베이스는 :core:widget에 둔다(R4). 근거는 홈 화면 위젯과 알림 위젯과 빠른 설정 타일에 있다.
  10. R13. (2026-09-25) 화면이 없는 기능은 ui 모듈을 두지 않는다. :feature:mcp 는 domain·data 둘이다. 여러 기능의 능력을 한데 부르는 기능(MCP 도구)을 위해 이음새 인터페이스만 담은 :core:automation 을 두고, 각 기능의 data 가 구현을 Koin 에 등록한다. :feature:mcp:domain 이 :core:automation 을 의존하는 것은 R5 의 예외다 — 인터페이스와 데이터 클래스뿐이라 플랫폼·Compose 가 끌려오지 않는다. 브라우저 엔진은 터미널 화면과 MCP 가 함께 쓰므로 :core:browser 에 둔다(R4). 근거는 MCP 서버에 있다.
  11. R9. 패키지 루트는 모듈마다 다르다. 기능 분리 전의 패키지(…jarvis.<계층>.<기능>)를 그대로 쓴다.
  12. R10. 사용자에게 보이는 동작은 바뀌지 않는다. 분리 전 테스트가 검증하던 내용은 분리 후에도 전부 검증된다.
  13. R11. 타깃 선언(android/jvm/iosArm64/iosSimulatorArm64/wasmJs)은 한곳에만 있다. 모듈 빌드 파일은 자기와 다른 것만 적는다.
스코프에서 뺀 것
  • 기능당 모듈 하나(:feature:emulator 안에 계층을 함께 두는 안). 모듈 수는 적어지지만 Gradle 이 강제하던 "화면은 저장소를 못 본다"(R2)가 기능 안에서 사라진다. 이 프로젝트는 그 강제를 규칙의 근거로 쓰고 있어서(검증) 계층을 나눈 쪽을 택했다.
  • 패키지 이름 변경(jarvis.emulator.domain 식의 기능 우선 이름). 아래 결정 참조.
  • :core:domain. 기능 사이에 공유되는 도메인 타입이 지금 하나도 없다. 빈 모듈을 만들지 않는다(R4).
  • 모듈 이름 변경. :shared와 iOS 프레임워크 이름 Shared는 그대로 둔다. Xcode 프로젝트가 :shared:embedAndSignAppleFrameworkForXcode를 직접 부른다.
  • 기능별 앱 배포(Dynamic Feature, 별도 앱). 모듈 경계는 그쪽으로 가는 길을 열어 두지만 이번에 만들지는 않는다.

화면·동작

화면에 보이는 변화는 없다. 이 문서는 사용자에게 보이지 않는 구조에 대한 스펙이고, 그래서 검증도 화면이 아니라 "기존 테스트가 새 자리에서 같은 것을 검증하는가"로 한다.

항목값
제목해당 없음
설명해당 없음
컨트롤해당 없음
테스트 태그해당 없음

의존 방향은 Gradle 이 강제한다. :feature:emulator:ui의 빌드 파일에 :feature:emulator:data가 없으므로 화면에서 adb를 부르려면 컴파일이 깨진다. :feature:screen:ui에는 :feature:emulator:domain이 없어서 기능을 가로지르는 참조도 컴파일 단계에서 막힌다(R3).

결정: 기능 × 계층으로 나눈다 (분리 당시 모듈 16개, 터미널을 더해 지금 19개) 기능이 넷이고 계층이 셋이라 :core 둘과 :app:ui, :shared 를 더해 16개가 된다. 모듈 수가 늘어나는 대신 얻는 것은 두 가지다. 기능 사이 결합이 컴파일 단계에서 막히고(예전에는 :ui 한 모듈 안이라 screen 코드가 emulator 를 import 해도 빌드가 통과했다), 기능 하나를 통째로 잘라내거나 다른 앱에 끼우는 일이 가능해진다. 지금 실제 교차 참조는 없었으므로 이 분리는 예방이 목적이고, 그 사실을 여기 적어 둔다.

분리가 지금 가능해진 이유는 Koin과 Navigation3 때문이다. 손으로 조립하던 시절에는 JarvisContainer 가 모든 유스케이스를 알아야 해서 기능이 자기 조립을 가질 수 없었다.

결정: 패키지 이름은 그대로 둔다 모듈이 :feature:emulator:domain 인데 패키지가 jarvis.domain.emulator 라서 순서가 반대다. 기능 우선(jarvis.emulator.domain)으로 바꾸는 안을 검토했지만 버렸다. 파일 117개의 package·import 를 함께 고치면 이 변경의 diff 에서 "무엇이 어디로 옮겨졌는가" 를 읽을 수 없게 된다. 패키지가 이미 모듈마다 유일해서 R9 도 성립한다. 기능을 별도 저장소로 떼어낼 때가 오면 그때 같이 바꾼다.

Android namespace 는 패키지와 다르게 프로젝트 경로에서 만든다(:feature:emulator:data → io.github.taetae98coding.jarvis.feature.emulator.data). AGP 는 모듈마다 유일한 namespace 만 요구하고, 그 값은 R 클래스 좌표로만 쓰인다.

기능 모듈이 갖는 것

기능 하나는 세 개의 Koin 모듈을 내놓는다. 이름은 <기능>DomainModule · <기능>DataModule · <기능>UiModule 이다.

// :feature:emulator:ui — 라우트와 ViewModel 을 자기가 등록한다
val emulatorUiModule = module {
    viewModelOf(::EmulatorStatusViewModel)
    viewModelOf(::EmulatorDevicesViewModel)
    viewModel { parameters -> EmulatorScreenViewModel(parameters.get(), get(), get(), get()) }

    navigation<EmulatorRoute.Devices> { … }
    navigation<EmulatorRoute.Screen> { route -> … }

    // 백스택을 저장할 때 필요한 다형성 등록. 앱 셸이 getAll 로 모은다.
    navKeySerializers {
        subclass(EmulatorRoute.Devices::class, EmulatorRoute.Devices.serializer())
        subclass(EmulatorRoute.Screen::class, EmulatorRoute.Screen.serializer())
    }
}
결정: NavKey 직렬화 등록도 기능이 낸다 rememberNavBackStack 은 polymorphic(NavKey::class) 등록을 요구한다(근거). 그 목록을 앱 셸에 두면 화면을 더할 때마다 셸을 고쳐야 하고 R7 이 깨진다. 그래서 :core:ui 가 NavKeySerializers 타입을 정의하고, 기능이 Koin 에 하나씩 등록하고, 앱 셸이 getAll() 로 모아 SavedStateConfiguration 을 만든다. 라우트를 추가하고 등록을 잊으면 그 화면으로 이동할 때 런타임에 죽는 성질은 그대로다.
결정: HomeViewModel 을 기능별 ViewModel 로 해체한다 홈 화면은 네 기능의 카드를 놓는 자리다. 예전에는 HomeViewModel 하나가 앱 정보·에뮬레이터 개수·화면 꺼짐 방지·회전을 모두 들고 있었는데, 그러면 :app:ui 가 네 기능의 유스케이스를 알아야 해서 R3·R7 이 깨진다. 지금은 카드마다 자기 기능의 ViewModel 을 koinViewModel() 로 직접 받고, FeatureGrid 는 기능이 내놓은 HomeFeature(지원 여부·카드·타일의 아이콘과 라벨·화면 라우트) 일곱을 정렬해 배치만 한다(2026-09-26, 홈 적응형 배치). 지원 여부와 카드가 컴포저블 멤버라 기능이 그 안에서 자기 ViewModel 을 받고, 셸은 여전히 유스케이스를 모른다. 화면 꺼짐 방지의 앱 수명 효과도 :feature:screen:ui 의 Modifier.appScreenAwake() 안으로 들어가 앱 셸이 그 내부를 모른다.

계층 규칙의 예외

플랫폼에 닿는데 data 에 둘 수 없는 것이 아래 표의 것들이다. 모두 Compose 화면·ImageBitmap 처럼 UI 타입에 묶여 있어서 ui 에 expect 로 둔다. 예외를 만드는 대신 감추면 다음 사람이 규칙을 잘못 읽으므로, ui 에 expect 를 새로 두면 이 표에 한 줄을 더한다.

무엇어디왜 data에 못 두나
Modifier.keepScreenAwake(enabled) :feature:screen:ui Compose의 Modifier.keepScreenOn()이 플랫폼 API를 대신 부른다. Modifier 형태로만 존재하므로 Compose 밖으로 꺼낼 수 없다. 이 modifier가 커버하지 못하는 JVM은 :feature:screen:data 의 IdleInhibitor가 맡는다
HtmlFilePreview, rememberBrowserPage, BrowserPageView, browserTitle, closeBrowserPages :feature:terminal:ui 웹 페이지를 그리는 컴포저블과 그 수명이다. Android 는 WebView 를 AndroidView 로, JVM 은 :core:browser 의 JCEF 화면 밖 렌더링을 붙이므로 Compose 밖으로 꺼낼 수 없다(터미널에서 웹 브라우저, 파일 탭 보기 방식)
directoryPicker :feature:terminal:ui 폴더 선택 창은 화면에 뜨는 대화 상자다. 없는 타깃은 null 이고 경로를 직접 입력받는다(새 패널 제목·폴더)
EmulatorFrame.Pixels.toImageBitmap(), ImageBitmap.release(), FrameDecodeContext :feature:emulator:ui 기기 프레임을 Compose 의 ImageBitmap 으로 바꾸고 네이티브 픽셀 메모리를 놓는 일이다. ImageBitmap 이 Compose 타입이라 data 가 볼 수 없다(기기 화면 영상 스트림·호버)

PlatformContext

:core:data 의 expect class PlatformContext 는 플랫폼 핸들을 담는 상자다. Android에서만 Context를 들고 있고 나머지 셋에서는 빈 클래스다. Android 저장소와 시스템 설정 접근이 Context를 요구하는데, 그것을 data 가 전역으로 들고 있게 하지 않으려는 선택이다. 값은 진입점이 만들어 :shared 의 platformModule 이 Koin 에 등록하고, 각 기능의 data 모듈이 get() 으로 받는다.

결정: 전역 Context 대신 PlatformContext를 넘긴다 androidx.startup이나 ContentProvider로 애플리케이션 컨텍스트를 몰래 잡아 두는 방법도 있다. 의존성이 늘고, data 가 초기화 순서에 의존하게 되고, 테스트에서 갈아끼울 수 없어서 버렸다. 컨텍스트를 요구하는 것은 PlatformContext를 받는 Koin 정의들뿐이고, 그 값은 JarvisApplication이 startJarvisKoin(this)로 명시적으로 넘긴다. Application 서브클래스는 위젯이 Activity 없이 프로세스를 띄우게 되어 들였고, 하는 일은 그 한 줄과 알림 위젯의 포그라운드 동기화 등록(startJarvisNotificationWidgets(this))이다.

한계

  • 화면 테스트 전부(JarvisAppTest 34개와 가짜 리포지토리·픽스처)가 :app:ui 에 모여 있다. 앱 조립을 통째로 띄우는 테스트라 기능 모듈에 둘 자리가 없고, KMP 에는 테스트 코드를 모듈 사이에 공유하는 깔끔한 수단이 없다. 기능 단위 화면 테스트가 필요해지면 기능 모듈마다 가짜를 다시 만들거나 테스트 전용 모듈을 만들어야 한다.
  • 기능 모듈 자체에는 아직 화면 테스트가 없다. 기능의 ViewModel 규칙을 보는 테스트(EmulatorDevicesViewModelTest)도 픽스처 때문에 :app:ui 의 jvmTest 에 있다.
  • 모듈이 19개라 콜드 빌드 태스크 수가 세 배 남짓 늘었다. 증분 빌드와 병렬성은 좋아지지만 CI 의 첫 빌드는 느려진다.
  • expect/actual 은 한 모듈 안에서만 짝이 맞는다. 그래서 플랫폼 구현이 필요한 기능은 반드시 자기 data 모듈(또는 :core:data)을 거친다.
  • 모듈 경계를 넘는 선언은 public 이 된다. 기능의 Koin 모듈은 앱 코드에서도 보인다. Kotlin 에 "이 모듈에게만 공개" 가 없어서 규약으로만 막는다.
  • 패키지 순서가 모듈 순서와 반대다(결정). IDE 의 프로젝트 트리와 패키지 트리가 다르게 보인다.
