요구사항

R1~R9 가 알림, R10~R13 이 빠른 설정 타일, R14~R15 가 둘의 공통이다.

  1. R1. "화면 회전" 카드와 "화면 꺼짐 방지 (시스템 전역)" 카드에 "알림에 고정" 스위치 행이 있다. 알림을 만들 수 있는 플랫폼(Android)에서만 보이고, 다른 플랫폼에서는 행 자체가 없다.
  2. R2. 스위치를 켜면 알림 창에 그 기능의 알림이 뜨고, 끄면 사라진다. 값은 설정 영구 저장으로 복원된다. 두 기능의 스위치는 서로 독립이다.
  3. R3. 화면 회전 알림은 접힌 상태에 현재 상태 문구와 잠금 버튼이 있고, 펼치면 0°·90°·180°·270° 버튼과 -90°·+90° 버튼이 더 있다. 동작 규칙은 카드·위젯과 같다(화면 회전 R2~R5).
  4. R4. 화면 꺼짐 방지 알림은 현재 상태 문구와 켬/끔 버튼이 있다. 규칙은 시스템 전역 화면 꺼짐 방지와 같다.
  5. R5. 알림은 소리·진동 없이 뜨고(낮은 중요도), 지속(ongoing) 알림이며, 버튼이 아닌 본문을 탭하면 앱이 열린다. 알림 자체는 앱 프로세스가 죽어 있어도 버튼이 동작한다(위젯 R4).
  6. R6. 알림이 보여주는 상태는 위젯과 같은 시점에 갱신된다. (a) 알림 버튼을 탭한 직후, (b) 시스템 설정(자동 회전·고정 각도·화면 꺼짐 시간)이 바뀌었을 때, (c) 앱이 포그라운드에 있는 동안은 즉시.
  7. R7. 사용자가 알림을 스와이프로 지워도(Android 14+) "알림에 고정" 값은 그대로 켜져 있다. 앱이 다음에 포그라운드로 올 때(onStart) 알림을 다시 띄운다. 지운 알림을 그 자리에서 다시 띄우지는 않는다.
  8. R8. 알림 권한(POST_NOTIFICATIONS)이 없을 때 스위치를 켜면 권한 요청이 열린다. 설정값은 켜진 채 저장되고, 허용되는 순간 알림이 뜬다. 권한이 없는 동안은 스위치 아래에 그 사실이 보인다.
  9. R9. 시스템 설정 변경 권한(WRITE_SETTINGS)이 없으면 알림의 모든 버튼이 권한 중계 Activity 를 열고, 알림 문구가 권한이 필요하다고 말한다(위젯 R5와 같다).
  10. R10. 빠른 설정 타일 편집 목록에 "화면 회전" 타일과 "화면 꺼짐 방지" 타일이 있다. 사용자가 편집 목록에서 끌어다 놓아 추가한다.
  11. R11. 화면 회전 타일을 탭하면 +90° 돌리고 그 각도에 고정한다. 부제에 현재 각도와 잠금 여부가 보이고, 잠겨 있으면 활성, 자동 회전이면 비활성 상태다.
  12. R12. 화면 꺼짐 방지 타일을 탭하면 켬/끔이 바뀐다. 켜져 있으면 활성 상태다.
  13. R13. 타일은 보이는 동안(빠른 설정 패널이 열려 있는 동안)만 상태를 수집해 즉시 갱신하고, 보이지 않는 동안은 아무것도 하지 않는다. 권한이 없으면 탭이 권한 중계 Activity 를 열고 부제가 "권한 필요"다.
  14. R14. 알림·타일의 조작은 카드·위젯과 같은 유스케이스를 거친다(위젯 R7). 규칙이 네 곳에 적히지 않는다.
  15. R15. Android 외 플랫폼에는 알림도 타일도 만들지 않는다. 앱은 Android 13(API 33) 이상만 지원한다.
스코프에서 뺀 것
  • 포그라운드 서비스로 알림을 진짜로 고정하기. Android 14 의 FLAG_ONGOING_EVENT 변경을 피하는 유일한 앱 경로지만, API 34+ 에서 specialUse 타입 선언과 마켓 심사 사유가 필요하고 프로세스를 상주시킨다. 위젯이 지킨 "프로세스 없이 동작한다"와 반대여서 지시대로 onStart 재게시(R7)로 대신한다.
  • 스와이프로 지운 알림의 즉시 재게시. setDeleteIntent로 받을 수는 있지만 사용자가 지운 것을 곧바로 되살리는 동작이다. 지시가 onStart를 골랐다.
  • 재부팅 뒤 자동 게시. RECEIVE_BOOT_COMPLETED 권한이 하나 더 필요하다. 위젯과 같은 이유로 넣지 않는다. 다음 앱 실행의 onStart에 다시 뜬다(한계).
  • 타일 자동 추가 프롬프트(StatusBarManager.requestAddTileService, API 33+)와 타일 롱프레스 화면. 지시에 없다. 사용자가 편집 목록에서 추가하고, 롱프레스는 시스템 기본(앱 정보)이다.
  • 화면 회전 타일의 각도 직접 선택. 타일은 버튼 하나다. 각도를 고르는 것은 알림·위젯·카드가 맡는다.
  • 앱 수명 내 화면 꺼짐 방지의 알림·타일. 앱이 떠 있는 동안만 유효한 기능이라 밖에서 켤 이유가 없다.

공통 구현

commonMain에 들어가는 것은 "알림에 고정" 설정과 알림 권한 상태다. 알림·타일 코드는 위젯과 같은 Android 전용 모듈에 산다.

모델·규칙 (공용)
DeviceRotationNotificationStatus · DeviceRotationNotificationRepository · ObserveDeviceRotationNotificationUseCase · SetDeviceRotationNotificationPinnedUseCase (:feature:rotation:domain), SystemScreenAwakeNotificationStatus · SystemScreenAwakeNotificationRepository · ObserveSystemScreenAwakeNotificationUseCase · SetSystemScreenAwakeNotificationPinnedUseCase (:feature:screen:domain)
저장 (공용)
DefaultDeviceRotationNotificationRepository(키 device_rotation_notification_pinned), DefaultSystemScreenAwakeNotificationRepository(키 system_screen_awake_notification_pinned). 둘 다 SettingsStore + NotificationPermission을 합친다
알림 권한 (공용 계약)
:core:data data/notification/NotificationPermission.kt. expect fun createNotificationPermission(context: PlatformContext): NotificationPermission. Android 만 본문이 있고 나머지는 UnsupportedNotificationPermission(supported = false)
설정 저장소
SettingsStore가 :feature:screen:data에서 :core:data data/settings로 올라간다. 두 번째 기능(rotation)이 쓰게 되어 모듈 구조의 예고대로다. public이 된다

// :feature:rotation:domain — 화면 꺼짐 방지도 이름만 다른 같은 모양이다
data class DeviceRotationNotificationStatus(
    val supported: Boolean = false,   // 이 플랫폼이 알림을 만들 수 있는가
    val permitted: Boolean = false,   // POST_NOTIFICATIONS 가 허용됐는가
    val pinned: Boolean = false,      // 사용자가 "알림에 고정"을 켰는가
)

interface DeviceRotationNotificationRepository {
    fun observeStatus(): Flow<DeviceRotationNotificationStatus>   // cold
    fun readStatus(): DeviceRotationNotificationStatus              // 첫 프레임 초기값 전용
    fun setPinned(pinned: Boolean)
    fun requestPermission()
}

class SetDeviceRotationNotificationPinnedUseCase(
    private val notification: DeviceRotationNotificationRepository,
) {
    suspend operator fun invoke(pinned: Boolean) {
        // 권한이 없어도 값은 켜 둔다. 허용되는 순간 알림이 뜬다(SetKeepSystemScreenAwakeUseCase 와 같은 판단).
        notification.setPinned(pinned)

        if (pinned && !notification.observeStatus().first().permitted) {
            notification.requestPermission()
        }
    }
}

// :core:data — 두 기능이 같은 권한을 본다
interface NotificationPermission {
    val supported: Boolean
    fun readPermitted(): Boolean
    fun observePermitted(): Flow<Boolean>
    fun requestPermission()
}

expect fun createNotificationPermission(context: PlatformContext): NotificationPermission

WRITE_SETTINGS의 observeWriteSettingsPermission과 같은 자리다.
결정: 알림 권한은 투명 Activity 가 런타임 다이얼로그로 요청한다 WRITE_SETTINGS는 설정 화면에서만 허용할 수 있어 requestPermission()이 설정 인텐트를 열면 끝이었다. POST_NOTIFICATIONS는 런타임 권한이라 Activity 가 requestPermissions를 불러야 다이얼로그가 뜬다. data 계층은 애플리케이션 컨텍스트만 갖고 있으므로, :core:data androidMain에 화면 없는 PostNotificationsPermissionActivity를 두고 NEW_TASK로 띄운다. 요청은 카드 스위치를 켤 때만 오므로 앱이 포그라운드라 백그라운드 시작 제한에 걸리지 않는다. 두 번 거부해 다이얼로그가 더 뜨지 않으면(shouldShowRequestPermissionRationale이 false) 앱 알림 설정 화면을 연다. 버린 후보: 앱 알림 설정 화면만 열기(정식 다이얼로그가 있는데 설정으로 보내는 것은 나쁜 UX), ui 모듈의 expect 컴포저블에서 rememberLauncherForActivityResult(권한은 data 가 요청한다는 기존 규칙을 깬다).
결정: 앱이 포그라운드인 동안 알림을 동기화하고, 그것이 onStart 재게시다 :core:widget의 NotificationWidgets.syncWhileStarted가 ProcessLifecycleOwner의 STARTED 동안 각 기능의 NotificationWidget.sync()를 돌린다. sync()는 "알림에 고정" 상태와 기능 상태를 combine해 수집하고, 고정이고 권한이 있으면 notify, 아니면 cancel한다. 이 한 수집이 R2(스위치 즉시 반영), R6(c)(포그라운드 즉시 갱신), R7(onStart마다 첫 방출이 다시 게시), R8(권한이 들어오는 순간 게시)을 모두 만든다. MainActivity.onStart에 직접 쓰지 않는 이유는 :androidApp이 :shared만 보고, 프로세스 수명 관찰이 Activity 하나보다 정확해서다. 상태 조회 규칙의 "수집은 화면 수명에 묶는다"가 여기서는 프로세스 포그라운드 수명이다.
결정: 백그라운드 갱신은 위젯의 설정 변경 트리거를 함께 쓴다 앱이 없는 동안의 R6(b)는 위젯과 같은 문제다. WidgetRefresh.scheduleOnChange에 브로드캐스트 액션 인자를 더해, 위젯은 ACTION_APPWIDGET_UPDATE를, 알림은 자기 리시버의 REFRESH 액션을 받게 했다. 알림 리시버는 REFRESH를 받으면 설정을 다시 읽어 고정이면 다시 게시하고 job 을 다시 건다. 고정이 꺼졌거나 사용자가 알림을 지웠으면(deleteIntent) job 을 지워 사슬을 끊는다. job id 는 위젯과 다르다(회전 0x4A5203, 꺼짐 방지 0x4A5204).
결정: 회전 타일의 탭은 +90°다 후보는 셋이었다. 잠금 토글은 시스템의 "자동 회전" 타일과 같아 만들 이유가 없다. 앱 열기는 타일의 뜻이 아니다. +90°는 알림·위젯 없이도 타일만으로 네 각도를 돌 수 있고, 각도를 고르면 잠근다는 규칙(R5)에 따라 고정도 함께 된다. 자동 회전으로 되돌리는 것은 시스템 타일이 있다.
결정: NotificationPermission은 expect이고, 기능 data 에는 새 expect가 없다 "알림에 고정" 리포지토리에서 플랫폼에 기대는 것은 권한만이다. 저장은 SettingsStore가 이미 플랫폼을 숨긴다. 그래서 두 기능의 Default…NotificationRepository는 commonMain에만 있고, 플랫폼 분기는 :core:data의 createNotificationPermission 하나다. 기능마다 SettingsStore를 한 번씩 만들어 두 인스턴스가 생기는데, 네 플랫폼 모두 같은 파일·노드·저장소를 가리켜 값과 변경 알림이 어긋나지 않는다.

한계

  • Android 14+ 에서 알림은 사용자가 지울 수 있고, 지우면 다음 앱 실행까지 없다. 지시가 고른 동작이다. 위젯과 타일은 영향이 없다.
  • 재부팅 뒤에는 앱을 한 번 열어야 알림이 다시 뜬다. 알림은 재부팅에 남지 않고 BOOT_COMPLETED 리시버를 넣지 않았다.
  • 자동 회전 중에는 알림의 각도가 늦게 바뀐다. 위젯과 같은 한계다. 앱이 포그라운드면 즉시고, 타일은 보이는 동안 즉시다.
  • Android 16 은 두 알림을 한 그룹으로 묶어 접힌 창에는 하나만 보인다. 펼치면 둘이 다 나온다(android.html 한계).
  • 알림 채널을 시스템 설정에서 막으면 스위치가 켜져 있어도 알림이 보이지 않는다. permitted는 앱 단위 알림 허용만 본다. 채널 차단은 카드에 표시되지 않는다.
  • 알림의 색은 앱 팔레트와 다르다. RemoteViews는 JarvisTheme을 받지 못해 시스템 동적 색 리소스(system_accent1_*·system_neutral2_*)를 쓴다. 위젯의 GlanceTheme과 같은 이유다.
  • 알림 문구가 카드·위젯과 세 곳에 적혀 있다. 위젯과 같은 이유(ui 모듈을 의존하지 않음)다. 문구는 위젯 스펙이 기준이다.
  • 타일은 사용자가 직접 추가해야 보인다. 자동 추가 프롬프트는 스코프 밖이다.
