화면 테마 (라이트·다크·시스템)

홈 카드에서 라이트·다크·시스템 중 하나를 고르면 앱 전체가 그 색으로 바뀌고, 앱을 껐다 켜도 고른 값이 남는다.

사용자 지시

lightMode, darkMode, systemMode 3ㄱㅐ 지원해서 선택할 수 있도록 Home에 추가해줘. 이 값은 앱 재시작해도 유지해야해.

2026-09-25 대화.

요구사항

  1. R1. 홈 기능 그리드에 "화면 테마" 카드가 있고, 시스템 설정·라이트·다크 셋 중 하나만 고를 수 있다. 기본값은 시스템 설정이다.
  2. R2. 고르는 즉시 앱 전체(모든 화면·다이얼로그)가 그 모드의 색으로 바뀐다. 라이트는 항상 라이트 색, 다크는 항상 다크 색이다.
  3. R3. 시스템 설정 모드는 OS 의 다크 모드 설정을 따르고, 앱이 떠 있는 동안 OS 설정이 바뀌면 다시 켜지 않아도 따라간다(디자인 시스템 R3 과 같다).
  4. R4. 고른 값은 설정 영구 저장을 거쳐 앱을 완전히 껐다 켜도 복원된다. 다음 실행의 첫 프레임부터 저장된 모드로 그린다.
  5. R5. 저장소가 앱 밖에서 바뀌어도 카드와 색이 따라간다. 저장된 문자열을 모드로 해석할 수 없으면 시스템 설정으로 본다.
  6. R6. 앱이 직접 그리지 않는 표면(Android 상태 막대·내비게이션 막대 아이콘, iOS 상태 막대, macOS 창 제목 막대, Web 페이지 배경·스크롤바)도 가능한 플랫폼에서는 고른 모드를 따른다. 어디까지 가능한지는 플랫폼별 판정에 있다.
스코프에서 뺀 것
  • 시간대별 자동 전환(해 지면 다크). OS 가 이미 제공하므로 시스템 설정 모드로 대신한다.
  • 모드마다 다른 팔레트(다크 색을 여러 벌 두는 것). 색은 디자인 시스템의 라이트·다크 두 벌뿐이다.
  • 터미널 글자 영역. 셸 프로그램이 어두운 배경을 가정하므로 라이트 모드에서도 터미널 창은 어둡다(터미널).

화면·동작

항목값
제목화면 테마
아이콘JarvisIcons.Moon (새 아이콘. 초승달 윤곽선)
설명앱의 밝은 색과 어두운 색을 고릅니다. 시스템 설정은 OS 의 다크 모드를 따릅니다.
컨트롤Material3 RadioButton 세 줄. 줄 전체가 selectable(role = RadioButton) 이라 라벨을 눌러도 골라진다. 라디오 버튼 자체는 표시 역할만 한다. 라벨은 위에서부터 "시스템 설정" · "라이트" · "다크"
테스트 태그카드 feature:themeMode, 줄 feature:themeMode:system / feature:themeMode:light / feature:themeMode:dark
  • 줄을 누르면 즉시 저장소에 쓴다. 화면 상태의 원본은 메모리가 아니라 저장소다(설정 영구 저장의 동작과 같다). 저장소가 알려 준 값이 카드의 선택과 루트 테마 양쪽에 돌아온다.
  • 루트 JarvisTheme 은 darkTheme 을 인자로 받는다. 시스템 설정 모드면 isSystemInDarkTheme(), 라이트면 false, 다크면 true 다.
  • 모드가 바뀌면 플랫폼에도 알린다(R6). 무엇을 하는지는 플랫폼마다 다르고, 아무것도 못 하는 플랫폼은 조용히 no-op 이다.
결정: 세그먼트 버튼이 아니라 라디오 줄이다 M3 SingleChoiceSegmentedButtonRow 가 이런 삼지선다의 표준 컨트롤이지만, 홈 그리드의 카드 최소 폭이 220dp(gridMinCellWidth)라 내용 폭이 188dp 다. 세 칸이면 칸당 62dp 인데 M3 기본 여백 24dp 를 빼면 38dp 라 "시스템" 세 글자(14sp, 약 42dp)가 잘린다. 카드 폭은 화면에 따라 달라지므로 폭에 무관한 세로 라디오 줄을 택했다. FilterChip 을 FlowRow 에 놓는 안은 좁으면 두 줄로 접혀 카드 높이가 흔들려서 버렸다.

공통 구현

기능 하나가 :feature:theme:domain · :feature:theme:data · :feature:theme:ui 셋을 갖는다(모듈 구조 R1). 패키지는 domain.theme · data.theme · ui.theme 다.

모델
domain/theme/ThemeMode.kt — enum class ThemeMode { SYSTEM, LIGHT, DARK } 와 fun isDark(systemInDark: Boolean): Boolean. 모드를 실제 다크 여부로 푸는 규칙은 이 한 함수에만 있다
계약
domain/theme/ThemeSettingsRepository.kt(설정. observeThemeMode() · readThemeMode() · setThemeMode(mode)), domain/theme/ThemeAppearanceRepository.kt(플랫폼 표면. applyThemeMode(mode))
유스케이스
ObserveThemeModeUseCase(scope): StateFlow<ThemeMode>, SetThemeModeUseCase(mode), ApplyThemeModeUseCase()(설정을 수집해 플랫폼 표면에 넘긴다)
상태
data/theme/DefaultThemeSettingsRepository.kt. 키 theme_mode, 값은 "system" · "light" · "dark" 문자열. 모르는 값은 SYSTEM
공급
internal expect fun createThemeAppearance(context: PlatformContext): ThemeAppearance (data.theme). ThemeAppearance.apply(mode) 하나를 가진 인터페이스다
UI
ui/theme/ThemeModeCard.kt(카드), ui/theme/ThemeModeViewModel.kt(카드), ui/theme/AppTheme.kt 의 @Composable fun appDarkTheme(): Boolean 과 ThemeEffectViewModel(앱 루트)
// :feature:theme:ui — 앱 셸이 루트에 쓰는 한 줄
JarvisTheme(darkTheme = appDarkTheme()) { … }

@Composable
fun appDarkTheme(): Boolean {
    val viewModel = koinViewModel<ThemeEffectViewModel>()   // init 에서 ApplyThemeModeUseCase 를 띄운다
    val mode by viewModel.themeMode.collectAsStateWithLifecycle()
    return mode.isDark(isSystemInDarkTheme())
}
// :feature:theme:domain — 언제 플랫폼에 알리는지
class ApplyThemeModeUseCase(settings, appearance) {
    suspend operator fun invoke() {
        settings.observeThemeMode().collect(appearance::applyThemeMode)
    }
}
결정: SettingsStore 에 문자열을 더한다 모드는 셋이라 boolean 하나로 적을 수 없다. 후보는 셋이었다.
  • 채택. SettingsStore 에 getString · putString · observeString 을 더하고, 네 actual 이 각자 저장소의 문자열 API 를 부른다. 설정 영구 저장 스펙이 "다른 타입이 필요하면 인터페이스에 메서드를 추가하고 네 actual 을 함께 늘린다" 고 정해 둔 길이다.
  • boolean 두 개(dark_forced, light_forced)로 쪼개는 안. 둘 다 true 인 상태가 표현 가능해져서 버렸다.
  • Int(서수)로 적는 안. 문자열이 필요한 건 마찬가지고, 서수는 enum 순서를 바꾸면 저장값이 뒤바뀐다. 문자열 이름은 그 위험이 없다.
값은 enum 이름의 소문자다. 저장값 해석은 ThemeMode.fromStored(value) 가 맡고, 모르는 값은 SYSTEM 이다(R5).
결정: 플랫폼 표면은 data 의 expect 로 적용한다 화면 꺼짐 방지는 Compose 의 Modifier 가 플랫폼 API 를 대신 불러서 ui 에 예외를 두었지만, 여기서는 네 플랫폼 모두 애플리케이션 단위 핸들(Android UiModeManager, iOS UIApplication 의 창, JVM 시스템 프로퍼티, Web document)로 닿을 수 있어 모듈 구조 R5 대로 data 에 둔다. Android 에서 Activity 를 요구하는 enableEdgeToEdge 재호출 안(ui 예외가 필요했다)은 UiModeManager.setApplicationNightMode 가 앱의 uiMode 를 통째로 바꿔 시스템 막대까지 맞춰 주므로 버렸다. 자세한 후보는 각 플랫폼 스펙에 있다.
결정: 첫 프레임의 다크 여부는 저장소를 동기로 읽어 정한다 ObserveThemeModeUseCase 는 observeThemeMode().stateIn(scope, WhileSubscribed(), readThemeMode()) 다. Flow 의 첫 방출을 기다리면 첫 프레임이 시스템 색으로 그려졌다가 바뀌어 깜빡인다(R4 "첫 프레임부터"). 설정 영구 저장의 read* 규칙 그대로다.
결정: JVM 은 시작 시점에 한 번 더 적용한다 macOS 창 제목 막대의 외관은 AWT 가 뜰 때 시스템 프로퍼티 apple.awt.application.appearance 를 한 번만 읽는다. 그래서 :shared 의 JVM startJarvisKoin() 이 첫 창보다 먼저 ThemeAppearanceRepository.applyThemeMode(ThemeSettingsRepository.readThemeMode()) 를 부른다. 다른 세 플랫폼은 런타임 적용만으로 충분해서 이 호출이 없다. 자세한 것은 jvm.html.

플랫폼별 판정

앱 안의 색(R1–R5)은 네 플랫폼 모두 commonMain Compose 코드로 같다. 갈리는 것은 R6, 앱 밖 표면이다.

플랫폼판정앱 밖 표면문서
Android구현UiModeManager.setApplicationNightMode. 앱의 uiMode 가 바뀌어 상태 막대 아이콘 색도 따라간다. MainActivity 가 onConfigurationChanged 에서 enableEdgeToEdge() 를 다시 부른다android.html
iOS구현UIWindow.overrideUserInterfaceStyle. 상태 막대와 isSystemInDarkTheme() 이 함께 따라간다ios.html

Web구현document.documentElement.style.colorScheme. 캔버스 밖 페이지 배경·스크롤바가 따라간다web.html

한계

  • Android 창 배경(Theme.Material.Light.NoActionBar)은 첫 프레임 전에 잠깐 밝다. 다크 모드를 골라도 앱을 켤 때 흰 화면이 한 프레임 보일 수 있다. 디자인 시스템에 이미 적힌 한계다.
  • iOS 는 창에 오버라이드가 걸리기 전(첫 컴포지션 이전)의 상태 막대가 시스템 외관을 따른다. 앱 안의 색은 첫 프레임부터 맞다.
  • JVM 은 창 제목 막대가 다음 실행부터 따라간다(우회). 라이트·다크로 켠 프로세스에서 시스템 설정으로 되돌리면 내용도 다음 실행까지 그 외관에 머문다. skiko 가 OS 설정이 아니라 앱의 유효 외관을 읽기 때문이다. Linux·Windows 는 프로퍼티가 무시되고 예외는 없다.
  • Web 은 캔버스가 그려지기 전 잠깐의 페이지 배경이 브라우저 기본이다. color-scheme 은 캔버스가 그려진 뒤 적용된다.
