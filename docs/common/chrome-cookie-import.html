Chrome 쿠키 가져오기

브라우저 탭 주소 줄의 아이콘 버튼을 누르면 이 PC 의 Chrome 프로필(계정) 목록이 뜨고, 고른 프로필의 모든 사이트 쿠키를 이 앱의 웹뷰로 옮겨 이미 로그인된 채로 웹을 쓴다. 시스템 웹뷰의 영구 저장소에 들어가서 앱을 껐다 켜도, 페이지를 옮겨도 로그인이 이어진다.

사용자 지시

webView 주소창 옆에 cookie/session 정보 받아오는 아이콘 버튼 추가해줘. 그리고 클릭 시 PC에 로그인된 chrome 계정 목록 나타내고 해당 계정의 Cookie/Session 같은 정보를 포함하도록 해줘. 이 작업은 한번만 되는게 아니라 앱 종료후 다시 켜도 유지해야하고 지금 보는 사이트만 가져오는게 아니라 모든 사이트 가져와서 웹페이지 이동해도 로그인 이어가는게 목표야.

2026-09-24 대화. "webView" 는 터미널의 브라우저 탭으로, "주소창 옆" 은 그 탭의 주소 줄로 읽었다. "chrome 계정 목록" 은 이 PC 의 Chrome 프로필(Local State 의 profile.info_cache, 프로필마다 로그인된 Google 계정이 붙는다)로 읽었다. "Cookie/Session 같은 정보" 는 로그인을 잇는 쿠키로 읽었다 — Chrome 의 localStorage·IndexedDB 는 옮길 수 없다(한계).

요구사항

  1. R1. 브라우저 탭 주소 줄에서 새로 고침 버튼 다음, 주소 입력칸 앞에 아이콘 버튼(JarvisIcons.User, "Chrome 계정 가져오기")을 둔다. Chrome 쿠키 가져오기를 지원하는 타깃에서만 보인다(R6).
  2. R2. 버튼을 누르면 이 PC 의 Chrome 프로필 목록이 드롭다운으로 뜬다. 항목은 위에서부터 Default, Profile 1, … 순이고, 각 항목은 프로필 이름과 로그인된 Google 계정 이메일(있으면)을 보인다. 목록은 버튼을 누를 때마다 그때의 상태를 다시 읽는다(저장하지 않는다). 프로필이 하나도 없으면 "가져올 계정이 없습니다" 를 보인다.
  3. R3. 프로필을 고르면 그 프로필에 저장된 모든 사이트의 쿠키를 복호화해서 지금 브라우저 탭 웹뷰의 쿠키 저장소에 넣고, 넣은 뒤 페이지를 새로 고친다. 지금 보는 사이트만이 아니라 저장된 쿠키 전부다.
  4. R3a. 쿠키의 SameSite 는 웹뷰가 받아들이도록 넣는다. Chrome 의 미지정(samesite = -1)은 Chrome 기본값인 Lax 로 넣는다(None 이 아니다). None(0)은 Secure 일 때만 None 으로, Secure 가 아니면 Lax 로 낮춘다. WKWebView 는 Secure 가 아닌 SameSite=None 쿠키를 버리기 때문이다 — 이를 어기면 Google 의 SID·HSID·APISID(미지정·비-Secure) 가 통째로 버려져 로그인이 안 된다.
  5. R3c. 도메인 쿠키(.example.com)는 그것이 닿아야 할 호스트마다 호스트 전용으로 복제해서 넣는다 — example.com, www.example.com, 그리고 이 프로필이 쿠키를 가진 하위 도메인 전부. 데스크톱 웹뷰(wry)가 도메인 쿠키를 앞의 . 을 떼고 호스트 전용으로 저장해서(jvm.html) 원본 그대로면 .google.com 로그인 쿠키가 www.google.com·accounts.google.com 같은 실제 로그인 검사 도메인에 닿지 않기 때문이다. 이렇게 펴야 YouTube·Naver 로그인이 이어진다(2026-09-24 손으로 확인).
  6. R3b. 가져오기가 끝나면 결과를 Snackbar 로 알린다. 세 가지다 — 성공 "쿠키 N개를 가져왔습니다"(넣고 되읽기 확인, R8a), 키체인·읽기 실패 "쿠키를 가져오지 못했습니다 — 키체인 접근을 허용했는지 확인하세요"(0개), 웹뷰 미준비 "웹뷰가 준비되지 않아 넣지 못했습니다 — 페이지가 뜬 뒤 다시 시도하세요"(되읽기 비어 있음). Snackbar 는 네이티브 페이지에 가려지므로 떠 있는 동안 페이지를 치운다(R6 과 같은 이유). 성공일 때만 페이지를 새로 고쳐(R3) 로그인된 화면이 뜬다.
  7. R4. 넣은 쿠키는 시스템 웹뷰의 기본(영구) 저장소에 들어간다. 그래서 (ㄱ) 모든 브라우저 탭이 같은 쿠키를 함께 쓰고, (ㄴ) 페이지를 옮기거나 새 브라우저 탭을 열어도 로그인이 이어지고, (ㄷ) 앱을 껐다 켜도 남는다. 한 번 가져오면 다시 가져오지 않아도 된다.
  8. R5. 다시 같은 프로필을 고르면 그 프로필의 지금 쿠키로 덮어쓴다(같은 이름·도메인·경로면 값이 바뀐다). 이렇게 만료됐거나 바뀐 로그인을 새로 고친다.
  9. R6. 드롭다운이 떠 있는 동안에는 웹 페이지가 사라지고 그 칸이 비어 보인다. 닫으면 같은 페이지가 다시 보인다(새로 부르지 않는다). 네이티브 웹뷰가 Compose 로 그린 드롭다운을 가리기 때문이다(브라우저 R9 와 같은 이유).
  10. R7. Chrome 쿠키 가져오기를 지원하지 않는 타깃(Android·iOS·Web, 그리고 macOS 가 아닌 데스크톱)에서는 버튼이 없다. 지원 판정은 실행 중에 바뀌지 않는다.
  11. R8. 복호화 키를 얻거나 쿠키를 읽지 못하면(키체인 접근을 허용하지 않음, Chrome 이 설치돼 있지 않음 등) 아무 쿠키도 넣지 않고 조용히 no-op 이다(0개). 앱은 예외로 끝나지 않는다.
  12. R8a. 넣은 뒤 방금 넣은 도메인의 쿠키를 되읽어 실제로 저장소에 들어갔는지 확인한다. 라이브러리의 cookieManager.setCookie 는 웹뷰(panel)가 아직 붙지 않았으면 예외 없이 아무 일도 하지 않으므로, 되읽어 비어 있으면 "웹뷰가 준비되지 않아 넣지 못했습니다 — 페이지가 뜬 뒤 다시 시도하세요" 를 알리고 새로 고치지 않는다. 되읽기가 비어 있지 않을 때만 성공으로 보고 새로 고친다(R3).
스코프에서 뺀 것
  • 쿠키가 아닌 저장소 — localStorage·sessionStorage·IndexedDB·Service Worker 캐시. Chrome 은 이것들을 프로필 폴더의 LevelDB 에 두는데, 시스템 웹뷰(WKWebView)의 저장 형식과 달라 옮길 수 없다. 로그인은 거의 다 쿠키로 이어지므로 쿠키만 가져온다(한계).
  • 북마크, 방문·다운로드 기록, 저장된 비밀번호, 자동완성, 확장 프로그램.
  • 가져온 쿠키를 이 앱이 따로 파일에 저장하는 것. 시스템 웹뷰의 기본 저장소가 이미 영구라서(R4) 두 번 저장하지 않는다. 인증 토큰을 평문으로 한 벌 더 두지 않으려는 것이기도 하다.
  • Chrome 이 아닌 브라우저(Edge·Brave·Safari 등)와 macOS 가 아닌 Chrome(Windows·Linux 는 키 보관 방식이 다르다).
  • 가져올 쿠키를 사이트별로 고르는 것. "모든 사이트" 가 지시다.
2026-09-25: JVM 엔진이 JCEF 로 바뀌었다 웹 브라우저의 JVM 엔진이 WKWebView(wry) 에서 Chromium(JCEF)으로 바뀌었다. 그래서 JVM 에서는 R3a·R3c·R6 이 필요 없어졌다 — 쿠키를 Chrome 이 저장한 모양 그대로(도메인 쿠키, SameSite 그대로) CDP Network.setCookies 로 넣고, 드롭다운·Snackbar 는 Compose 가 그린 페이지 위에 그대로 뜬다. R4 의 "시스템 웹뷰의 기본 저장소" 는 JVM 에서 엔진의 영구 저장소(앱 데이터 폴더의 jcef/cache)다. R8a 의 되읽기는 Network.getCookies 다. 나머지(R1·R2·R3·R3b·R5·R7·R8)는 그대로다. 가져오기는 JVM 에만 있으므로(R7) wry 우회였던 expandCookiesForHostOnlyStore 는 지운다.

공통 구현

도메인
ChromeProfile(directory, name, email), BrowserCookie(name, value, domain, path, expiresEpochSeconds, isSecure, isHttpOnly, sameSite, isSessionOnly).
TerminalRepository.isChromeImportSupported: Boolean, observeChromeProfiles(): Flow<List<ChromeProfile>>(cold, 수집할 때 읽는다 — 상태 조회), suspend importChromeCookies(profileDirectory): List<BrowserCookie>(명령, 복호화 결과를 돌려준다).
use case: IsChromeImportSupportedUseCase, ObserveChromeProfilesUseCase, ImportChromeCookiesUseCase.
공급
TerminalDataSource 에 isChromeImportSupported, observeChromeProfiles(), importChromeCookies(dir) 를 더한다. 실제 읽기·복호화는 JVM actual(Terminal.jvm.kt → ChromeCookieReader)에만 있고, 그 밖(UnsupportedTerminalDataSource, Android)은 false·빈 목록이다. 새 expect 함수는 만들지 않는다 — 기존 createTerminalDataSource 이음매를 그대로 쓴다
상태
TerminalViewModel.isChromeImportSupported, suspend chromeProfiles() = observeChromeProfilesUseCase().first()(드롭다운을 열 때 지금 값을 읽는 명령), suspend importChromeCookies(dir)
UI
TerminalBrowser.kt 의 주소 줄에 가져오기 버튼과 드롭다운. 프로필을 고르면 importCookies(dir) 로 받은 각 쿠키를 io.github.kdroidfilter.webview.cookie.Cookie 로 바꿔(SameSite 는 R3a 규칙) state.cookieManager.setCookie("https://<domain>", cookie) 로 넣고, 넣은 개수를 SnackbarHostState.showSnackbar 로 알린 뒤 성공이면 navigator.reload() 한다. 드롭다운이 열렸거나(R6) Snackbar 가 떠 있는 동안(R3b) 웹뷰 크기를 0 으로 줄인다(pageHidden || menuExpanded || snackbar)
결정: 시스템 웹뷰의 영구 쿠키 저장소에 한 번 넣는 것으로 R4(영구·모든 탭·모든 사이트)를 끝낸다 composewebview 의 JVM 백엔드(wry)는 incognito 가 꺼진 기본값에서 WKWebsiteDataStore.default()(영구) 를 쓴다(바이트코드에서 defaultDataStore·nonPersistentDataStore 분기 확인, jvm.html). WebViewState.cookieManager.setCookie 는 이 공유 저장소에 쓰므로, 한 번 넣으면 (ㄱ) 모든 브라우저 탭이 같은 저장소를 읽고 (ㄴ) 앱을 다시 켜도 남는다. 그래서 가져온 쿠키를 이 앱이 따로 저장하지 않는다. 만약 이 저장소가 영구가 아닌 것으로 드러나면, 대안은 가져온 쿠키를 설정 저장소에 스냅샷으로 두고 브라우저 웹뷰가 뜰 때마다 다시 넣는 것이다 — 인증 토큰을 평문으로 한 벌 더 두게 되므로 지금은 택하지 않는다.
결정: 복호화 결과(쿠키 목록)를 data 가 UI 로 돌려주고 주입은 UI 가 한다 쿠키를 넣을 대상(cookieManager)은 살아 있는 웹뷰의 Compose 상태다. data 계층은 그 상태를 모른다. 그래서 data 는 복호화한 BrowserCookie 목록만 돌려주고, composewebview 의존성이 이미 있는 UI 가 이를 라이브러리 Cookie 로 바꿔 넣는다. importChromeCookies 는 결과가 있는 명령이라 suspend 가 맞다(상태 조회 규칙의 "명령과 그 결과").

한계

  • 쿠키만 옮긴다. 사이트가 localStorage·IndexedDB 에 로그인 상태를 두면(일부 SPA) 그 사이트는 다시 로그인해야 한다. Chrome 의 LevelDB 저장 형식을 WKWebView 로 옮길 수 없다.
  • 데스크톱은 도메인 쿠키를 호스트별로 펴서 넣으므로(R3c), 프로필에 쿠키가 없던 하위 도메인은 빠진다. 예: 방문한 적 없는 myaccount.google.com 은 로그인이 안 이어질 수 있다. 로그인 흐름이 지나는 accounts.*·nid.* 같은, 쿠키가 있는 하위 도메인은 이어진다.
  • 쿠키가 다 들어가도 사이트가 세션을 기기·User-Agent 에 묶으면(Google 은 점점 그렇게 간다) 다시 확인을 요구할 수 있다. 다만 SID·__Secure-3PSID·LOGIN_INFO 등 로그인 쿠키가 제대로 들어가면 보통 YouTube 로그인은 이어진다(R3a 를 어기면 이 쿠키들이 버려져 로그아웃으로 보였다).
  • 처음 가져올 때 macOS 키체인 접근 허용 창이 한 번 뜬다. "항상 허용" 을 누르지 않으면 가져올 때마다 뜬다. 이 앱은 Chrome 이 아니라서 Chrome 이 만든 키체인 항목을 처음 읽을 때 사용자 확인이 필요하다.
  • 쿠키를 가져오는 프로필과 Chrome 이 동시에 켜져 있어도 읽는다(Cookies DB 를 복사해서 연다). 다만 Chrome 이 방금 쓴, 아직 메인 DB 에 합쳐지지 않은 쿠키(WAL)는 빠질 수 있다.
  • 가져온 뒤 Chrome 에서 로그아웃하거나 세션이 만료돼도 이 앱의 쿠키는 그대로다. 최신 상태로 맞추려면 같은 프로필을 다시 가져온다(R5).
  • 플랫폼마다의 한계는 각 플랫폼 문서에 있다.
