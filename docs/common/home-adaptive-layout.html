홈 적응형 배치 (지원 기능 우선 정렬 · 소형 창 타일 · 기능 화면)

홈은 이 플랫폼에서 쓸 수 있는 기능을 앞에 놓는다. 창이 Medium(600dp) 이상이면 지금처럼 홈에서 바로 제어하는 카드를, 그보다 좁으면 아이콘과 라벨뿐인 타일을 놓고, 타일을 누르면 그 기능만 담은 화면에서 설정한다.

사용자 지시

지금 홈화면에 많은 기능들이 노출되잖아. 그래서 모바일 화면에서 답답한 것 같아.

일단 정렬을 각 플랫폼 별로 가능한 것들 먼저 노출되도록 해줘.

그리고 각 기능별 홈화면 만들어서 거기서 설정할 수 있도록 UI/UX 개선해줘.

Medium 이상 사이즈 단말에서는 지금처럼 홈에서 제어할 수 있는 것들 노출하고 Medium보다 작은 경우 단순히 아이콘 + 라벨만 노출해서 홈에서 세팅하도록 해줘.

2026-09-26 대화.

요구사항

  1. R1. 홈의 기능 순서는 이 플랫폼에서 지금 쓸 수 있는 기능이 먼저다. 지원 여부가 같은 기능들 사이의 순서는 FeatureGrid 에 적은 순서(화면 꺼짐 방지, 시스템 전역 화면 꺼짐 방지, 화면 테마, 프로파일링, 에뮬레이터, 화면 회전, 터미널, 배터리, 집중 타이머, 개발자 도구, 단위 변환, 텍스트 도구, 계산기, QR 코드, 세계 시계)를 지킨다(안정 정렬).
  2. R2. 지원 여부는 기능이 스스로 말한다. 정적인 기능(화면 꺼짐 방지, 화면 테마, 프로파일링, 집중 타이머, 개발자 도구, 단위 변환, 텍스트 도구, 계산기, QR 코드, 세계 시계)은 늘 지원이고, 상태에 달린 기능(시스템 전역 화면 꺼짐 방지·화면 회전의 supported, 터미널의 isSupported, 에뮬레이터의 셀 수 있는 플랫폼 유무, 배터리의 BatteryStatus)은 그 상태를 따르며 값이 바뀌면 순서도 바뀐다.
  3. R3. 창 너비가 600dp 이상(M3 창 크기 등급 Medium·Expanded)이면 홈은 지금과 같은 기능 카드를 놓는다. 카드의 컨트롤·문구·테스트 태그는 바뀌지 않는다.
  4. R4. 창 너비가 600dp 미만(Compact)이면 홈은 기능마다 아이콘 하나와 라벨 하나뿐인 타일을 놓는다. 타일에는 스위치·버튼·수치가 없다.
  5. R5. 타일을 누르면 그 기능의 화면이 열린다. 화면 꺼짐 방지·시스템 전역 화면 꺼짐 방지·화면 테마·프로파일링·화면 회전·배터리·집중 타이머는 뒤로 버튼과 제목이 있는 상단 막대 아래에 홈 카드와 같은 컨트롤을 담은 새 화면이고, 에뮬레이터·터미널·개발자 도구·단위 변환·텍스트 도구·계산기·QR 코드·세계 시계는 카드를 눌렀을 때와 같은 기존 화면이다.
  6. R6. 기능 화면에서 바꾼 설정은 홈 카드에서 바꾼 것과 같다. 같은 ViewModel·유스케이스를 거치고 같은 곳에 저장된다.
  7. R7. 지원하지 않는 기능의 타일은 잠긴다(눌리지 않고 흐리게 그려진다). 카드 모드에서 그 기능의 카드가 잠기는 것과 같은 뜻이다.
  8. R8. 창 크기가 바뀌면(데스크톱 창 크기 조절, 태블릿 분할 화면) 다음 프레임에 카드와 타일이 서로 바뀐다. 앱을 다시 켤 필요가 없다.
  9. R9. 앱 셸(:app:ui)은 여전히 기능의 ViewModel·유스케이스를 모른다. 기능은 지원 여부·카드·아이콘·라벨·화면 라우트를 하나의 값(HomeFeature)으로 내놓고, 셸은 그 값만 본다.
스코프에서 뺀 것
  • 앱 정보 카드는 창 크기와 무관하게 홈 맨 위에 그대로 남는다. 줄이거나 타일로 바꾸라는 지시가 없었다.
  • 카드 모드에서 카드를 눌러 기능 화면으로 가는 것. Medium 이상에서는 홈에서 바로 제어하라는 지시라, 카드는 지금과 같이 동작하고 새 진입점을 더하지 않았다. 창을 좁혔다 넓히면 기능 화면이 백스택에 남아 카드 모드에서도 열려 있을 수 있는데, 이때도 뒤로 가면 홈이다.
  • Expanded 등급의 별도 배치(두 칸 화면 등). Medium 과 Expanded 를 가르지 않는다.
  • 사용자가 순서를 바꾸거나 기능을 숨기는 것. 지시에 없다.

결정: 기능이 HomeFeature 하나를 내놓고, 셸은 그것만 정렬·배치한다
  • 채택. :core:ui 의 인터페이스. 지원 여부와 카드가 @Composable 이라 기능이 자기 ViewModel 을 koinViewModel() 로 직접 받는다. 셸이 유스케이스를 모른다는 기존 결정이 그대로 지켜지고, 기능을 더할 때 고치는 셸 파일도 여전히 FeatureGrid 하나다. DeviceScreens 가 같은 꼴(컴포저블 멤버를 가진 인터페이스)이다.
  • 셸이 기능마다 is<기능>Supported() 컴포저블을 따로 부르고 카드·타일도 따로 적는다. 열다섯 기능 × 네 값을 셸이 손으로 짝지어야 해서 버렸다.
  • Koin 에 HomeFeature 를 등록하고 셸이 getAll() 로 모은다. 순서를 Koin 모듈 로드 순서에 맡기게 되어 버렸다. 순서는 셸이 한 곳에서 적는 편이 읽기 쉽다.
  • 플랫폼마다 expect 로 고정 순서를 준다. 지원 여부가 상태(에뮬레이터 개수, 권한)에 달린 기능을 표현할 수 없어 버렸다.
결정: 창 등급은 LocalWindowInfo.containerSize 로 직접 가른다
  • 채택. Compose 가 네 타깃 모두 WindowInfo.containerSize 에 창(Android 는 Window, iOS 는 UIWindow, JVM 은 ComposeWindow 내용, Web 은 canvas) 크기를 넣어 준다. 열 줄이고 의존성이 없다. 테스트는 LocalWindowInfo 를 바꿔 끼워 Compact 를 만든다.
  • org.jetbrains.compose.material3:material3-window-size-class 의 calculateWindowSizeClass(). 실험 API(@ExperimentalMaterial3WindowSizeClassApi)고 Android 에서는 Activity 를 요구해 컴포지션 로컬로 바꿔 끼울 수 없다. 버렸다.
  • material3-adaptive 의 currentWindowAdaptiveInfo(). androidx.window 를 끌고 오고 위와 같은 이유로 테스트가 어렵다. 버렸다.
  • BoxWithConstraints 로 홈 영역의 너비를 잰다. 지시가 "단말 크기" 라 창 기준이 맞고, 화면 여백(16dp)만큼 경계가 어긋난다. 버렸다.
결정: 기능 화면은 홈 카드를 그대로 담는다 화면 꺼짐 방지·화면 테마·프로파일링·화면 회전·시스템 전역 화면 꺼짐 방지·배터리·집중 타이머의 기능 화면은 상단 막대 아래에 그 기능의 카드 컴포저블을 그대로 놓는다. 컨트롤을 화면용으로 다시 만들면 카드와 화면이 서로 다른 상태·문구를 갖게 되고 테스트 태그도 둘이 된다. 카드를 재사용하면 R6 이 구조로 보장되고, 카드 테스트가 기능 화면에서도 같은 태그로 돈다.
결정: 타일은 높이를 고정한다 LazyVerticalGrid 는 한 줄의 항목을 같은 높이로 늘리지 않는다. 라벨이 한 줄인 타일과 두 줄인 타일("화면 꺼짐 방지 (시스템 전역)")이 나란히 놓이면 아래 끝선이 어긋나므로 tileHeight(112dp = 아이콘 32 + 간격 8 + bodyMedium 두 줄 40 + 카드 여백 16 × 2)로 고정하고 라벨은 두 줄에서 말줄임한다. staggered 그리드를 쓰지 않는 이유도 같다 — 높이가 같으면 행으로 묶어도 빈 공간이 없다.

한계

  • 지원 여부가 나중에 바뀌는 기능(에뮬레이터 개수, 회전 권한, 배터리 유무)은 그 순간 순서가 움직인다. 사용자가 누르려던 자리가 바뀔 수 있다. 에뮬레이터·배터리는 답이 오기 전을 지원으로 두어 움직임을 한 번으로 줄였다.
  • 기능 화면이 백스택에 있는 채로 창을 넓히면 카드 모드에서 열 수 없는 화면이 열려 있는 상태가 된다. 뒤로 가면 홈이고 동작에 문제는 없다.
  • 타일 라벨은 두 줄에서 말줄임한다. 128dp 타일에 "화면 꺼짐 방지 (시스템 전역)" 이 두 줄에 다 들어가는 것은 M3 기본 글꼴 기준이라, 시스템 글꼴 크기를 크게 키우면 끝이 잘릴 수 있다.
  • 배치 결과(열 수, 타일 높이)는 자동 테스트로 가리지 않는다. 홈 그리드 세로 배치와 같은 이유다. 순서는 시맨틱 노드의 좌표로 확인한다.
