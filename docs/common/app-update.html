앱 업데이트

main 에 새 버전이 머지되면 GitHub Actions 가 macOS DMG 를 만들어 GitHub Release 로 올리고, 데스크톱 앱은 앱 정보 카드에 새 버전을 알려 버튼 하나로 받아 설치하고 다시 띄운다.

사용자 지시

origin/main에 머지되면 git action으로 dmg파일 만들어서 release, tag 지정하도록 하면 어때? 그리고 우리 앱에서는 버전 확인해서 최신버전 있으면 업데이트 기능을 재공해서 설치까지 하는거지.

2026-09-25 대화.

jvm을 dmg로 만드는데 서명이 필요해? local에서는 gradle로 바로 되던거 아니었어?

ad-hoc으로 진행해줘. 설치도 버튼 누르면 바로 종료하고 재실행까지 해줘.

2026-09-25 대화. 서명이 DMG 빌드가 아니라 배포(Gatekeeper)와 업데이트 뒤 권한 유지에만 영향을 준다는 설명을 듣고 ad-hoc 서명을 골랐다. 설치 방식은 "받아 두고 다음 종료 때 교체" 대신 "바로 종료하고 교체한 뒤 재실행"을 골랐다.

요구사항

  1. R1. 머지하면 배포. origin/main 에 push 가 들어오면 GitHub Actions 가 ./gradlew :desktopApp:packageReleaseDmg 로 DMG 를 만들고, 태그 v<appVersion> 와 같은 이름의 GitHub Release 를 만들어 DMG 를 올린다. appVersion 은 gradle/libs.versions.toml 의 값이다(release 빌드 R4).
  2. R2. 버전을 올린 머지만 배포. 태그 v<appVersion> 가 이미 있으면 워크플로는 빌드하지 않고 성공으로 끝난다. 같은 버전의 Release 를 덮어쓰지 않는다.
  3. R3. 체크섬. Release 에는 DMG 와 함께 그 SHA-256 을 적은 <DMG 이름>.sha256 이 올라간다. 체크섬이 없는 Release 는 앱이 설치 대상으로 보지 않는다.
  4. R4. ad-hoc 서명. CI 는 인증서 없이 jpackage 의 ad-hoc 서명 그대로 올린다. 저장소 Secrets 에 서명 키를 두지 않는다.
  5. R5. 새 버전 확인. 데스크톱 앱은 GitHub 의 최신 Release(releases/latest, draft·prerelease 제외)를 읽어, 태그의 버전이 지금 앱의 APP_VERSION 보다 크면 새 버전으로 본다. 버전은 MAJOR.MINOR.PATCH 를 숫자로 비교하고, 이 형식이 아닌 태그는 무시한다.
  6. R6. 확인 시점. 앱 정보 카드가 화면에 있는 동안 처음 한 번, 그 뒤 AppUpdateCheckInterval(1시간)마다 다시 확인한다. 카드가 화면에서 사라지면 확인을 멈춘다(상태 조회).
  7. R7. 알림. 새 버전이 있으면 앱 정보 카드에 "새 버전" 줄과 그 버전, "업데이트" 버튼이 나타난다. 없거나 확인하지 못했으면 그 줄은 없다.
  8. R8. 설치. "업데이트"를 누르면 DMG 를 받아 SHA-256 을 확인하고, DMG 안의 Jarvis.app 을 설치된 앱 옆에 풀어 둔 뒤 앱을 정상 종료한다. 앱이 끝나면 설치된 Jarvis.app 을 새것으로 바꾸고 다시 띄운다. 사용자가 누를 것은 버튼 하나다.
  9. R9. 실패하면 그대로. 받기·확인·풀기 중 하나라도 실패하면 앱은 종료하지 않고 카드에 "업데이트하지 못했습니다: <이유>"와 "다시 시도" 버튼을 보여준다. 설치된 앱은 바뀌지 않는다. 교체 단계에서 실패하면 옛 앱을 제자리로 돌려놓고 다시 띄운다.
  10. R10. 설치된 앱만. 업데이트는 .app 번들로 설치된 macOS 앱에서만 켜진다. :desktopApp:run 으로 띄운 개발 실행, macOS 밖 데스크톱, Android·iOS·Web 에서는 확인도 하지 않고 줄도 없다.
스코프에서 뺀 것
  • Developer ID 서명·공증. 인증서가 없고 사용자가 ad-hoc 을 골랐다. 첫 설치에서 Gatekeeper 확인이 필요하다(한계).
  • Android·iOS·Web 의 앱 안 업데이트. 각각 Play·App Store·호스팅이 배포하고 앱이 자기 설치본을 바꿀 수 없다(플랫폼 스펙).
  • Intel Mac DMG. CI 러너가 arm64 라 DMG 는 arm64 JDK 를 담는다(jvm release 빌드).
  • 받는 중 진행률, 건너뛸 버전 고르기, 자동 설치. 버튼을 누를 때만 설치한다.

공급

결정: 확인은 GitHub REST API 를 1시간 간격으로 폴링한다 GitHub 는 새 Release 를 클라이언트에 밀어 주는 수단이 없다 — webhook 은 서버가 받는 것이고 앱은 공개 주소가 없다. 저장소가 public 이라 토큰 없이 GET /repos/taetae98coding/Jarvis/releases/latest 를 부른다. 토큰 없는 요청은 IP 하나에 시간당 60회라 회사처럼 여러 사람이 한 IP 로 나가면 모자랄 수 있어서, 앞 응답의 ETag 로 If-None-Match 를 보낸다. 304 는 한도에 세지 않는다. 버린 후보: releases.atom 피드(한도는 없지만 자산 주소가 없어 결국 API 를 한 번 더 불러야 한다), /releases/latest/download/<이름> 로 바로 받기(버전을 먼저 알 수 없다).
결정: 앱이 끝난 뒤 셸 스크립트가 번들을 바꾼다 돌고 있는 앱이 자기 번들을 바꾸면 JVM 이 열어 둔 jar·네이티브 라이브러리가 사라져 죽을 수 있다(실행 중 다시 빌드와 같은 문제). 그래서 앱은 새 번들을 설치된 앱 옆(.Jarvis-update.app)에 풀어 두기까지만 하고, 자기 pid 가 끝나기를 기다렸다가 두 번의 mv 로 바꾸고 open 으로 다시 띄우는 /bin/sh 스크립트를 띄운 뒤 정상 종료한다. 무거운 복사는 앱이 살아 있을 때 끝나므로 앱이 없는 시간은 mv 두 번이다. 정상 종료는 창을 닫을 때와 같은 경로(exitApplication)를 탄다 — exitProcess 로 끝내면 JCEF 를 닫지 않아 Chromium 도우미가 남는다. 버린 후보: Sparkle(네이티브 프레임워크라 JNA 브리지와 EdDSA 키 관리가 필요하다), Hydraulic Conveyor(업데이트까지 해 주지만 jpackage 빌드를 통째로 바꿔야 한다), DMG 를 Finder 로 열어 사용자가 끌어 놓게 하기(사용자가 "설치까지"를 원했다).
결정: 앱 종료 요청은 data 가 내놓는 Flow<Unit> 로 창에 전한다 exitApplication 은 desktopApp 의 application { } 안에서만 부를 수 있고 data 는 창을 모른다. JVM data 가 appQuitRequests: Flow<Unit> 을 내놓고(:shared 가 jarvisQuitRequests 로 감싼다) main.kt 가 LaunchedEffect 에서 첫 값을 기다려 exitApplication() 을 부른다. 창 수명 동안 한 번 오는 사건이라 상태가 아니고, 뒤늦게 구독해도 놓치지 않게 마지막 하나를 남긴다.

배포 워크플로

파일
.github/workflows/release.yml
시작
push 가 main 에 들어올 때, 그리고 손으로(workflow_dispatch). 한 번에 하나만 돈다(concurrency: release)
러너
macos-15(arm64). jpackage 는 돌린 OS 의 설치본만 만든다
순서
  1. gradle/libs.versions.toml 에서 appVersion 을 읽는다.
  2. git ls-remote --tags origin v<버전> 이 비어 있지 않으면 끝낸다(R2).
  3. JDK 21 과 Gradle 을 준비하고 ./gradlew :desktopApp:packageReleaseDmg. 번들 JDK 는 foojay 가 받는 toolchain 21 이다.
  4. shasum -a 256 Jarvis-<버전>.dmg > Jarvis-<버전>.dmg.sha256(R3).
  5. gh release create v<버전> --target <커밋> --generate-notes 로 태그·Release 를 만들고 두 파일을 올린다.
권한
contents: write. 저장소 기본 GITHUB_TOKEN 만 쓴다

한계

  • ad-hoc 서명이라 브라우저로 받은 첫 DMG 는 다른 Mac 에서 Gatekeeper 가 막는다. "시스템 설정 → 개인정보 보호 및 보안 → 그래도 열기" 또는 xattr -dr com.apple.quarantine /Applications/Jarvis.app 이 한 번 필요하다. 앱이 직접 받은 DMG 에는 quarantine 속성이 붙지 않아 업데이트는 막히지 않는다(jvm.html).
  • ad-hoc 서명은 빌드마다 코드 해시가 달라 macOS 가 업데이트된 앱을 다른 앱으로 볼 수 있다. 폴더 접근·자동화 같은 개인정보 보호 권한을 업데이트 뒤 다시 물을 수 있다.
  • appVersion 을 올리지 않은 머지는 배포되지 않는다(R2). 배포하려면 버전을 올려 머지한다.
  • 앱이 쓰기 권한이 없는 곳(관리자가 아닌 계정의 /Applications, 마운트한 DMG, App Translocation 경로)에서 돌면 풀기 단계에서 실패하고 R9 의 메시지가 나온다.
  • 업데이트가 앱을 정상 종료하므로 열린 터미널 세션은 창을 닫을 때처럼 끝난다. 작업 공간 배치는 남는다.
