화면 상태 소유 (ViewModel)

화면 하나가 쓰는 상태와 유스케이스 호출을 androidx.lifecycle.ViewModel이 소유한다. 앱 전체 상태 하나였던 JarvisAppState가 기능별·화면별 ViewModel 일곱으로 갈라진다.

사용자 지시

Koin 적용해서 DI 사용하도록 해줘. 그리고 Compose에서 제공하는 Retain 개념과 ViewModel 개념 Navigation3 개념 적용해서 Koin이랑도 연동까지 구현해줘.

2026-09-22 대화. 같은 지시에서 의존성 주입, 화면 이동, 재생성을 넘기는 상태 스펙이 함께 나왔다.

요구사항

  1. R1. 화면 상태와 유스케이스 호출은 ViewModel이 소유한다. @Composable 함수는 StateFlow를 모으고 콜백을 부르는 일만 한다.
  2. R2. ViewModel 은 유스케이스만 생성자로 받는다. 리포지토리·저장소·플랫폼 API·Compose 타입을 받지 않는다.
  3. R3. ViewModel 은 Koin 의 viewModel 정의로 등록하고 화면은 koinViewModel()로만 받는다.
  4. R4. 화면 수명 ViewModel(EmulatorDevicesViewModel, EmulatorScreenViewModel)은 그 화면이 백스택에서 빠질 때 onCleared()되고, 들고 있던 코루틴이 취소된다. 기기 화면 촬영은 그 시점에 멈춘다.
  5. R5. 앱 수명 ViewModel(ScreenAwakeEffectViewModel)은 화면을 옮겨 다녀도 살아 있다. 화면 꺼짐 방지 효과는 이 ViewModel 의 스코프에서 적용된다.
  6. R6. 상태를 만드는 코루틴 스코프는 viewModelScope다. 앱 수명 CoroutineScope를 ViewModel 에 넘기지 않는다.
  7. R7. 네 타깃 모두 같은 ViewModel 코드를 쓴다. ViewModelStoreOwner를 화면 코드가 직접 만들지 않는다.
  8. R9. ViewModel 은 그 기능의 ui 모듈 안에서 internal 이다. 기능이 내놓는 것은 인자 없는 카드·화면 컴포저블과 Koin 모듈뿐이다.
  9. R8. 사용자에게 보이는 동작은 바뀌지 않는다. 특히 에뮬레이터 개수는 구독자가 없어도 흐르고(Eagerly), 기기 목록과 실행 잠금은 화면이 열려 있는 동안에만 흐른다(WhileSubscribed).
스코프에서 뺀 것
  • SavedStateHandle. 프로세스가 죽은 뒤 복원해야 하는 값은 지금 백스택뿐이고, 그것은 Navigation3 의 백스택이 저장한다. ViewModel 안에는 복원할 사용자 입력이 없다.
  • UI 이벤트 채널(Channel + collectAsEffect). 스낵바·토스트·다이얼로그가 없어서 한 방향 상태 흐름으로 충분하다.
  • 화면별 UiState data class. 카드마다 독립된 StateFlow를 쓰는 지금 형태가 불필요한 재구성을 덜 만든다. 카드가 서로의 값에 의존하게 되면 그때 합친다.

화면·동작

화면에 보이는 변화는 없다. 옮긴 것은 상태의 소유자와 수명이다.

항목값
제목해당 없음
설명해당 없음
컨트롤해당 없음
테스트 태그해당 없음

결정: 앱 수명 상태도 ViewModel 에 둔다 화면 꺼짐 방지 효과는 카드보다, 그리고 어느 화면보다 오래 살아야 한다(화면 꺼짐 방지). 예전에는 루트의 LaunchedEffect가 그 수명을 만들었다. 지금은 ScreenAwakeEffectViewModel의 viewModelScope가 만들고, 앱 셸은 Modifier.appScreenAwake() 한 줄만 붙인다. 얻는 것: 컴포지션이 다시 만들어져도(Android Activity 재생성) 효과가 끊기고 다시 걸리는 일이 없다. 잃는 것: 효과가 언제 취소되는지가 LaunchedEffect만큼 코드에 드러나지 않는다 — 그래서 init 위에 그 사실을 주석으로 남긴다.
결정: 화면 상태를 WhileSubscribed로 유지한다 ViewModel 수명이 화면 수명이라 SharingStarted.Eagerly로 바꿔도 결과가 비슷해 보인다. 그대로 뒀다. 기기 목록은 실행 중인 기기 수만큼 adb 명령을 더 도는 조회고(기기 목록), 화면이 전환 애니메이션 동안 살아 있는 사이에도 폴링이 돌 이유가 없다. 반대로 에뮬레이터 개수는 Eagerly여야 카드가 "확인 중…"에서 숫자로 한 번만 바뀐다.
결정: 기기 화면 ViewModel 은 deviceId만 받는다 예전 라우트는 EmulatorDevice를 통째로 들고 다녔다. 지금은 deviceId만 받아 observeDevices()에서 찾는다. 이유는 두 가지다. 라우트 키는 저장·복원되므로 직렬화 가능한 최소 식별자여야 하고(백스택 저장), 기기의 상태(isAsleep, canControl)는 화면이 열려 있는 동안에도 바뀌므로 복사해 온 값보다 목록이 사실이다. 대가로 목록이 첫 답을 하기 전 한 프레임 동안 기기 이름이 비어 있을 수 있다 — 그 사이에는 제목 없이 "화면을 가져오는 중…"만 보인다.

ViewModelStoreOwner

Owner 는 우리가 만들지 않는다. 앱 수명 owner 는 플랫폼이 주고(플랫폼별 판정), 화면 수명 owner 는 Navigation3 의 rememberViewModelStoreNavEntryDecorator()가 엔트리마다 만든다. 그 데코레이터가 백스택에서 빠지는 엔트리의 ViewModelStore를 비우는 것이 R4 의 구현이다.

한계

  • ViewModel 의 상태 테스트는 :feature:emulator:ui의 jvmTest에만 있다. viewModelScope가 Dispatchers.Main.immediate를 쓰고, 테스트에서 그것을 갈아끼우는 Dispatchers.setMain이 Wasm 에서는 쓸 수 없다. 나머지 타깃은 화면 테스트로만 확인된다.
  • onCleared()가 언제 불리는지는 플랫폼이 정한다. JVM 데스크톱에서 창을 강제로 죽이면 ApplyKeepScreenAwakeUseCase의 정리(caffeinate 종료)가 돌지 못한다. 이 성질은 예전 LaunchedEffect 시절과 같다.
  • EmulatorScreenViewModel이 deviceId로 기기를 못 찾으면(목록에서 사라진 기기) 화면은 제목 없이 "화면을 가져오는 중…"에 머문다. 목록으로 자동으로 돌아가지는 않는다.
  • onCleared()가 실제로 불리는지 보는 테스트가 없다. 화면을 나갔다 다시 들어와 첫 프레임부터 시작하는지를 화면 테스트로 확인하려 했지만, 가짜 저장소가 프레임을 즉시 흘려보내 "화면을 가져오는 중…"이 한 프레임도 남지 않아 판정할 수 없었다. 지금은 데코레이터(rememberViewModelStoreNavEntryDecorator)의 계약에 기대고 있다.
