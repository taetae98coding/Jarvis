재생성을 넘기는 상태 (retain)

기기 화면에 마지막으로 그린 프레임을 retain으로 들고 있는다. 컴포지션이 다시 만들어져도 빈 화면으로 되돌아가지 않고, 화면을 떠나면 프레임도 함께 버려진다.

사용자 지시

Koin 적용해서 DI 사용하도록 해줘. 그리고 Compose에서 제공하는 Retain 개념과 ViewModel 개념 Navigation3 개념 적용해서 Koin이랑도 연동까지 구현해줘.

2026-09-22 대화. 같은 지시에서 의존성 주입, ViewModel, 화면 이동 스펙이 함께 나왔다.

요구사항

  1. R1. 기기 화면의 마지막 프레임과 "가져오지 못했다" 표시는 retain이 들고 있는다. 컴포지션이 다시 만들어지는 동안에도 값이 유지된다.
  2. R2. 프레임을 rememberSaveable로 저장하지 않는다. 디코딩된 이미지는 직렬화하지 않는다.
  3. R3. 프레임은 ViewModel에 두지 않는다. ImageBitmap은 화면 계층의 타입이다.
  4. R4. 기기 화면 엔트리가 백스택에서 빠지면 프레임도 버려진다. 다시 들어가면 "화면을 가져오는 중…"부터 시작한다.
  5. R5. deviceId가 바뀌면 이전 기기의 프레임을 보여주지 않는다.
  6. R6. 보관해 주는 저장소가 없는 플랫폼에서도 코드는 같고 예외 없이 동작한다. 그때 retain은 remember와 같게 움직인다.
스코프에서 뺀 것
  • RetainedEffect. 재생성을 넘겨 살아 있어야 하는 코루틴이 없다. 앱 수명 효과는 ViewModel이, 화면 수명 수집은 LaunchedEffect가 맡는다.
  • 직접 만든 RetainedValuesStore 제공. retainManagedRetainedValuesStore()로 루트에 저장소를 깔면 skiko 타깃에서도 "컴포지션을 벗어난 값 보관"을 흉내낼 수 있다. 재생성 경로가 없는 플랫폼에서 보관할 이유가 없고, 화면을 떠난 프레임이 메모리에 남는 쪽이 오히려 R4 를 어긴다.
  • 프레임 캐시(기기별로 마지막 프레임을 모아 두기). 목록에 미리보기를 붙이는 기능이 생기면 그때 별도 스펙으로 다룬다.

수명

Compose 는 값의 수명을 셋으로 구분한다. 이 앱은 셋을 각각 쓴다.

API사는 동안이 앱에서 쓰는 곳
remember컴포지션에 붙어 있는 동안스크롤 상태, 디코딩 결과를 담을 로컬 값
retain컴포지션을 벗어나도, RetainedValuesStore가 보관하는 동안기기 화면의 마지막 프레임
rememberSaveable직렬화되어 프로세스가 죽어도백스택(rememberNavBackStack 내부)
ViewModel그 화면이 백스택에 있는 동안화면 상태와 유스케이스 호출
결정: 프레임은 retain이고 ViewModel 이 아니다 EmulatorScreenViewModel도 같은 수명을 갖는다(엔트리가 빠지면 정리된다). 그런데도 프레임을 ViewModel 에 올리지 않았다. ImageBitmap은 플랫폼 그래픽 객체를 감싼 Compose 타입이고, 그것을 ViewModel 에 두면 화면 계층의 자원이 상태 계층으로 올라간다. ViewModel 은 ByteArray를 흘려보내는 데까지만 알고, 디코딩과 그 결과의 수명은 화면이 갖는다. 덧붙여 retain은 "이 값은 컴포지션보다 오래 살아야 한다"는 의도를 그 자리에 한 단어로 적어 준다.
결정: rememberSaveable은 쓰지 않는다 프레임은 기기 해상도 PNG 한 장이다. Android 의 저장 상태는 Bundle을 거쳐 시스템 프로세스로 가고, 메가바이트 단위 값을 넣으면 TransactionTooLargeException으로 앱이 죽는다. 게다가 저장할 값은 이미 낡은 프레임이다 — 프로세스가 다시 뜨면 0.5초 안에 새 프레임이 온다.

누가 보관하나

retain은 스스로 값을 붙들지 않는다. 컴포지션을 벗어날 때 LocalRetainedValuesStore에 물어보고, 저장소가 보관하겠다고 하면 남고 아니면 버려진다. 기본값은 아무것도 보관하지 않는 ForgetfulRetainedValuesStore다. 그래서 저장소를 제공하는 플랫폼에서만 값이 실제로 재생성을 넘고, 나머지에서는 remember와 같다(R6).

한계

  • 실제로 값을 보관하는 플랫폼이 Android 하나고, 그 Android 마저 configChanges 선언 때문에 재생성 경로가 드물다. 지금 retain이 주는 가장 큰 값은 동작보다 표시다 — 이 값의 수명이 컴포지션보다 길다는 사실이 코드에 적혀 있다.
  • retain은 직렬화하지 않으므로 프로세스가 죽으면 프레임도 사라진다. 그것이 rememberSaveable과의 차이고, 여기서는 의도다.
  • retain은 실험 단계 API 가 아니지만 아티팩트가 runtime과 분리돼 있어 버전을 따로 올려야 한다. Compose Multiplatform 을 올릴 때 runtime-retain 버전도 같은 줄로 맞춰야 하고, 어긋나면 runtime 내부 API 불일치로 링크가 깨진다.
