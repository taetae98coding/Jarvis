의존성 주입

리포지토리 구현·유스케이스·ViewModel·화면 라우트를 Koin 모듈로 선언하고, 쓰는 쪽은 생성자 주입과 koinViewModel()로만 받는다. 손으로 조립하던 JarvisContainer와 DataModule은 사라진다.

사용자 지시

Koin 적용해서 DI 사용하도록 해줘. 그리고 Compose에서 제공하는 Retain 개념과 ViewModel 개념 Navigation3 개념 적용해서 Koin이랑도 연동까지 구현해줘.

2026-09-22 대화. 같은 지시에서 ViewModel, 화면 이동, 재생성을 넘기는 상태 스펙이 함께 나왔다.

요구사항

  1. R1. 리포지토리 구현, 유스케이스, ViewModel, 화면 라우트는 Koin 모듈에 선언한다. 어느 클래스도 자기 의존을 직접 new 하지 않는다.
  2. R2. Koin 모듈은 Gradle 모듈마다 자기 것을 선언한다. 기능 하나가 <기능>DomainModule·<기능>DataModule·<기능>UiModule 셋을 내놓고, :shared는 그 목록을 합치고 플랫폼 핸들만 더한다.
  3. R3. Koin 은 프로세스마다 한 번 시작한다. 네 플랫폼 진입점이 startJarvisKoin()을 부르고, 두 번 불려도 첫 번째만 유효하다.
  4. R4. 리포지토리는 앱 전체에 하나(single), 유스케이스는 부를 때마다 새로(factory), ViewModel 은 viewModel 정의로 등록한다.
  5. R5. 플랫폼 핸들(PlatformContext)은 :shared가 등록하고 :data는 get()으로만 받는다. :data는 Context를 전역으로 들고 있지 않는다. 앱 수명 CoroutineScope 는 등록하지 않는다 — :data 가 스스로 구독을 붙잡고 있지 않아야 해서다(상태 조회 규칙 R12).
  6. R6. 네 타깃이 같은 모듈 선언을 쓴다. 플랫폼 분기는 data 모듈의 expect/actual 안에만 남고, Koin 모듈에는 없다.
  7. R7. 테스트는 가짜 리포지토리를 담은 Koin 모듈을 끼워 화면 전체를 띄운다. 유스케이스와 ViewModel 은 진짜 모듈이 만들고, 테스트마다 Koin 을 새로 세운다.
  8. R8. 사용자에게 보이는 동작은 바뀌지 않는다. 주입 전 테스트가 검증하던 내용은 주입 후에도 전부 검증된다.
스코프에서 뺀 것
  • koin-annotations (KSP). 정의가 서른 개 남짓이라 DSL 로 다 읽힌다. KSP 를 붙이면 네 타깃마다 프로세서 설정이 붙고, 생성 코드가 없으면 IDE 에서 정의를 따라갈 수 없다.
  • koin-android(androidContext(), AndroidViewModel). Android 전용 API 라 공용 모듈 선언이 갈라진다. PlatformContext가 이미 같은 일을 한다.
  • Koin scope API(scope<T> { }). 화면 수명 객체는 Koin scope 가 아니라 ViewModel과 NavEntry가 맡는다. 수명 개념을 두 군데 두지 않는다.
  • 모듈 지연 로딩(lazyModules). 시작 비용이 문제가 된 적이 없다.

화면·동작

화면에 보이는 변화는 없다. 주입이 실패하면 화면이 뜨지 않고 NoDefinitionFoundException으로 죽는다. 그래서 검증은 화면이 아니라 "모든 정의가 해석되는가"와 "기존 화면 테스트가 주입으로도 같은 것을 검증하는가"로 한다.

공통 구현

모듈

Koin 모듈 파일은 Gradle 모듈마다 하나다. 기능을 더할 때 고치는 파일이 그 기능의 계층과 같은 자리에 있고, 기존 기능의 파일은 열지 않는다.

Koin 모듈파일등록하는 것
<기능>DomainModulefeature/<기능>/domain/.../<기능>DomainModule.kt그 기능의 유스케이스. factoryOf(::GetAppInfoUseCase) 식으로 생성자만 가리킨다
<기능>DataModulefeature/<기능>/data/.../<기능>DataModule.kt리포지토리 구현을 도메인 인터페이스 타입으로 single. expect 팩토리(createSettingsStore 등)를 여기서 부른다
<기능>UiModulefeature/<기능>/ui/.../<기능>UiModule.kt그 기능의 ViewModel, 화면 라우트, 라우트 키 직렬화 등록(Koin ↔ Navigation3)

// :shared — 조립은 이 목록 하나로 끝난다. 기능을 더하면 세 줄이 늘어난다.
internal fun jarvisModules(context: PlatformContext): List<Module> =
    listOf(
        platformModule(context),
        appInfoDomainModule, appInfoDataModule, appInfoUiModule,
        emulatorDomainModule, emulatorDataModule, emulatorUiModule,
        screenDomainModule, screenDataModule, screenUiModule,
        rotationDomainModule, rotationDataModule, rotationUiModule,
        appUiModule,
    )

무엇정의왜
리포지토리 6개 (기능 넷에 흩어져 있다)single상태를 들고 있지 않고 cold Flow 만 내놓는다(상태 조회 규칙 R11). 플랫폼 데이터 소스를 감싸는 얇은 객체라 여러 벌 만들 이유가 없다
유스케이스 20개factory상태가 없다. 리포지토리 참조만 들고 있어서 만드는 비용이 필드 대입 한 번이다
ViewModel 7개viewModel수명은 Koin 이 아니라 ViewModelStore가 정한다. ViewModel 참고

라우트 키 직렬화 등록single(named<T>()):core:ui의 navKeySerializers DSL. 앱 셸이 getAll 로 모아 백스택 저장 설정을 만든다(근거)
PlatformContextsingle진입점이 만든 인스턴스를 그대로 넣는다(single { context })

시작 지점

Compose 트리 밖에서 시작한다. Android 의 Context만 진입점에서 명시적으로 넘긴다.

플랫폼어디서호출
AndroidJarvisApplication.onCreatestartJarvisKoin(this)
iOSMainViewController() 진입 시startJarvisKoin()
JVMmain()startJarvisKoin()
Webmain()startJarvisKoin()

startJarvisKoin()은 두 번 불려도 안전하다. iOS 는 MainViewController()가 여러 번 만들어질 수 있다. 이미 시작돼 있으면 그 인스턴스를 그대로 돌려준다. Android 는 2026-09-24 부터 Application.onCreate에서 부르므로 프로세스마다 한 번이다. 홈 화면 위젯이 Activity 없이 프로세스를 띄우면서 MainActivity.onCreate에서 옮겼다.

fun startJarvisKoin(): Koin =
    // 이미 시작된 Koin 에 startKoin 을 다시 부르면 KoinAppAlreadyStartedException 이다.
    KoinPlatformTools.defaultContext().getOrNull()
        ?: startKoin { modules(jarvisModules(PlatformContext())) }.koin
결정: 컴포지션 안이 아니라 진입점에서 startKoin 한다 KoinApplication { } 컴포저블로 컴포지션 안에서 시작하면 Android Context를 LocalContext로 얻을 수 있어서 진입점을 고치지 않아도 된다. 버렸다. 컴포지션이 다시 만들어질 때 Koin 인스턴스도 다시 만들어지고, 그러면 ViewModel은 살아남은 채 이미 취소된 앱 스코프를 쥔 리포지토리를 계속 들고 있게 된다. 설정 토글이 회전 뒤에 조용히 멈추는 종류의 버그다.
결정: rememberPlatformContext()를 없앤다 Compose 트리에서 Context를 꺼내던 계층 규칙의 예외 하나가 사라진다. 이제 진입점(JarvisApplication)이 컨텍스트를 startJarvisKoin(context)에 넘기므로, 플랫폼 핸들이 Compose 를 거치지 않는다. :shared의 androidMain에는 Context를 PlatformContext로 감싸는 한 줄만 남는다. PlatformContext 자체는 :core:data에 있다. 예전에 버렸던 "androidx.startup으로 전역 컨텍스트 보관" 과는 다르다. 초기화 순서를 숨기는 것이 없고, 컨텍스트를 넘기는 코드가 진입점에 그대로 보인다. Application 서브클래스는 위젯 때문에 들였지만, 그것이 하는 일은 startJarvisKoin(this) 한 줄이다.
결정: 유스케이스는 factory, 리포지토리는 single 반대로 두면(유스케이스 single) 정의가 서른 개 넘는 객체를 앱이 뜰 때 다 만들게 되고, 상태 없는 객체를 공유해서 얻는 것이 없다. 리포지토리를 factory로 두면 에뮬레이터 폴링이 구독자 수만큼 돌고 설정 변경 구독이 서로 보이지 않는다.

받는 쪽

어디어떻게 받나
리포지토리 구현, 유스케이스, ViewModel생성자 파라미터. Koin API 를 import 하지 않는다. 기능의 유스케이스는 Koin 없이도 new 할 수 있고 테스트가 그렇게 한다
화면(@Composable)koinViewModel(). 그 외 타입을 화면에서 직접 꺼내지 않는다 — 화면이 유스케이스를 koinInject() 하기 시작하면 상태 소유가 흐려진다
Koin 라우트 정의 본문Scope 리시버. get()으로 내비게이터를 받고 koinViewModel()로 ViewModel 을 받는다

테스트 주입

화면 테스트는 가짜 리포지토리를 담은 모듈을 만들어 프로덕션과 같은 전역 Koin 을 세운다. 기능들의 domain·ui Koin 모듈은 진짜 그대로 쓰고 data 모듈만 바꿔 끼운다. 유스케이스와 ViewModel 을 손으로 조립하던 rememberTestJarvisAppState()가 사라지고, 대신 조립 자체가 테스트 대상이 된다.

@Composable
internal fun TestJarvisApp(emulator: EmulatorRepository = FakeEmulatorRepository(), …) {
    remember(scope) {
        // 이전 테스트가 남긴 것이 있으면 먼저 치운다.
        if (KoinPlatformTools.defaultContext().getOrNull() != null) stopKoin()

        startKoin { modules(fakes, /* 기능들의 domain·ui 모듈, appUiModule */) }
    }

    JarvisApp()
}
결정: 테스트도 전역 Koin 을 쓴다 처음에는 KoinApplication { } 컴포저블로 테스트마다 격리된 Koin 을 만들려 했다. 동작하지 않는다. 그 함수가 쓰는 rememberKoinApplication 은 전역 Koin 이 이미 있으면 새 인스턴스를 만들지 않고 전역 것을 그대로 쓴다. 테스트가 컴포지션을 정리하지 않고 끝나면 먼저 실행된 테스트의 가짜 저장소가 그대로 남아, 다음 테스트가 자기 가짜에 클릭 결과를 기대하며 실패한다. 증상이 "토글이 눌리지 않는다" 라서 원인을 찾기까지 시간이 걸렸다. 대신 테스트마다 전역 Koin 을 세우고 이전 것을 stopKoin() 으로 치운다.

한계

  • Koin 은 런타임에 해석한다. 정의를 빼먹어도 컴파일은 통과하고 앱이 뜰 때 죽는다. :shared의 해석 테스트가 그 간격을 메우지만, 그 테스트는 JVM 에서만 돈다. 네 타깃이 같은 모듈을 쓰므로 한 타깃에서 해석되면 나머지도 해석된다는 전제에 기대고 있다.
  • ViewModel 정의는 해석 테스트로 확인하지 않는다. ViewModelStoreOwner 없이 꺼낼 수 없어서다. 대신 :app:ui의 화면 테스트가 실제로 koinViewModel()을 거친다.
  • viewModelScope 가 Dispatchers.Main.immediate 다. JVM 에서 이 디스패처는 kotlinx-coroutines-swing이 클래스패스에 있어야 존재한다. Compose Desktop 은 그것을 데려오지 않아서 :shared의 jvmMain이 직접 선언한다. 처음에는 Compose Desktop 이 준다고 보고 넣지 않았는데, 그때 있던 앱 수명 스코프(Dispatchers.Main)를 만드는 순간 Dispatchers.Main[missing]으로 뜨지 않았다.
  • 테스트가 전역 Koin 을 쓴다. 같은 타깃의 테스트가 동시에 돌면 서로의 Koin 을 치우게 된다. 지금은 네 타깃 모두 테스트를 순차로 돌리므로 성립하지만, 병렬 실행을 켜면 깨진다.
  • 모듈 경계를 넘는 선언은 public이 된다. 기능들의 Koin 모듈이 앱 코드에서도 보인다. 예전 DataModule과 같은 종류의 한계고, 규약으로만 막는다.
