Wi-Fi 기기 페어링

Android Studio 의 "Pair Devices Using Wi-Fi" 처럼, 케이블 없이 QR 코드나 6자리 페어링 코드로 실물 Android 기기를 개발자 머신의 adb 에 페어링하고 연결한다.

사용자 지시

Android Studio 보면 무선으로 디바이스 페어링 할 수 있도록 지원하잖아. 우리도 동일한 기능 만들어줘. iOS도 가능한지 검토해서 같이 구현해줘.
- 가능한 플랫폼만 조사해서 진행해줘.

2026-09-24 대화.

"iOS 도 가능한지" 는 페어링 대상 기기가 iPhone·iPad 인 경우로 읽었다(Xcode 의 무선 연결에 해당). 이 앱이 도는 네 타깃은 기존 기기 기능과 같이 모두 같은 화면을 갖는다. 기기 종류별 판정은 기기 종류별 조사, 앱 타깃별 판정은 플랫폼별 판정에 있다.

요구사항

  1. R1. 기기 목록 상단 막대에 JarvisIcons.Wifi 아이콘 버튼(contentDescription "Wi-Fi 로 페어링")이 있고, 누르면 페어링 화면으로 간다. 뒤로 가면 기기 목록으로 돌아온다.
  2. R2. 페어링 화면은 Android Studio 와 같이 "QR 코드" 와 "페어링 코드" 두 탭을 갖는다. 처음에는 "QR 코드" 탭이 열린다.
  3. R3. QR 코드 탭은 WIFI:T:ADB;S:<서비스 이름>;P:<비밀번호>;; 를 담은 QR 을 그린다. 서비스 이름은 jarvis- 뒤에 영숫자 10자, 비밀번호는 영숫자 12자이고, 화면에 들어올 때마다 새로 만든다. QR 은 테마와 무관하게 흰 바탕에 검은 칸이다.
  4. R4. 기기가 QR 을 스캔해 그 서비스 이름으로 페어링을 알리면(mDNS _adb-tls-pairing._tcp), 사용자가 더 누르지 않아도 그 주소로 비밀번호를 써서 페어링한다. 다른 이름의 페어링 서비스에는 반응하지 않는다.
  5. R5. QR 탭의 상태 문구는 "스캔을 기다리는 중…" → "<주소> 와 페어링하는 중…" → 결과(성공/실패) 순으로 바뀐다. 결과가 나오면 "새 QR 코드" 버튼으로 이름·비밀번호를 새로 만들어 다시 기다린다.
  6. R6. 페어링 코드 탭은 개발자 머신이 mDNS 로 찾은 페어링 대기 기기를 서비스 이름과 주소로 나열한다. 기기에서 "페어링 코드로 기기 페어링" 창을 열면 1초 안팎으로 나타나고, 닫으면 사라진다.
  7. R7. 줄마다 코드 입력칸과 "페어링" 버튼이 있다. 입력칸은 숫자만 받고 6자리를 넘기지 않는다. 6자리가 아니면 버튼이 잠긴다. 화면이 막는 것과 별개로 도메인도 6자리 숫자가 아닌 코드를 기기까지 보내지 않는다.
  8. R8. 페어링 요청이 끝날 때까지 그 줄의 버튼은 잠기고 "페어링하는 중…" 이 보인다. 같은 기기에 요청이 겹쳐 나가지 않는다.
  9. R9. 페어링에 성공하면 개발자 머신이 그 기기에 연결까지 한다. 연결된 기기는 다음 목록 갱신(최대 5초) 때 실물 기기로 나타나고, 그때부터 화면·제스처가 USB 기기와 똑같이 동작한다.
  10. R10. 실패하면 adb 가 준 이유 한 줄을 그대로 보여준다(예: Failed: Wrong password or connection was dropped.). 코드 탭은 같은 줄에서 다시 시도할 수 있다.
  11. R11. 개발자 머신이 페어링 대기 기기를 찾을 수 없으면(adb 가 없음, 데스크톱 앱이 꺼져 있음) 빈 목록이 아니라 "개발자 머신에서 페어링 대기 기기를 찾을 수 없습니다." 를 보여준다. 0개와 찾을 수 없음을 구분한다.
  12. R12. iPhone·iPad 는 공개 도구로 무선 첫 페어링을 시작할 수 없다(조사). 페어링 화면 아래에 "iPhone·iPad 는 처음 한 번 케이블로 연결해 '이 컴퓨터 신뢰' 를 눌러야 합니다. 그 뒤로는 같은 네트워크에서 케이블 없이 기기 목록에 나타납니다." 를 보여 주고, 그 밖의 동작은 하지 않는다.
스코프에서 뺀 것
  • 주소(IP:포트)를 손으로 입력해 페어링하는 것. Android Studio 의 이 화면에도 없다. mDNS 가 막힌 네트워크에서는 터미널에서 adb pair 를 직접 부른다.
  • iPhone·iPad 의 케이블 페어링(devicectl manage pair). 무선 페어링이 아니고, 케이블을 꽂으면 Finder·Xcode 가 이미 신뢰를 묻는다(조사).
  • 페어링 해제, 무선 연결 끊기(adb disconnect). 지시에 없고, 끊는 것은 USB 로 다시 꽂아야 되돌릴 수 있는 경우가 있다.
  • Android 10 이하의 adb tcpip 5555 방식. 한 번은 USB 가 필요해서 "무선 페어링" 이 아니다.
  • 에뮬레이터 페어링. 에뮬레이터는 처음부터 adb 에 붙어 있다.

기기 종류별 조사

페어링하는 주체는 언제나 개발자 머신(macOS)이다. 기기와 같은 네트워크에서 mDNS 를 보고, SDK 도구를 실행할 수 있는 곳이 그곳뿐이다.

Android — 구현

Android 11+ 의 무선 디버깅은 공개된 adb 명령만으로 끝까지 간다. 이 머신의 adb 37.0.1 에서 adb mdns check·adb mdns services·adb pair 가 모두 동작하고, 무선으로 붙은 실물 기기 두 대가 adb-<시리얼>-<임의>._adb-tls-connect._tcp 시리얼로 adb devices 에 나오는 것을 확인했다.

QR 코드                                   페어링 코드
───────                                   ──────────
앱이 이름·비밀번호를 만들어 QR 로 보여 줌   기기가 6자리 코드와 주소를 보여 줌
기기가 스캔 → <이름> 으로 mDNS 알림        기기가 adb-<시리얼>-<임의> 로 mDNS 알림
        └──────── adb mdns services 에 _adb-tls-pairing._tcp 로 나타남 ────────┘
                     adb pair <주소> <비밀번호 또는 코드>
                     → Successfully paired to <주소> [guid=adb-<시리얼>-<임의>]
                     adb 가 _adb-tls-connect._tcp 를 보고 스스로 연결 (안 되면 adb connect)

후보와 명령의 세부는 JVM 스펙에 있다.

iOS — 불가

iPhone·iPad 의 페어링은 CoreDevice 의 비공개 프로토콜(RemotePairing)이고, Apple 이 주는 공개 도구는 xcrun devicectl 뿐이다. 무선으로 처음 페어링하는 경로는 공개 도구에 없어서 구현하지 않고 안내 문구(R12)로 대신한다.

후보결과
iOS 26 이하 + Xcode 26 이하불가. 처음 한 번은 케이블로 연결해 기기에서 "이 컴퓨터 신뢰" 를 눌러야 한다(Apple 문서 "Pair devices using a cable"). 그 뒤로는 같은 네트워크에서 자동으로 무선 연결된다 — 개발 머신의 iPad 가 transportType: localNetwork, pairingState: paired 로 나오는 것을 확인했다. 이 머신의 iPhone·iPad 는 둘 다 iOS 26.6.1 이다
iOS 27 + Xcode 27 의 Device Hub "Pair Nearby Device…"버렸다. 케이블 없이 첫 페어링이 되지만, Mac 이 _remotepairing-pairable-host._tcp 로 자기를 알리고 Mac 에 뜬 PIN 을 iPhone 에 입력하는 방향이라 Mac 쪽을 Device Hub GUI 만 할 수 있다. devicectl 에는 그 알림을 띄우는 명령이 없다. 직접 알리려면 비공개 프로토콜을 다시 구현해야 한다(jkcoxson/idevice pair_host 가 역공학으로 한 일)
devicectl manage pair --device <UDID>버렸다. CoreDevice 가 이미 찾은 기기와 페어링한다. 페어링 안 된 iPhone 이 보이는 경로는 USB 뿐이라, 결국 케이블 페어링이고 무선 페어링이 아니다. 기기에서 신뢰를 누르게 하는 것은 Finder·Xcode 가 케이블을 꽂는 순간 이미 한다. 성공 시 종료 코드 0 과 Paired with device:, 실패 시 1 과 com.apple.dt.CoreDeviceError 다. 페어링 안 된 기기가 없어 실제로는 확인하지 못했다
devicectl list devices --include-wireless-pairable-devices버렸다. 문서에 없는 옵션이다. 받아들이고 0 으로 끝나지만 개발 머신에서 기기가 하나도 늘지 않았다
mDNS _remotepairing-manual-pairing._tcp버렸다. Apple TV·Vision Pro 가 PIN 페어링을 기다릴 때 알린다. iPhone·iPad 는 알리지 않고, 개발 머신에서도 아무것도 보이지 않았다. Apple TV·Vision Pro 는 이 앱의 기기 목록 대상이 아니다
pymobiledevice3 remote pair, libimobiledevice버렸다. 앞의 것은 RemotePairing 을 지원하는 기기(Apple TV 등)만 무선으로 되고, 뒤의 것은 USB(lockdown) 만 된다. 둘 다 역공학한 비공개 프로토콜이라 Xcode 가 바뀌면 깨진다

iOS 27 이상이 널리 쓰이고 devicectl 에 무선 페어링 명령이 생기면 다시 본다. 그때는 DevicePairingRepository 에 iOS 대기 기기를 더하는 것으로 충분하다.

UI
ui/emulator/WifiPairingScreen.kt(두 탭), ui/emulator/QrCode.kt(QR 인코더), ui/emulator/QrCodeImage.kt(그리기, QrCodeImageDefaults). 라우트 EmulatorRoute.Pairing
상태
WifiPairingViewModel — 선택된 탭, 현재 QR 과 그 QrPairingState(SharingStarted.Eagerly — 코드 탭을 보는 동안에도 QR 세션이 이어지고 결과가 남는다), 코드 탭의 대기 기기 목록(WhileSubscribed), 줄마다의 입력값·진행 여부와 마지막 결과(CodePairingState)

결정: 기존 emulator 기능 안에 두되 리포지토리는 따로 둔다 페어링은 기기 목록 화면에서 들어가고, 비 JVM 타깃은 에뮬레이터 에이전트를 거쳐야 한다. 에이전트 서버가 :feature:emulator:data 에 있으므로 새 기능 모듈로 떼면 모듈끼리 서로를 봐야 한다(기능은 서로를 의존하지 않는다). 대신 EmulatorRepository 에 메서드를 더하지 않고 DevicePairingRepository 를 따로 둔다. 기기 목록·화면·실행과 수명이 다르고(페어링 화면이 떠 있는 동안만 산다), 기존 가짜 저장소 네 벌을 고치지 않아도 된다.
결정: QR 비밀번호는 클라이언트가 만들고, 에이전트는 상태를 들지 않는다 QR 세션을 에이전트에 두면(POST /pairing/qr 로 시작, GET 으로 상태 조회) 에이전트가 세션 수명과 정리 시점을 가져야 한다. 대신 에이전트는 "지금 보이는 페어링 서비스" 와 "이 주소에 이 코드로 페어링" 두 가지만 하고, QR 이름·비밀번호와 기다리는 일은 도메인 유스케이스가 한다. QR 과 코드 두 흐름이 같은 pair 하나로 끝난다 — QR 의 비밀번호가 곧 페어링 코드다.
결정: QR 인코더를 직접 둔다 후보는 셋이었다.

결정: 서비스 이름과 비밀번호는 영숫자만 쓴다 WIFI: 형식은 ; , : \ " 를 역슬래시로 이스케이프해야 한다. 영숫자만 쓰면 이스케이프가 필요 없어서, 기기 쪽 파서가 이스케이프를 어떻게 다루는지에 기대지 않는다. 이름 접두사 jarvis- 는 mDNS 목록에서 누가 만든 세션인지 사람이 알아보기 위한 것이다(Android Studio 는 studio-). 비밀번호에는 : 이 들어가면 안 된다는 제약도 있다 — adb 서버가 host:pair:<비밀번호>:<주소> 를 첫 : 에서 자른다(services.cpp). 난수는 Uuid.random() 에서 뽑는다. commonMain 에서 네 타깃 모두 암호학적으로 안전한 난수에 닿는 표준 경로가 그것뿐이고, Random.Default 처럼 예측할 수 있으면 같은 네트워크의 다른 호스트가 먼저 기기와 짝을 맺을 수 있다. Android Studio 도 SecureRandom 을 쓴다.
결정: 페어링 뒤 adb connect 를 부르지 않고 연결을 기다리기만 한다 adb 서버는 페어링에 성공하면 곧바로 그 guid 로 연결을 시도하고(client/adb_wifi.cpp 의 adb_secure_connect_by_service_name), 그 뒤에도 알려진 기기의 _adb-tls-connect._tcp 를 보면 스스로 붙는다. Android Studio 도 adb connect 를 부르지 않고 기다린다. 우리가 adb connect <IP:포트> 를 더 부르면 같은 기기가 mDNS 이름과 IP:포트 두 시리얼로 붙어 목록에 두 번 나올 수 있다. 그래서 최대 10초 동안 adb devices 에 guid 로 시작하는 시리얼이 생기는지만 보고, 생기면 Paired(isConnected = true), 안 생기면 false 로 답한다. 늦게 붙어도 기기 목록이 알아서 보여 준다.

한계

  • 기기와 개발자 머신이 같은 네트워크에서 mDNS 가 통해야 한다. 회사망·게스트망처럼 멀티캐스트를 막는 네트워크에서는 대기 기기가 나타나지 않고, QR 은 "스캔을 기다리는 중…" 에 머문다. Android Studio 도 같은 조건이다.
  • JVM 외에는 데스크톱 앱이 같은 머신에 떠 있어야 한다. 없으면 "찾을 수 없습니다" 가 보인다.
  • QR 이름이 다른 도구와 겹치지 않는다는 보장은 확률뿐이다. 영숫자 10자라 사실상 겹치지 않는다.
  • 코드 탭은 모든 _adb-tls-pairing._tcp 를 보여 준다. 다른 머신의 Android Studio 가 띄운 QR 을 스캔 중인 기기(studio-…)도 잠깐 줄로 보일 수 있고, 거기에 코드를 넣으면 실패한다.
  • 페어링 결과는 adb 의 영어 문구를 그대로 보여 준다. 실패 이유를 번역하려면 adb 버전마다 문구를 따라가야 한다.
  • 로컬 에이전트는 인증이 없다. 같은 머신의 다른 프로세스나 브라우저 페이지도 페어링 요청을 보낼 수 있지만, 페어링하려면 기기 화면에 뜬 코드를 알아야 한다.
