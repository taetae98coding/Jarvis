사용자 지시

우리앱의 디자인 가이드를 정의해줘.

1. M3를 베이스로 사용하고 공통 JarvisTheme 만들어줘.
- dimen
- color
- typhography
- 기타 너가 필요한 것들.

2. 공통 JarvisTheme를 모든 컴포넌트가 존중하지만 경우에 따라 컴포넌트 별 Theme값을 가질 수 있어.
- Compose에 새롭게 소개된 style 기능 적극 사용.
- ***Defaults 패턴으로 소유해서 사용.

3. ImageVector를 만들어서 IconButton, Icon 등 적극 사용하도록 리팩토링해줘.

2026-09-24 대화.

요구사항

  1. R1. 앱의 루트는 MaterialTheme 대신 JarvisTheme 로 감싼다. JarvisTheme 은 안에서 MaterialTheme(colorScheme, typography, shapes) 를 부르므로, Material 3 컴포넌트(Switch, FilterChip, OutlinedButton …)는 인자를 따로 받지 않아도 Jarvis 값으로 그려진다.
  2. R2. JarvisTheme 은 여섯 가지 토큰을 공급한다: colorScheme(M3 색 역할), colors(M3 에 없는 역할: success·warning·terminal), typography(M3 글꼴 단계), codeTextStyle(고정폭), shapes(M3 모서리 단계), dimens(간격·아이콘 크기·선 굵기·레이아웃). 값은 토큰 표와 같다.
  3. R3. 색은 라이트·다크 두 벌이고, 기본값은 시스템 설정(isSystemInDarkTheme())을 따른다. 시스템 설정이 바뀌면 앱을 다시 켜지 않아도 따라간다. 사용자가 고른 모드를 넘기는 자리가 JarvisTheme(darkTheme = …) 이고, 그 값은 화면 테마가 정한다.
  4. R4. 기능 코드(feature/*/ui, app/ui, core/ui)는 dp·sp 숫자와 Color(…) 리터럴을 직접 쓰지 않고 JarvisTheme 토큰이나 컴포넌트의 *Defaults 를 거친다. 예외는 결정에 적은 세 가지뿐이다.
  5. R5. 기본값을 가진 컴포넌트는 모두 같은 이름의 <컴포넌트>Defaults object 를 가진다. 기본값은 JarvisTheme 토큰에서 오고, 호출하는 쪽은 인자로 Defaults 와 다른 값을 넘겨 그 컴포넌트만의 값을 가진다. 기능 하나에서만 쓰는 컴포넌트는 그 기능 모듈이 자기 Defaults 를 소유한다.
  6. R6. 컨테이너의 여백·배경·모양·테두리·크기와 상태(선택·hover·눌림)에 따른 변화는 Compose Foundation 1.12 의 Style API(Style { … }, Modifier.styleable)로 정의한다. 그런 컴포넌트는 style: Style = Style 인자를 받고, 넘긴 Style 은 Defaults 의 Style 위에 속성 단위로 덮어쓴다. 넘기지 않은 속성은 기본값이 남는다.
  7. R7. 아이콘은 JarvisIcons 가 가진 ImageVector 로 그린다. 글자로 흉내 낸 아이콘(← 뒤로, ×)과 글자뿐인 도구 버튼(좌우 분할 등)은 IconButton + Icon 으로 바꾼다. 아이콘만 있는 버튼은 원래 라벨을 contentDescription 으로 가진다.
  8. R8. 이 작업은 기능의 동작을 바꾸지 않는다. 테스트 태그, 설명 문구, 클릭·토글 결과는 그대로다. 바뀌는 것은 버튼 라벨이 글자에서 contentDescription 으로 옮겨 가는 것뿐이다.
스코프에서 뺀 것
  • Android 12+ 동적 색(배경화면에서 뽑는 색). 네 타깃의 모양을 같게 두려고 쓰지 않는다.
  • 글꼴 파일 번들. 플랫폼 기본 글꼴을 그대로 쓴다(결정).
  • 앱 안에서 라이트/다크를 고르는 설정 화면. 이 문서에서는 JarvisTheme(darkTheme = …) 인자로 받을 자리만 두었고, 2026-09-25 화면 테마가 그 자리를 채웠다.
  • 터미널 글자 영역의 색. 셸 프로그램은 어두운 배경을 가정하므로 라이트 테마에서도 터미널 창은 어둡다(터미널).

M3 가 가진 역할(색 역할, 글꼴 단계, 모서리 단계)은 M3 타입 그대로 두고, M3 에 없는 것(success·warning·terminal 색, 고정폭 글꼴, 치수)만 Jarvis 타입으로 더한다. JarvisTheme.colorScheme 은 M3 의 LocalColorScheme 이 internal 이라 Style 블록에서 읽을 수 없어서 같은 값을 우리 CompositionLocal 에도 한 번 더 넣는다.
결정: Style 은 컨테이너에, Defaults 는 글자·색 인자에 Style API 는 textStyle·contentColor 도 자식에게 물려준다고 되어 있지만, 그 값은 BasicText 가 받은 스타일에 비어 있는 속성만 채운다(StyleProperties.toTextStyle(supplied)). M3 Text 는 LocalTextStyle·LocalContentColor 로 색과 크기를 항상 채워서 넘기므로 Style 의 글자 속성이 이긴 적이 없다. 그래서
  • Style: 여백(contentPadding), 배경, 모양, 테두리, 최소 크기, 상태별 변화(selected·hovered·pressed)와 그 애니메이션(animate).
  • Defaults 의 값·함수: 글꼴(TextStyle), 글자·아이콘 색, CardColors 처럼 M3 컴포넌트가 인자로 받는 것.
Defaults 의 Style 은 val style: Style 로 둔다. Style 블록은 컴포지션 밖에서 실행되고 테마 값은 jarvisDimens 처럼 그때 읽으므로, 테마가 바뀌어도 같은 객체를 다시 쓸 수 있다. 컴포넌트는 Modifier.styleable(state, Defaults.style, style) 로 기본 Style 과 호출자의 Style 을 차례로 적용해 오른쪽이 속성 단위로 이긴다. 호출자가 style = Defaults.style then … 처럼 기본값을 다시 넘길 필요가 없다.
결정: 모듈 :core:designsystem 을 새로 둔다 :core:ui 에 넣으면 테마만 필요한 모듈도 Navigator·Koin 내비게이션 의존성을 함께 받는다. 디자인 시스템은 Compose 와 M3 만 알고 앱의 어떤 개념(라우트, ViewModel)도 모르게 둔다. 의존 방향은 :feature:*:ui·:core:ui·:app:ui → :core:designsystem 한 방향이다(모듈 구조).
결정: 아이콘은 ImageVector.Builder + SVG 경로 문자열로 직접 만든다 후보는 넷이었다.
  • 채택. ImageVector.Builder(…).addPath(addPathNodes("M12 5v14…"), stroke = …). 의존성이 없고 네 타깃에서 같은 경로를 그린다. 경로 문자열 하나가 아이콘 하나라 고치기 쉽다. by lazy 로 처음 쓸 때 한 번만 만든다.
  • material-icons-core/-extended. 지금 의존성에 없고, androidx 가 1.7.x 이후 새 버전을 내지 않으며 Material Symbols 로 옮기라고 안내한다. extended 는 수천 개 아이콘이라 Wasm 번들이 커진다. 버렸다.
  • Compose Resources 의 벡터 XML(Res.drawable.* + vectorResource). ImageVector 를 얻을 수는 있지만 리소스 로딩을 거치고(Web 은 비동기), 지시가 요구한 "ImageVector 를 만든다"와 거리가 있다. 버렸다.
  • Material Symbols 가변 글꼴. 글꼴 파일을 번들해야 하고 Icon 이 아니라 Text 로 그려져 IconButton·tint 규약을 벗어난다. 버렸다.
결정: 리터럴이 남는 세 곳
  • 토큰과 Defaults 의 정의 — 값이 처음 태어나는 자리다.
  • 터미널 ANSI 팔레트(TerminalPalette.kt) — 0–15 는 VS Code 테마, 16–255 는 xterm 정의값이다. 셸 프로그램이 이 값을 가정하므로 테마 토큰이 아니다.
  • 화면과 무관한 수 — 제스처 최소 시간, 화면 좌표 변환, 줄 번호 같은 것. dp·sp·Color 가 아니다.
결정: 글꼴 파일을 번들하지 않는다 Pretendard 같은 한글 글꼴을 넣으면 네 타깃의 글자 모양이 같아지지만, 한글 글꼴은 굵기 하나에 수 MB 라 Web 첫 로딩이 그만큼 늦어진다. 지금은 M3 기본 단계(크기·줄 간격)만 정하고 글꼴 모양은 플랫폼에 맡긴다. 넣을 때는 JarvisTypography.kt 의 FontFamily 한 곳만 바꾼다.
결정: Style API 의 실험 표시는 컨벤션 플러그인에서 한 번에 풀어 준다 Style API 는 @ExperimentalFoundationStyleApi 다. 파일마다 @OptIn 을 달면 Style 을 쓰는 모든 기능 파일이 같은 줄을 반복한다. jarvis.kmp.compose 가 languageSettings.optIn(…) 으로 Compose 모듈 전체에 켠다. API 가 바뀌면 컴파일이 깨져서 바로 드러나므로 숨겨지는 위험은 없다.

한계

  • Style API 는 실험 API 다. Compose 버전을 올릴 때 이름이나 시그니처가 바뀔 수 있고, 그러면 *Defaults.style 과 styleable 을 부르는 곳을 함께 고친다. 컴파일이 깨지므로 조용히 틀어지지는 않는다.
  • Style 의 글자 속성(textStyle, contentColor)은 M3 Text 에 닿지 않는다(결정). 글자는 Defaults 로만 바꾼다.
  • M3 컴포넌트(Switch, FilterChip, OutlinedButton)는 Style 인자가 없다. 이들은 MaterialTheme 을 거쳐 Jarvis 색·모양을 따르고, 개별 값은 M3 의 *Defaults(예: ButtonDefaults.ButtonWithIconContentPadding)로 바꾼다.
  • 글꼴 모양은 플랫폼마다 다르다(결정).
  • 시각적 결과(색이 맞는지, 애니메이션이 부드러운지)는 자동 테스트가 보지 않는다. 시맨틱 트리에 색이 없어서다.
