기기 화면 영상 스트림·호버

기기 화면을 스크린샷 폴링이 아니라 기기 안의 에이전트가 인코딩한 영상으로 받고, 누름·끌기·마우스 호버를 같은 에이전트의 소켓으로 그 자리에서 기기에 넣는다. Android Studio 의 Running Devices 와 같은 구조다.

사용자 지시

안드로이드 스튜디오에서 제공하는 running device 기능은 되게 빠릿빠릿하게 동작하는게 왜 우리껀 느려? 그리고 마우스 올렸을 때 hover효과도 있는데 왜 우리껀 없어?? 최대한 빠르게 동작하고 hover도 지원해줘.

2026-09-24 대화. "우리 것" 은 기기 목록·화면·제스처의 스트리밍 화면과 터미널의 기기 탭(같은 컴포저블)이다. "hover 효과" 는 Running Devices 에서 마우스를 기기 화면 위로 움직이면 기기 안의 버튼·목록이 마우스 호버 상태로 바뀌는 것(기기 쪽 효과)으로 읽었다. 데스크톱 앱 쪽의 시각 효과가 아니다.

왜 느렸나

2026-09-24 개발 머신에서 잰 값이다(macOS arm64, SM-F966N 무선 adb).

단계예전비용
프레임500ms 마다 adb exec-out screencap -p한 장에 0.34~0.65초. PNG 인코딩이 기기 CPU 에서 돌고 400KB 가 USB·Wi-Fi 를 탄다. 초당 1~2장
탭adb shell input tap기기가 input 프로세스(Java VM)를 매번 새로 띄운다. 눌러서 반응까지 0.2~0.4초
드래그손을 뗀 뒤 input swipe 한 번끄는 동안 기기에는 아무것도 가지 않는다. 뗀 뒤에 기기가 혼자 재생한다
호버없음input 명령에는 호버 이벤트가 없다

Android Studio 는 기기 안에 자기 에이전트(screen-sharing-agent)를 올려 MediaCodec 으로 H.264 영상을 만들고 adb forward 소켓으로 받으며, 입력은 같은 소켓으로 MotionEvent 를 직접 주입한다. 프레임 하나에 수십 KB, 입력은 왕복 수 ms 다. 마우스 호버도 ACTION_HOVER_MOVE 로 기기에 들어가서 기기 UI 가 반응한다.

요구사항

  1. R1. Android 기기(에뮬레이터·실물)의 화면은 기기 안의 에이전트가 인코딩한 영상 스트림으로 받는다. 화면이 바뀌는 동안 초당 30장 이상이 흐른다(기기 디스플레이 갱신률과 인코더가 허용하는 한).
  2. R2. 화면을 누른 순간 DOWN 이, 끄는 동안 MOVE 가, 뗀 순간 UP 이 기기에 들어간다. 뗀 뒤에 한 번에 보내지 않는다. 기기 화면에서 누름이 보이기까지 100ms 안이다(같은 머신의 에뮬레이터 기준).
  3. R3. 마우스가 누르지 않고 기기 화면 위를 움직이면 그 위치가 마우스 호버로 기기에 들어가서, 기기 안의 UI 가 호버 상태를 그린다. 터치(손가락)로는 호버가 가지 않는다.
  4. R4. 좌표는 지금 보고 있는 프레임의 픽셀 좌표로 보내고, 그 프레임의 크기를 함께 보낸다. 에이전트가 프레임 크기를 기기 디스플레이 크기로 바꾼다. 회전 직후처럼 프레임 크기가 달라진 순간의 입력은 버려지고 엉뚱한 곳을 누르지 않는다.
  5. R5. 같은 기기를 보는 곳이 여럿(기기 목록의 화면과 터미널 탭 두 개)이어도 기기 안의 에이전트와 스트림은 하나다. 마지막 구독자가 떠나면 잠시 뒤 에이전트를 끝낸다.
  6. R6. 에이전트를 올리지 못하거나 스트림이 끊기면(기기가 뽑혔거나 꺼졌으면) 마지막 프레임을 그대로 두고 주기적으로 다시 시도한다. 한 장도 못 받았으면 기기 화면 R11의 "화면을 가져올 수 없습니다." 다.
  7. R7. 영상을 풀고 화면에 올리는 동안 UI 스레드가 멈추지 않는다. 소켓 읽기·H.264 디코딩·픽셀 변환은 전부 UI 스레드 밖이다(기기 화면 R14).
  8. R8. 데스크톱 앱 밖의 도구를 사용자가 설치할 필요가 없다. 기기 에이전트와 디코더는 앱에 함께 들어간다.
  9. R9. 프레임은 화면이 보이는 동안에만 흐른다(기기 화면 R10, 기기 탭 R11). 구독이 끊기면 소켓과 에이전트도 닫는다.
  10. R10. 프레임이 새로 올 때마다 이전 프레임의 네이티브 픽셀 메모리를 곧바로 놓는다. 초당 60장이 GC 를 기다리며 쌓이지 않는다.
  11. R11. 로컬 에이전트(HTTP)를 거치는 타깃(Android·iOS·Web)도 같은 스트림에서 나온 최신 프레임을 받는다. 요청마다 기기를 새로 찍지 않으므로 응답이 수십 ms 안에 끝나고, 폴링 주기를 그만큼 줄인다.
  12. R12. iOS 시뮬레이터는 예전대로 simctl io screenshot 폴링이다. 바뀌지 않는다.
스코프에서 뺀 것
  • 키 입력(텍스트·하드웨어 키), 마우스 휠 스크롤, 오른쪽 클릭, 멀티터치·핀치. 에이전트 프로토콜에는 있지만 지시에 없다.
  • 오디오.
  • Android·iOS·Web 타깃에서 영상 스트림을 직접 받는 것. 각각 MediaCodec·VideoToolbox·WebCodecs 로 디코더를 붙여야 하고, 세 벌의 디코더는 이 지시의 범위를 넘는다. 이 타깃들은 호스트가 디코딩한 최신 프레임을 JPEG 로 받는다(R11).
  • 데스크톱 앱 UI 쪽의 호버 시각 효과. 지시의 "hover 효과" 는 기기 안에서 일어나는 것이다.
  • 호버가 화면을 벗어났다는 이벤트(ACTION_HOVER_EXIT). 한계.
  • 화면 크기에 맞춰 영상 해상도를 다시 협상하는 것. 시작할 때 정한 최대 크기 하나로 간다.

화면·동작

항목값
화면 문구기기 화면과 같다. "화면을 가져오는 중…", "화면을 가져올 수 없습니다.", 제스처 불가 문구, 화면 켜기 카드. 새 문구는 없다
첫 프레임에이전트 올리기(adb push) → 시작 → 첫 키프레임까지 0.5~1.5초. 그동안 "화면을 가져오는 중…"
누름포인터가 닿은 순간 Touch(DOWN), 움직이면 Touch(MOVE), 떼면 Touch(UP). 탭과 드래그를 구분하지 않는다 — 기기가 구분한다
호버PointerType.Mouse 이고 눌린 버튼이 없는 Move 마다 Hover(x, y). 터치·스타일러스는 보내지 않는다
순서한 기기의 제스처는 보낸 순서대로 기기에 닿는다. 보내는 중에 쌓인 MOVE·Hover 는 마지막 하나만 남기고 버린다. DOWN·UP·CANCEL 은 버리지 않는다
영상 크기긴 변 최대 2048px(MirrorMaxSize). 1080×2520 은 878×2048, 1848×2960 은 1278×2048 로 온다. 화면은 ContentScale.Fit 그대로다
테스트 태그바뀌지 않는다. emulator:frame 이 프레임이다

공통 구현

도메인
EmulatorFrame(sealed) — Encoded(bytes): PNG·JPEG 한 장. Pixels(width, height, pixels): 디코딩된 BGRA 8888, 행 간격 width × 4.
EmulatorGesture(sealed) — Touch(action, x, y, frameWidth, frameHeight), Hover(x, y, frameWidth, frameHeight). TouchAction { DOWN, MOVE, UP, CANCEL }. 예전의 Tap·Swipe 는 없다.
EmulatorRepository.observeScreen(deviceId): Flow<EmulatorFrame?>. sendGesture 는 그대로
데이터 (JVM)
feature/emulator/data/src/jvmMain/.../emulator/mirror/ — ScrcpyServer.kt(에이전트 올리기·시작·소켓), H264Decoder.kt(FFmpeg), ControlMessages.kt(입력 메시지 인코딩), ScreenMirror.kt(세션 = 프레임 Flow + 제어 채널).
src/jvmMain/resources/scrcpy/scrcpy-server-v4.1 — 기기 에이전트. 아래 결정
데이터 (공통)
EmulatorDataSource.observeScreen 의 타입만 바뀐다. 에이전트 클라이언트(HostAgent.kt)는 받은 바이트를 Encoded 로 감싼다. expect 선언은 늘지 않는다
UI
EmulatorStream 은 EmulatorFrame 을 ImageBitmap 으로 바꾼다. Encoded 는 예전대로 decodeToImageBitmap(), Pixels 는 internal expect fun EmulatorFrame.Pixels.toImageBitmap(): ImageBitmap. 둘 다 FrameDecodeContext 에서 한다(R7).
internal expect fun ImageBitmap.release() — 이전 프레임의 네이티브 메모리를 놓는다(R10). EmulatorFrameState 는 RetainObserver 가 되어 onRetired 에서 마지막 프레임도 놓는다.
DeviceScreen 의 포인터 처리는 awaitPointerEventScope 루프 하나다. Press·Move·Release 를 그대로 Touch 로, 안 눌린 마우스 Move 를 Hover 로 보낸다. 슬롭 판정·최소 지속 시간은 없어졌다 — 기기가 알아서 한다
상태
EmulatorScreenViewModel.onGesture 는 바로 보내지 않고 큐에 넣는다. 코루틴 하나가 순서대로 꺼내 보내고, 꺼낼 때 뒤에 같은 종류의 MOVE·Hover 가 쌓여 있으면 마지막만 보낸다. 제스처마다 launch 하면 HTTP 를 타는 타깃에서 UP 이 MOVE 를 앞질러 간다

프레임 픽셀 버퍼

Pixels.pixels 는 데이터 소스가 돌려 쓰는 버퍼다. 1080×2520 BGRA 한 장이 10MB 인데 초당 60장을 새로 할당하면 600MB/s 의 쓰레기가 생긴다. 데이터 소스는 FramePoolSize(4)장짜리 링을 돌리고, 같은 버퍼는 4 프레임 뒤에 다시 쓰인다. 받는 쪽은 받은 자리에서 곧바로 복사해야 한다(UI 는 Skia 비트맵으로, 에이전트는 JPEG 로). 복사를 미루면 다음 프레임이 덮어쓴다. 느린 구독자가 4장 이상 뒤처지면 한 장이 찢어져 보일 수 있고, 다음 프레임이 바로 고친다.

스트림 공유

JVM 의 observeScreen(adb 시리얼) 은 기기마다 conflate().shareIn(scope, WhileSubscribed(stopTimeoutMillis = MirrorSessionLinger, replayExpirationMillis = 0), replay = 1) 다(R5). 상태 조회 규칙이 허용하는 "비싼 조회를 나눌 때" 의 예외다.

  • conflate() — 느린 구독자가 프레임을 밀어 두지 않는다. 디코더가 UI 를 기다리지 않는다.
  • replay = 1 — 나중에 붙는 구독자(두 번째 탭, 에이전트의 HTTP 요청)가 다음 화면 변화를 기다리지 않고 지금 프레임을 받는다. 화면이 멈춰 있으면 에이전트는 새 프레임을 보내지 않으므로, 이게 없으면 first() 가 영원히 기다린다.
  • stopTimeoutMillis — 로컬 에이전트가 100ms 마다 first() 로 붙고 떠난다. 여유가 없으면 요청마다 기기 에이전트를 올리고 내린다(1초). 3초로 둔다.
  • replayExpirationMillis = 0 — 멈춘 뒤 다시 붙는 구독자가 오래된 프레임을 지금 화면처럼 받지 않는다.

좌표

포인터 위치는 그려진 영역 기준으로 기기 화면과 같이 프레임 픽셀로 바꾸고, 그 프레임의 width × height 를 함께 싣는다. 기기 에이전트는 자기가 지금 보내는 영상 크기와 다르면 이벤트를 버린다(R4). 영상은 디스플레이를 축소한 것이라 좌표 변환은 에이전트가 한다 — 우리는 디스플레이 해상도를 알 필요가 없다.

결정: 기기 에이전트는 scrcpy-server 를 번들한다

기기 안에서 화면을 인코딩하고 입력을 주입하는 코드는 Android 버전마다 숨은 API 가 바뀐다(SurfaceControl, DisplayControl, InputManager.injectInputEvent). 직접 쓰고 유지하는 일이 이 기능의 본체보다 크다.

  • 채택. scrcpy 의 서버(scrcpy-server-v4.1, Apache-2.0, 734KB, SHA-256 deacb991…850cae)를 jvmMain/resources 에 넣고 adb push 로 올린다. Android 5.0+ 전부에서 검증된 코드고, 영상·입력·호버가 한 프로토콜에 있다. 기기 화면 스펙이 예전에 scrcpy 를 버린 이유는 "별도 설치" 와 "다른 타깃에 디코더가 없음" 이었다. 앞은 번들로 없어졌고, 뒤는 R11(호스트가 디코딩해서 JPEG 로) 로 푼다. 버전은 서버가 인자로 받은 버전 문자열과 자기 버전이 다르면 시작을 거부하므로 코드에 상수로 박아 둔다.
  • Android Studio 의 screen-sharing-agent. Studio 가 설치되어 있어야 하고 경로·프로토콜이 문서화되어 있지 않다. 버렸다.
  • adb exec-out screencorder --output-format=h264 -. 기기 안의 표준 도구라 올릴 것이 없지만, 3분마다 끊기고(--time-limit 상한) 입력 채널이 없어서 탭은 여전히 input 프로세스, 호버는 불가다. 버렸다.
  • screencap 을 PNG 없이(raw RGBA) 받기. 인코딩은 없지만 한 장이 10MB 라 무선 adb 에서는 1초를 넘는다. 버렸다.
  • 직접 만든 dex 에이전트가 JPEG 를 흘려보내기. 디코더는 어느 타깃에도 있지만 화면 캡처의 숨은 API 를 우리가 쫓아야 한다. 버렸다.
결정: H.264 디코더는 FFmpeg(bytedeco javacpp-presets)
  • 채택. org.bytedeco:ffmpeg:8.1.2-1.5.14 + macosx-arm64·macosx-x86_64 네이티브(각 20~24MB). Android Studio 가 Running Devices 에 쓰는 것과 같은 라이브러리다. libavcodec 의 H.264 디코더는 LGPL 이라 비-GPL 아티팩트로 충분하다. 1080×2520 한 장 디코딩 + BGRA 변환이 M 시리즈에서 5ms 안이다. 데스크톱은 macOS 만 지원하므로 그 둘만 넣는다.
  • JCodec(순수 Java). 의존성이 작지만 1080p 디코딩이 실시간을 못 따라가고 High profile 의 일부 기능이 빠져 있다. 버렸다.
  • macOS VideoToolbox 를 Java FFM 으로. 하드웨어 디코딩이지만 CMVideoFormatDescription·VTDecompressionSession 바인딩을 손으로 써야 한다. 버렸다.
  • 호스트에 설치된 ffmpeg CLI. 설치가 필요하다(R8). 버렸다.
결정: 호버는 기기에 넣고, 데스크톱 UI 에는 아무것도 그리지 않는다 Running Devices 의 호버 효과는 기기 안의 UI 가 ACTION_HOVER_MOVE 를 받아 그리는 것이다. 에이전트의 터치 메시지에 마우스 포인터 id(-1)와 HOVER_MOVE 동작을 실으면 에이전트가 SOURCE_MOUSE 로 주입한다. 데스크톱 앱 쪽에 커서나 강조를 따로 그리면 기기 화면을 가린다.
결정: 탭·스와이프 대신 DOWN·MOVE·UP 을 그대로 보낸다 예전에는 input 명령의 모양(tap x y, swipe … ms)에 맞춰 화면이 제스처를 분류하고 끝난 뒤 한 번에 보냈다. 이제 채널이 이벤트 단위라 분류할 이유가 없다. 길게 누르기·플링·드래그 앤 드롭이 저절로 된다. 도메인 모델도 이벤트 단위로 바꾸고 Tap·Swipe 는 지운다 — 두 벌을 두면 로컬 에이전트의 와이어 포맷도 두 벌이 된다.
결정: 픽셀 프레임을 도메인 타입으로 둔다 디코딩된 프레임을 PNG·JPEG 로 다시 인코딩해 ByteArray 로 넘기면 한 장에 10~40ms 가 더 들어 60fps 가 나오지 않는다. ImageBitmap 은 Compose 타입이라 도메인에 둘 수 없다(기기 화면). 그래서 폭·높이·BGRA 바이트만 가진 Pixels 를 도메인에 두고 ImageBitmap 변환은 ui 의 expect 로 뺀다.

한계

  • 호버가 끝났다는 이벤트를 보내지 않는다. 마우스가 기기 화면 밖으로 나가도 기기는 마지막 호버 위치에 머문다. 다음 터치나 호버가 들어오면 풀린다. scrcpy 와 같은 동작이다. 에이전트가 HOVER_EXIT 를 마우스 이벤트로 다루지 않아서 보내도 손가락 이벤트로 들어간다.
  • Android·iOS·Web 은 여전히 폴링이다. 100ms 마다 JPEG 한 장이라 최대 10fps 고, 제스처는 HTTP 왕복(에뮬레이터에서 5~20ms)이 든다. 영상을 직접 받으려면 타깃마다 디코더가 필요하다(스코프 밖).
  • 영상은 긴 변 2048px 로 축소된다. 기기 디스플레이가 그보다 크면(태블릿 1848×2960) 데스크톱에서 픽셀 단위로 확대해 보면 흐리다. 좌표는 에이전트가 되돌리므로 정확하다.
  • 디스플레이가 둘인 기기는 첫 디스플레이만. display_id 를 기본값(0)으로 둔다. 접힌 상태에 따라 켜진 디스플레이가 바뀌는 문제는 기기 화면과 같다.
  • 화면이 멈춰 있으면 프레임도 멈춘다. 에이전트는 화면이 바뀔 때만 인코딩한다. 그래서 새 구독자에게는 replay = 1 이 마지막 장을 준다.
  • 기기 안에 /data/local/tmp/scrcpy-server.jar 가 남는다. 세션마다 다시 올린다(734KB, 0.1~0.3초). 다른 scrcpy 클라이언트가 같은 경로를 쓰지만 서로 덮어써도 시작 시점에 자기 것을 올리므로 문제없다.
  • 데스크톱 배포 크기가 45MB 늘어난다. FFmpeg 네이티브 두 아키텍처다.
  • 화면이 꺼진 기기는 검은 프레임 한 장이 온 뒤 멈춘다. 화면 켜기 카드는 그대로 동작한다.
  • 에이전트 프로세스는 우리가 소켓을 닫으면 스스로 끝난다. 앱이 강제 종료되면 기기 안에 잠시 남지만, 소켓이 끊긴 것을 알고 곧 끝난다.
