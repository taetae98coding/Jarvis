사용자 지시

emulator 같은 경우 emulator뿐만 아니라 연결된 실제 디바이스도 포함시켜줘. 그리고 꺼진 emulator는 실행할 수 있도록 기능도 제공해줘.

2026-09-22 대화. 앞문장은 기기 목록·화면·제스처에 있다.

요구사항

  1. R1. 기기 목록에서 꺼져 있는 가상 기기 줄에 실행 아이콘 버튼(JarvisIcons.Play, contentDescription "실행")이 붙는다. 이미 실행 중인 기기와 실물 기기에는 붙지 않는다.
  2. R2. 버튼을 누르면 그 기기가 켜진다. Android 는 그 AVD 가, iOS 는 그 시뮬레이터가 뜬다.
  3. R3. 누른 뒤 그 기기가 실행 중이 되거나 목록에서 사라질 때까지 버튼은 잠기고, 아이콘 자리에 원형 진행 표시가 돌며 contentDescription 이 "켜는 중…" 이 된다. 같은 기기에 실행 요청이 두 번 나가지 않는다.
  4. R4. 2분 안에 켜지지 않으면 잠금을 풀어 다시 누를 수 있게 한다.
  5. R5. 켜진 기기는 다음 목록 갱신(최대 5초) 때 실행 중으로 바뀌고, 그때부터 화면을 볼 수 있다.
  6. R6. 켤 수 없는 기기에 실행 요청이 들어와도 기기까지 가지 않는다. 화면이 막는 것과 별개로 도메인에서 한 번 더 막는다.
스코프에서 뺀 것
  • 끄는 것. 켜는 것만 한다. 에뮬레이터를 끄는 건 되돌리기 어려운 동작이라 지시에 없는 이상 넣지 않는다.
  • 부팅 옵션(콜드 부트, 데이터 지우기, 창 없이 띄우기). AVD 에 저장된 설정 그대로 띄운다.
  • AVD·시뮬레이터를 새로 만들거나 지우는 것.
  • 실물 기기를 깨우거나 잠금을 푸는 것. 켤 대상이 아니다.
  • 실행 실패를 화면에 알리는 것. 아래 한계 참고.

상태
EmulatorDevicesViewModel.launchingDevices: StateFlow<Set<String>> — 실행을 눌렀고 아직 뜨지 않은 기기의 id. 요청 집합과 기기 목록을 combine 해서 유도한다

실행은 요청만 보내고 결과를 기다리지 않는다. 켜졌는지는 목록 폴링이 알려주는 것이 유일한 경로다. 그래서 들고 있는 것은 "요청을 보냈다" 하나뿐이고, 화면에 보이는 잠금은 그것과 목록에서 유도한다.

launchRequests  = 실행을 누른 id 들          (2분 뒤 스스로 빠진다)
launchingDevices = launchRequests 중에서
                   목록에 아직 "꺼진 기기" 로 남아 있는 id  ← 버튼이 보는 값 (R3)
결정: 켜지는 것을 기다리지 않고 목록 폴링으로 확인한다 emulator -avd 는 에뮬레이터가 꺼질 때까지 살아 있는 프로세스라 기다릴 수 없고, adb wait-for-device 는 어느 기기를 기다릴지 지정할 수 없다. 이미 5초마다 도는 목록이 "떴다" 를 알려주는 가장 정확한 신호다. 대신 그 신호가 오기 전까지는 버튼을 잠가 둔다.
결정: 잠금을 코루틴이 풀지 않고 목록에서 유도한다 처음에는 요청을 보낸 코루틴이 목록에서 그 기기가 사라지기를 기다렸다가(first {}) 집합에서 뺐다. 그 코루틴이 전이를 한 번 놓치면 버튼이 2분 내내 잠긴 채로 남는다. 실제로 Wasm 에서 그 상태를 확인하는 테스트가 세 번에 한 번꼴로 깨졌다. 유도한 값에는 놓칠 전이가 없다 — 목록이 곧 사실이고, 2분 타이머는 뜨지 않는 기기를 영원히 잠가 두지 않기 위한 대비로만 남는다(R4).
결정: 꺼진 AVD 의 id 가 바뀌는 것을 종료 조건에 포함한다 꺼진 AVD 는 avd:<이름>, 켜진 AVD 는 emulator-5554 다(식별자). 그래서 "그 id 가 실행 중이 되는 것" 만 기다리면 Android 에서는 영원히 끝나지 않는다. 시뮬레이터는 UDID 가 그대로라 실행 중으로 바뀐다. 두 경우를 한 조건으로 적으면 "그 id 가 꺼진 채로 목록에 남아 있지 않다" 가 된다.
결정: 실행 요청에 결과를 싣지 않는다 Boolean 을 돌려주면 에이전트를 거치는 세 타깃에서 "요청이 에이전트에 닿았다" 와 "에뮬레이터가 떴다" 가 뒤섞인다. 앞의 것은 사용자에게 쓸모가 없고, 뒤의 것은 에이전트도 모른다. 그래서 반환값을 없애고 목록만 믿는다.

에이전트 프로토콜

로컬 에이전트에 엔드포인트 하나가 더 붙는다. 제스처와 같은 모양이다.

메서드·경로본문응답
POST /emulators/launch{"id":"avd:Pixel_9_API_37"}, Content-Type: text/plain204. 본문을 읽지 못하면 400, GET 이면 405

에이전트는 요청을 받은 즉시 204 를 준다. 에뮬레이터가 뜨는 데 걸리는 시간(수십 초)을 HTTP 응답으로 기다리면 클라이언트 타임아웃(2초)에 먼저 걸린다.

수동 확인R2, R4, R5. 실제로 AVD·시뮬레이터가 뜨는 것 미검증—

실제로 emulator·simctl 을 띄우는 부분은 테스트하지 않는다. 결과가 머신 환경에 따라 달라지고, 성공하면 테스트가 에뮬레이터를 하나 띄운 채로 끝난다.

한계

  • 실패를 알 수 없다. AVD 이미지가 깨졌거나 디스크가 없어서 뜨지 않으면 화면에는 2분 동안 진행 표시만 돌고, 그 뒤 버튼이 다시 살아난다. 이유는 에뮬레이터의 표준 출력에만 있고 그걸 화면까지 가져오는 경로는 만들지 않았다.
  • 켜지기까지 수십 초 걸린다. 콜드 부트면 1분을 넘기기도 한다. R4 의 2분은 그보다 넉넉하게 잡은 값이다.
  • JVM 외에는 데스크톱 앱이 같은 머신에 떠 있어야 한다. 꺼져 있으면 목록 자체가 비어서 누를 버튼도 없다.
  • 실물 기기는 켤 수 없다. 버튼이 붙지 않는다.
  • 이미 뜨는 중인 에뮬레이터를 앱 밖에서(Android Studio 등) 켰다면, 목록에는 아직 꺼진 것으로 보여서 실행 버튼이 눌린다. emulator -avd 를 두 번 부르면 두 번째는 "이미 실행 중" 으로 실패하고 아무 일도 일어나지 않는다.
