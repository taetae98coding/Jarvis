사용자 지시

android/ios에만 해당될 것 같은데 DeviceRotation 카드 만들어줘. 0도, 90도, 270도, 360도 회전잠금on/off, +90도 회전, -90도 회전 제공해야해. 혹시 jvm, wasmJs도 가능하면 같이 추가해줘.

2026-09-22 대화.

(각도 목록의 "360도"를 어떻게 다룰지 물었고) 0/90/180/270 (표준)

2026-09-22 대화. 360도는 0도와 같은 방향이라 버튼이 겹친다. 대신 빠져 있던 180도를 넣어 네 방향을 모두 덮는다.

요구사항

  1. R1. 기능 그리드에 "화면 회전" 카드가 있다.
  2. R2. 카드에 0°·90°·180°·270° 버튼이 있고, 누르면 화면이 그 각도로 돌아간다.
  3. R3. 카드에 회전잠금 토글이 있다. 켜면 현재 각도에 고정되고, 끄면 다시 센서를 따른다.
  4. R4. 카드에 +90°·-90° 버튼이 있고, 현재 각도에서 한 칸씩 돌린다. 270°에서 +90°는 0°, 0°에서 -90°는 270°다.
  5. R5. 각도를 직접 고르면(R2, R4) 회전잠금이 함께 켜진다. 잠그지 않으면 센서가 즉시 되돌려 버튼이 아무 일도 하지 않은 것처럼 보인다.
  6. R6. 현재 각도와 잠금 여부는 앱 밖에서 바뀌어도 카드에 반영된다(상태 조회 규칙).
  7. R7. 특별 권한이 필요한 플랫폼에서 버튼이나 토글을 누르면 권한 설정 화면이 열리고, 허용 여부가 카드 설명에 보인다.
  8. R8. 지원하지 않는 플랫폼에서도 카드는 같은 자리에 있고, 잠긴 채로 왜 불가능한지 보여준다.
스코프에서 뺀 것
  • 360°. 0°와 같은 방향이라 버튼이 하나 더 있어도 구분되는 동작이 없다. 대신 지시에서 빠져 있던 180°를 넣었다.
  • 설정 영구 저장. 회전 각도와 잠금은 앱의 설정이 아니라 지금 기기가 어떤 상태인지다. 앱이 죽은 뒤에도 시스템(또는 브라우저 세션)에 그대로 남으므로 우리 저장소에 따로 적지 않는다. 카드는 항상 시스템에서 읽은 값을 보여준다.
  • JVM에서의 R2~R5. 데스크톱 디스플레이 회전은 공개 API가 없다. R8로 처리한다.

각도 기준

각도는 기기의 natural 방향에서 화면이 반시계로 돌아간 양이다. Android Surface.ROTATION_*와 Web ScreenOrientation.angle이 이미 같은 기준을 쓰고, iOS만 방향 상수로 옮겨야 한다. 방향이 헷갈리기 쉬워서 표로 못박는다.

각도기기 자세 (natural이 세로일 때)AndroidiOSWeb
0°똑바로ROTATION_0Portraitportrait-primary
90°반시계 90° (홈 버튼이 오른쪽)ROTATION_90LandscapeLeftlandscape-primary
180°거꾸로ROTATION_180PortraitUpsideDownportrait-secondary
270°시계 90° (홈 버튼이 왼쪽)ROTATION_270LandscapeRightlandscape-secondary

+90°는 이 표에서 아래로 한 칸, -90°는 위로 한 칸이다. natural이 가로인 기기(일부 태블릿)에서도 각도의 뜻은 같지만, Web은 각도가 아니라 portrait/landscape 이름으로만 잠글 수 있어 대응이 어긋날 수 있다(web.html).

// :domain — 화면과 규칙이 보는 것
enum class RotationAngle(val degrees: Int) { Degrees0(0), Degrees90(90), Degrees180(180), Degrees270(270) }

data class DeviceRotationStatus(
    val supported: Boolean = false,
    val permitted: Boolean = true,
    val locked: Boolean = false,
    val angle: RotationAngle? = null,   // null = 읽을 수 없음
)

interface DeviceRotationRepository {
    fun observeStatus(): Flow<DeviceRotationStatus>   // cold. 수집하는 동안에만 리스너가 붙는다
    fun readStatus(): DeviceRotationStatus              // 첫 프레임 초기값 전용
    fun setAngle(angle: RotationAngle)
    fun setLocked(locked: Boolean)
    fun requestPermission()
}

// :data — 플랫폼이 실제로 할 수 있는 것
internal expect fun createDeviceRotationDataSource(
    context: PlatformContext,
): DeviceRotationDataSource
결정: "각도를 고르면 잠근다"는 규칙은 유스케이스에 둔다 R5는 플랫폼 사정이 아니라 기능의 규칙이다. SetDeviceRotationAngleUseCase가 setLocked(true) 다음에 setAngle(angle)을 부르고, :feature:rotation:domain 테스트가 가짜 리포지토리로 순서까지 검증한다. 세 플랫폼의 actual에 같은 규칙을 세 번 적는 길은 버렸다. 잠금을 먼저 거는 이유는 Android에서 자동 회전이 켜진 채로 USER_ROTATION을 쓰면 값만 남고 화면은 그대로여서다.
결정: 상대 회전은 현재 각도를 리포지토리에서 읽어 계산한다 RotateDeviceUseCase가 observeStatus().first().angle에 ±90를 더해 절대 각도로 바꾼 뒤 SetDeviceRotationAngleUseCase에 넘긴다. 화면이 현재 각도를 들고 있다가 넘기는 길은 버렸다. 화면의 값은 마지막 방출 시점의 것이라, 그 사이 기기가 돌아가면 한 칸이 아니라 두 칸 돌게 된다. 각도를 모르는 상태(null)에서는 0°를 기준으로 삼는다.
결정: 회전 각도는 저장하지 않는다 화면 꺼짐 방지는 설정값을 저장하고 앱이 뜰 때 다시 적용한다. 회전은 반대다. 시스템(또는 브라우저)이 이미 값을 들고 있고 앱이 없어도 유지되므로, 우리가 한 벌 더 저장하면 두 값이 어긋날 때 무엇이 사실인지 알 수 없어진다. 카드는 항상 시스템에서 읽는다. 그래서 JarvisViewModel이 적용하는 효과 목록에도 회전은 없다.

실제로 화면이 도는 경로는 네 플랫폼 모두 미검증이다. 기기·브라우저에서만 돌고, 테스트 환경에는 돌릴 화면이 없다. 각 플랫폼 문서의 검증 절에 수동 확인 방법을 적었다.

한계

  • "기기 전역"인 곳은 Android뿐이다. iOS와 Web은 앱·문서 창만 돌아가고 시스템 회전잠금은 그대로다. 판정 표와 각 플랫폼 문서 참고.
  • 180°는 거절될 수 있다. 노치가 있는 iPhone은 거꾸로 방향을 지원하지 않아 요청이 실패하고 각도가 그대로 남는다. Android도 제조사 ROM이 막을 수 있다.
  • 고정한 각도를 다른 앱이 덮어쓸 수 있다. Android에서 방향을 고정한 앱을 열면 그 앱이 이긴다. 우리는 마지막에 쓴 값만 책임진다.
  • 회전잠금을 끄고 끝나지 않는다. 앱을 종료해도 Android에서는 걸어 둔 잠금이 남는다. 되돌리려면 토글을 끄거나 시스템 설정에서 자동 회전을 켜야 한다.
