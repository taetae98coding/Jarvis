사용자 지시

iterm처럼 terminal 띄울 수 있도록 home에 탭 추가하고 진입화면 만들어줘. iterm처럼 좌우분할,상하분할,탭형식추가 가능하도록 구현해줘.
- JVM 환경만 가능할 것 같은데 JVM은 무조건 구현하고, Andorid/iOS는 가능하면 구현 불가능하면 미구현해줘.

2026-09-24 대화. "home에 탭" 은 홈 그리드의 기능 카드 하나로 읽었다. 홈에는 탭 막대가 없고 기능마다 카드가 하나씩 놓인다(홈 그리드).

요구사항

  1. R1. 홈 그리드에 "터미널" 카드가 있다. 누르면 터미널 화면으로 이동한다. 셸을 띄울 수 없는 타깃에서는 카드가 같은 자리에 잠긴 채로 남고 이유를 보여준다(공통 규약).
  2. R2. 터미널 화면에 들어가면 탭 하나, 패널 하나가 있고 그 패널에 셸이 떠 있다.
  3. R3. 셸 출력은 xterm 호환 제어 시퀀스로 해석해 글자 격자로 그린다. 해석 범위는 아래 표다. 한글 같은 전각 문자는 두 칸을 차지한다.
  4. R4. 포커스된 패널의 키 입력이 그 셸로 간다. 문자(IME 로 조합한 한글 포함), Enter, Backspace, Tab, Shift+Tab, Esc, 방향키, Home/End/PageUp/PageDown/Insert/Delete, F1–F12, Ctrl+문자.
  5. R5. 좌우 분할 — 포커스된 패널을 좌우로 나누고 오른쪽에 새 셸을 띄운다. 새 패널이 포커스를 가져간다. 아이콘 버튼 SplitSideBySide(contentDescription "좌우 분할"), 단축키 ⌘D.
  6. R6. 상하 분할 — 포커스된 패널을 위아래로 나누고 아래에 새 셸을 띄운다. 새 패널이 포커스를 가져간다. 아이콘 버튼 SplitStacked(contentDescription "상하 분할"), 단축키 ⌘⇧D.
  7. R7. 새 탭 — 탭 줄 끝에 패널 하나짜리 탭이 붙고 선택된다. 아이콘 버튼 Add(contentDescription "새 탭"), 단축키 ⌘T.
  8. R8. 분할은 중첩된다. 두 패널 사이 경계선을 끌어 비율을 바꾼다. 비율은 0.1–0.9 로 묶인다.
  9. R9. 패널 크기가 바뀌면 격자의 열·행 수를 다시 계산하고 셸에 알린다.
  10. R10. 닫기 — Close 아이콘 버튼(contentDescription "닫기") 또는 ⌘W 가 포커스된 패널을 닫고 그 셸을 끝낸다. 형제 패널이 부모 자리를 채우고 포커스를 받는다. 탭의 마지막 패널이면 탭이 닫히고, 마지막 탭이면 홈으로 돌아간다. 탭의 닫기 아이콘(Close, contentDescription "탭 닫기")은 그 탭의 패널을 전부 닫는다.
  11. R11. 셸이 스스로 끝나면(exit) 그 패널이 R10 과 같이 닫힌다.
  12. R12. 패널을 누르면 포커스가 그 패널로 간다. 한 탭에 패널이 둘 이상이면 포커스된 패널에 테두리가 그려진다. ⌘] / ⌘[ 는 다음·이전 패널, ⌘⇧] / ⌘⇧[ 는 다음·이전 탭, ⌘1–⌘9 는 그 번호의 탭을 고른다.
  13. R13. 탭 이름은 그 탭에서 포커스된 패널의 셸이 OSC 0/2 로 정한 제목이다. 제목이 없으면 "셸 N"(N 은 탭 순번).
  14. R14. 화면 위로 밀려난 줄은 패널마다 2,000줄까지 남는다. 휠·드래그로 거슬러 올라가 볼 수 있고, 키를 누르면 맨 아래로 돌아온다.
  15. R15. 터미널 화면을 벗어나면(뒤로) 그 화면의 셸을 전부 끝낸다.
스코프에서 뺀 것
  • 텍스트 선택·복사, 찾기, 마우스 리포팅(?1000 계열). 붙여넣기는 입력 필드가 받아 준다(⌘V).
  • 프로필·색 테마·글꼴 설정, 패널 균등 정렬, 탭 순서 바꾸기, 패널을 다른 탭으로 옮기기.
  • 화면을 벗어난 뒤에도 셸을 살려 두기, 앱을 다시 켰을 때 세션 복원. 보이지 않는 셸이 떠돌지 않게 R15 로 막았다.
  • 개발자 머신의 셸을 다른 타깃에서 원격으로 쓰기. 에뮬레이터 기능은 로컬 에이전트로 그렇게 하지만, 셸은 인증 없는 로컬 HTTP 로 내보낼 수 없다(iOS 참고).
  • iOS 와 Web. 셸 프로세스를 띄울 수 없다(판정). Web 은 지시에 없었지만 같은 이유로 불가다.

공통 구현

기능 모듈 셋을 새로 만든다. :feature:terminal:domain · :feature:terminal:data · :feature:terminal:ui. 다른 기능과 마찬가지로 서로 다른 기능을 보지 않는다(모듈 구조).

리포지토리
TerminalRepository.isSupported: Boolean, suspend fun open(size: TerminalSize, program: TerminalProgram = Shell): TerminalSession? — null 은 셸을 띄우지 못한 것. program 과 isClaudeSupported 는 Claude 실행
세션
TerminalSession — isPty, output: Flow<ByteArray>(셸이 끝나면 완료), write(bytes), resize(size), close()
유스케이스
IsTerminalSupportedUseCase, OpenTerminalSessionUseCase
도메인 규칙
TerminalWorkspace — 탭·분할 트리·포커스. 불변 값이고 분할·닫기·탭 추가가 새 값을 돌려준다(R5–R8, R10, R12).
TerminalEmulator — 바이트를 글자 격자로 해석한다(R3, R9, R13, R14). 셸에 되돌려 줄 응답(DSR 등)도 만든다.
TerminalKey · encodeTerminalKey() — 키를 셸이 기대하는 바이트로 바꾼다(R4).
LineDiscipline — pty 가 없는 세션에서 에코와 줄 편집을 대신한다(Android).

결정: 터미널 해석과 그리기를 공통 코드로 직접 만든다 JVM 에서 가장 쉬운 길은 JetBrains 의 JediTerm(Swing 위젯)을 SwingPanel 로 끼우는 것이었다. 버렸다. (1) Swing 컴포넌트가 포커스를 쥐면 ⌘D 같은 단축키가 Compose 에 오지 않아 분할·탭을 Compose 로 만들 수 없다. (2) 패널마다 SwingPanel 이 생겨 분할 경계선 드래그와 겹쳐 그리기가 interop 의 제약을 그대로 받는다. (3) 화면 컴포저블이 플랫폼마다 갈라져 ui 에 expect 가 생긴다 — 이 프로젝트는 ui 에 expect 를 두지 않는다(예외). 직접 만들면 해석기를 commonTest 로 검증할 수 있고, Android 도 같은 화면을 쓴다. 대가는 해석 범위가 xterm 전체가 아니라는 것이고, 그 범위를 아래에 적는다.
결정: 에뮬레이터를 domain 에 둔다 바이트 → 격자 규칙은 플랫폼도 Compose 도 모르는 순수 로직이라 R5 의 "domain 은 아무것도 보지 않는다" 를 지킨다. ui 에 두면 화면 테스트 없이는 검증할 수 없고, data 에 두면 키 인코딩이 에뮬레이터의 모드(애플리케이션 커서 키)를 알아야 해서 화면이 data 를 봐야 한다.
결정: 입력은 커서 자리에 겹친 투명한 BasicTextField(state: TextFieldState) 가 받는다 Canvas 에 onKeyEvent 만 달면 IME 조합(한글)이 오지 않는다. 입력 필드가 조합을 받고, 조합이 끝나 확정된 글자만 셸로 보내고 필드를 비운다. 조합 중인 글자는 필드가 커서 자리에 그대로 보여준다. 특수 키는 onPreviewKeyEvent 가 먼저 가로채 바이트로 바꾼다 — 조합 중일 때의 Backspace·Enter·방향키는 IME 에 양보한다. 붙여넣기도 이 필드가 받는다.
처음에는 값을 받는 BasicTextField(value: TextFieldValue) 로 만들었다가 버렸다. onValueChange 에서 빈 값을 돌려주면 필드가 받는 인자가 직전과 같은 빈 값이라 IME 쪽 버퍼를 비우지 않고, 다음 글자가 앞 글자에 붙어 통째로 다시 왔다(p, pr, pri…). 한 프레임 뒤에 비우는 우회도 빠르게 칠 때 경계에서 글자가 겹쳤다. TextFieldState 는 상태가 곧 IME 버퍼라 clearText() 가 버퍼까지 비운다. Compose 테스트의 performTextInput 은 이 경로를 타지 않아 자동 테스트로 재현되지 않았고, 데스크톱 앱에서 손으로 확인했다.
결정: 에뮬레이터는 메인 스레드에서만 만진다 데이터 소스가 IO 스레드에서 읽은 덩어리를 viewModelScope(Main)에서 해석한다. 그리기도 메인이라 잠금이 필요 없다. 초당 수 MB 를 쏟는 명령(yes, 큰 파일 cat)에서는 해석이 프레임을 먹는다. 스냅숏을 복사해 넘기는 쪽은 한 화면 격자를 매 덩어리마다 복사해야 해서 지금 규모에서는 버렸다.

터미널 해석 범위

JVM 은 TERM=xterm-256color 를 넘긴다. 셸과 vim·less·top 이 실제로 쓰는 것을 중심으로 아래만 해석하고, 모르는 시퀀스는 끝까지 읽어서 버린다(화면에 찌꺼기가 찍히지 않는다).

한계

  • 해석 범위 밖의 시퀀스를 쓰는 프로그램은 화면이 틀어질 수 있다. 특히 마우스 리포팅을 켜는 프로그램(htop 의 클릭, vim 의 mouse=a)은 클릭이 가지 않는다.
  • 텍스트를 선택해 복사할 수 없다.
  • 창 크기를 줄였다 늘려도 잘린 줄이 되살아나지 않는다(reflow 없음).
  • 화면을 벗어나면 셸이 끝난다. 긴 작업은 tmux·nohup 으로 돌려야 한다.
  • 출력이 매우 많으면 메인 스레드 해석이 화면을 끊기게 한다(결정).
  • Android 는 pty 가 없어 대화형 전체 화면 프로그램이 돌지 않는다(Android).
