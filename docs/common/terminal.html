터미널

iTerm 처럼 앱 안에서 셸을 띄우고, 창을 좌우·상하로 나누고, 탭을 더한다. 탭은 왼쪽 목록의 패널에 속한다.

같은 날 뒤따른 지시로 탭 위에 패널 층이 생기고 배치와 세션이 앱을 다시 켜도 남게 됐다. 그 지시와 요구사항은 터미널 패널과 세션 유지에 있고, 이 문서에서 분할된 한 칸을 부르던 "패널" 은 그때부터 "창" 이다(용어). 아래 R2·R10·R13·R15 는 그 지시에 맞춰 고쳤다. 다시 뒤따른 탭 끌어 놓기 지시로 상단 막대의 동작 버튼이 없어지고 새 탭(+)은 탭 줄 끝으로, 분할은 탭을 끌어 놓는 것으로 바뀌었다. R5·R6·R7·R10 의 버튼 부분이 그렇게 고쳐졌다. 다시 뒤따른 분할 그룹 지시로 분할 트리가 탭이 아니라 패널에 붙고 나뉜 칸(그룹)마다 탭 줄을 가지게 됐다. R5–R8·R10·R12·R13 은 그룹 기준으로 고쳤다.

요구사항

  1. R1. 홈 그리드에 "터미널" 카드가 있다. 누르면 터미널 화면으로 이동한다. 셸을 띄울 수 없는 타깃에서는 카드가 같은 자리에 잠긴 채로 남고 이유를 보여준다(공통 규약).
  2. R2. 처음 터미널 화면에 들어가면 패널 하나에 탭 하나, 창 하나가 있고 그 창에 셸이 떠 있다. 그 뒤로는 저장된 배치가 복원된다(패널 R9).
  3. R3. 셸 출력은 xterm 호환 제어 시퀀스로 해석해 글자 격자로 그린다. 해석 범위는 아래 표다. 한글 같은 전각 문자는 두 칸을 차지한다.
  4. R4. 포커스된 창의 키 입력이 그 셸로 간다. 문자(IME 로 조합한 한글 포함), Enter, Shift+Enter(줄바꿈, 결정), ⌘← / ⌘→(입력 중인 줄의 맨 앞·맨 끝), ⌘⌫(입력 중인 줄 지우기)(결정), Backspace, Tab, Shift+Tab, Esc, 방향키, Home/End/PageUp/PageDown/Insert/Delete, F1–F12, Ctrl+문자.
  5. R5. 좌우 분할 — 포커스된 그룹을 좌우로 나누고 오른쪽에 새 셸 탭 하나짜리 그룹을 둔다. 새 그룹이 포커스를 가져간다. 단축키 ⌘D. 탭을 그룹의 왼쪽·오른쪽 변에 끌어 놓아도 좌우로 나뉜다(분할 그룹 R7).
  6. R6. 상하 분할 — 포커스된 그룹을 위아래로 나누고 아래에 새 셸 탭 하나짜리 그룹을 둔다. 새 그룹이 포커스를 가져간다. 단축키 ⌘⇧D. 탭을 그룹의 위·아래 변에 끌어 놓아도 상하로 나뉜다(분할 그룹 R7).
  7. R7. 새 탭 — 포커스된 그룹의 탭 줄 끝에 탭이 붙고 선택된다. 그룹마다 있는 + 버튼(Add, contentDescription "새 탭", 분할 그룹 R2), 단축키 ⌘T.
  8. R8. 분할은 중첩된다. 두 그룹 사이 경계선을 끌어 비율을 바꾼다. 비율은 0.1–0.9 로 묶인다.
  9. R9. 창 크기가 바뀌면 격자의 열·행 수를 다시 계산하고 셸에 알린다.
  10. R10. 닫기 — ⌘W 는 포커스된 그룹의 선택된 탭을, 탭의 닫기 아이콘(Close, contentDescription "탭 닫기")은 그 탭을 닫고 셸을 끝낸다. 그룹의 마지막 탭이면 그룹이 사라지고 형제 그룹이 부모 자리를 채우며 닫힌 자리와 맞닿은 그룹이 포커스를 받는다. 패널의 마지막 그룹이면 패널이 빈 채로 남는다(분할 그룹 R3, 패널 R7).
  11. R11. 셸이 스스로 끝나면(exit) 그 탭이 R10 과 같이 닫힌다.
  12. R12. 창을 누르면 그 그룹이 포커스를 받는다. 패널에 그룹이 둘 이상이면 포커스된 그룹의 창에 테두리가 그려진다. ⌘] / ⌘[ 는 다음·이전 그룹, ⌘⇧] / ⌘⇧[ 는 그룹 안 다음·이전 탭, ⌘1–⌘9 는 그룹 안 그 번호의 탭을 고른다(분할 그룹 R11).
  13. R13. 탭 이름은 그 탭의 창이 OSC 0/2 로 정한 제목이다. 제목이 없으면 "셸 N", Claude 탭이면 "Claude N"(N 은 그룹 안 탭 순번).
  14. R14. 화면 위로 밀려난 줄은 창마다 2,000줄까지 남는다. 휠·드래그로 거슬러 올라가 볼 수 있고, 키를 누르면 맨 아래로 돌아온다. 전체 화면 프로그램이 마우스 보고나 대체 화면을 켰을 때 휠이 하는 일은 터미널 휠 스크롤에 있다.
  15. R15. 터미널 화면을 벗어나도(뒤로) 셸은 끝나지 않는다. 다시 들어오면 같은 셸과 화면이 보인다(패널 R13). 셸은 사용자가 창을 닫거나 셸이 끝나거나 앱이 끝날 때 끝난다.
스코프에서 뺀 것
  • 텍스트 선택·복사, 찾기, 마우스 리포팅(?1000 계열)의 누르기·끌기·움직임. 휠만 보고한다(터미널 휠 스크롤). 붙여넣기는 입력 필드가 받아 준다(⌘V).
  • 프로필·색 테마·글꼴 설정, 창 균등 정렬, 탭 순서 바꾸기, 창을 다른 탭으로 옮기기.
  • 화면을 벗어난 뒤에도 셸을 살려 두기, 앱을 다시 켰을 때 세션 복원. 보이지 않는 셸이 떠돌지 않게 R15 로 막았다.
  • 개발자 머신의 셸을 다른 타깃에서 원격으로 쓰기. 에뮬레이터 기능은 로컬 에이전트로 그렇게 하지만, 셸은 인증 없는 로컬 HTTP 로 내보낼 수 없다(iOS 참고).
  • iOS 와 Web. 셸 프로세스를 띄울 수 없다(판정). Web 은 지시에 없었지만 같은 이유로 불가다.

단축키의 ⌘ 는 Compose 의 isMetaPressed 다. macOS 에서는 Command 키고, 하드웨어 키보드를 단 Android 에서는 Meta 키다. 터치만 있는 기기는 탭 줄의 + 로 탭을 더하고 탭을 끌어 놓아 나눈다(탭 끌어 놓기). 창 하나만 닫는 단축키 ⌘W 의 터치 대응은 없다 — 탭 닫기나 셸의 exit 뿐이다.

공통 구현

기능 모듈 셋을 새로 만든다. :feature:terminal:domain · :feature:terminal:data · :feature:terminal:ui. 다른 기능과 마찬가지로 서로 다른 기능을 보지 않는다(모듈 구조).

리포지토리
TerminalRepository.isSupported: Boolean, suspend fun open(size: TerminalSize, program: TerminalProgram = Shell): TerminalSession? — null 은 셸을 띄우지 못한 것. program 과 isClaudeSupported 는 Claude 실행
세션
TerminalSession — isPty, output: Flow<ByteArray>(셸이 끝나면 완료), write(bytes), resize(size), close()
유스케이스
IsTerminalSupportedUseCase, OpenTerminalSessionUseCase
도메인 규칙
TerminalWorkspace — 그룹 분할 트리·탭·포커스. 불변 값이고 분할·닫기·탭 추가가 새 값을 돌려준다(R5–R8, R10, R12).
TerminalEmulator — 바이트를 글자 격자로 해석한다(R3, R9, R13, R14). 셸에 되돌려 줄 응답(DSR 등)도 만든다.
TerminalKey · encodeTerminalKey() — 키를 셸이 기대하는 바이트로 바꾼다(R4).
LineDiscipline — pty 가 없는 세션에서 에코와 줄 편집을 대신한다(Android).
공급

결정: 터미널 해석과 그리기를 공통 코드로 직접 만든다 JVM 에서 가장 쉬운 길은 JetBrains 의 JediTerm(Swing 위젯)을 SwingPanel 로 끼우는 것이었다. 버렸다. (1) Swing 컴포넌트가 포커스를 쥐면 ⌘D 같은 단축키가 Compose 에 오지 않아 분할·탭을 Compose 로 만들 수 없다. (2) 창마다 SwingPanel 이 생겨 분할 경계선 드래그와 겹쳐 그리기가 interop 의 제약을 그대로 받는다. (3) 화면 컴포저블이 플랫폼마다 갈라져 ui 에 expect 가 생긴다 — 이 프로젝트는 ui 에 expect 를 두지 않는다(예외). 직접 만들면 해석기를 commonTest 로 검증할 수 있고, Android 도 같은 화면을 쓴다. 대가는 해석 범위가 xterm 전체가 아니라는 것이고, 그 범위를 아래에 적는다.
결정: 에뮬레이터를 domain 에 둔다 바이트 → 격자 규칙은 플랫폼도 Compose 도 모르는 순수 로직이라 R5 의 "domain 은 아무것도 보지 않는다" 를 지킨다. ui 에 두면 화면 테스트 없이는 검증할 수 없고, data 에 두면 키 인코딩이 에뮬레이터의 모드(애플리케이션 커서 키)를 알아야 해서 화면이 data 를 봐야 한다.
결정: 입력은 커서 자리에 겹친 투명한 BasicTextField(state: TextFieldState) 가 받는다 Canvas 에 onKeyEvent 만 달면 IME 조합(한글)이 오지 않는다. 입력 필드가 조합을 받고, 조합이 끝나 확정된 글자만 셸로 보내고 필드를 비운다. 조합 중인 글자는 필드가 커서 자리에 그대로 보여준다. 특수 키는 onPreviewKeyEvent 가 먼저 가로채 바이트로 바꾼다 — 조합 중일 때의 Backspace·Enter·방향키는 IME 에 양보한다. 붙여넣기도 이 필드가 받는다.
처음에는 값을 받는 BasicTextField(value: TextFieldValue) 로 만들었다가 버렸다. onValueChange 에서 빈 값을 돌려주면 필드가 받는 인자가 직전과 같은 빈 값이라 IME 쪽 버퍼를 비우지 않고, 다음 글자가 앞 글자에 붙어 통째로 다시 왔다(p, pr, pri…). 한 프레임 뒤에 비우는 우회도 빠르게 칠 때 경계에서 글자가 겹쳤다. TextFieldState 는 상태가 곧 IME 버퍼라 clearText() 가 버퍼까지 비운다. Compose 테스트의 performTextInput 은 이 경로를 타지 않아 자동 테스트로 재현되지 않았고, 데스크톱 앱에서 손으로 확인했다.
결정: Shift+Enter 는 ESC CR(\x1b\r)을 보낸다 터미널에서 "줄바꿈" 은 키 자체가 아니라 셸 쪽 프로그램이 해석하는 바이트다. xterm 은 Shift+Enter 를 Enter 와 똑같이 CR 로 보내서 받는 쪽이 둘을 구별할 수 없다. Orca(2026-09 설치본의 app.asar 에서 확인)는 수정자가 Shift 뿐인 Enter 를 가로채 ESC CR 을 보내고, 앱이 kitty 키보드 프로토콜을 켰을 때만 ESC [13;2u 를 보낸다. 같은 방식을 따른다. ESC CR 은 Alt(Meta)+Enter 와 같은 바이트라 Claude Code 같은 TUI 가 줄바꿈으로 받고, zsh 의 emacs 키맵도 ^[^M 을 줄바꿈 삽입(self-insert-unmeta)으로 받는다.
버린 후보: ESC [13;2u(CSI u) 를 늘 보내기 — kitty 프로토콜을 켜지 않은 프로그램은 이 시퀀스를 모르고 u 같은 찌꺼기로 받는다. 이 에뮬레이터는 CSI > u 를 해석하지 않으므로 프로토콜이 켜질 일이 없다. LF(\n, Ctrl+J) 보내기 — 셸에서는 Enter 와 똑같이 명령을 실행한다.
소프트 키보드의 Enter 는 키 이벤트가 아니라 줄바꿈 글자로 와서 Shift 를 알 수 없다. 하드웨어 키보드에서만 성립한다.
결정: ⌘← 는 Ctrl+A(0x01), ⌘→ 는 Ctrl+E(0x05), ⌘⌫ 는 Ctrl+U(0x15) 를 보낸다 터미널에는 ⌘ 에 해당하는 수정자가 없다. xterm 의 수정자 인자(ESC [1;9D 같은 Meta 비트)는 받는 프로그램 대부분이 모른다. 그래서 ⌘ 조합은 셸로 보내지 않고 화면 단축키에 남겨 왔고(R12), 창의 입력 필드가 ⌘← / ⌘→ / ⌘⌫ 를 받아 비어 있는 자기 안에서 커서를 옮기거나 지우느라 아무 일도 일어나지 않았다.
Orca(2026-09 설치본의 app.asar 에서 확인)는 수정자가 ⌘ 뿐인 ← / → / ⌫ 를 가로채 0x01 / 0x05 / 0x15 를 보낸다. iTerm2 의 기본 키 매핑도 ← / → 는 같다. 같은 방식을 따른다. readline·zsh 의 emacs 키맵과 Claude Code 가 앞의 두 바이트를 줄 맨 앞·맨 끝으로 받는다. 수정자가 ⌘ 말고 더 있으면(⌘⇧← 등) 지금처럼 셸로 보내지 않는다. IME 조합 중에는 방향키·Backspace 와 같이 IME 에 양보한다.
Ctrl+U 는 받는 쪽마다 지우는 범위가 다르다. readline(bash)·Claude Code 는 커서 앞부분(macOS 의 ⌘⌫ 와 같다), zsh 의 emacs 키맵은 줄 전체(kill-whole-line, 2026-09-25 zsh -f 에서 확인)를 지운다. 커서가 줄 끝에 있는 흔한 경우에는 결과가 같다. zsh 에서 커서 앞만 지우는 backward-kill-line 은 기본 키맵에 묶인 바이트가 없어 보낼 대안이 없다.
버린 후보: Home / End 의 xterm 바이트(ESC [H / ESC [F, 애플리케이션 모드면 ESC OH / ESC OF) 보내기 — Claude Code 는 받지만 macOS 기본 zsh 는 받지 않는다. /etc/zshrc 는 terminfo 의 khome·kend(xterm-256color 에서 ESC OH / ESC OF)만 줄 맨 앞·맨 끝에 묶고 애플리케이션 커서 모드(smkx)는 켜지 않아서, 프롬프트에서 가는 ESC [H / ESC [F 는 아무 위젯에도 묶이지 않는다(2026-09-25, macOS 26 에서 확인). Ctrl+A / Ctrl+E 는 키맵 설정 없이 둘 다에서 된다. 대가로 vim 일반 모드에서 ⌘← 는 숫자 증가(Ctrl+A)가 된다 — Orca·iTerm2 와 같다.
⌘⌦(Fn+⌘⌫, 커서 뒤 지우기, Orca 는 Ctrl+K 0x0B) 와 ⌘↑ / ⌘↓(스크롤) 는 지시에 없어 넣지 않았다.
결정: 에뮬레이터는 메인 스레드에서만 만진다 데이터 소스가 IO 스레드에서 읽은 덩어리를 viewModelScope(Main)에서 해석한다. 그리기도 메인이라 잠금이 필요 없다. 초당 수 MB 를 쏟는 명령(yes, 큰 파일 cat)에서는 해석이 프레임을 먹는다. 스냅숏을 복사해 넘기는 쪽은 한 화면 격자를 매 덩어리마다 복사해야 해서 지금 규모에서는 버렸다.

한계

  • 해석 범위 밖의 시퀀스를 쓰는 프로그램은 화면이 틀어질 수 있다. 마우스 리포팅을 켜는 프로그램(htop 의 클릭, vim 의 mouse=a)에는 휠만 가고 클릭은 가지 않는다(터미널 휠 스크롤).
  • 글자 선택은 끌기뿐이다(끌어 선택·복사). 두 번 눌러 낱말, ⌘C 는 없다.
  • 창 크기를 줄였다 늘려도 잘린 줄이 되살아나지 않는다(reflow 없음).
  • 앱을 끝내면 셸이 끝난다(패널 한계). 긴 작업은 tmux·nohup 으로 돌려야 한다.
  • 출력이 매우 많으면 메인 스레드 해석이 화면을 끊기게 한다(결정).
  • Android 는 pty 가 없어 대화형 전체 화면 프로그램이 돌지 않는다(Android).
