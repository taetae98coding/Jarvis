프로파일링 (CPU·메모리·GPU·네트워크·디스크)

홈의 "프로파일링" 카드가 이 앱이 돌고 있는 기기의 CPU·메모리·GPU 사용률, 네트워크 속도, 디스크 읽기·쓰기 사용률, 디스크 남은 용량을 1초마다 새로 보여준다.

사용자 지시

home에 Profiling 정보 노출하도록 구현해줘.
- cpu, memory, gpu, network, disk(read/write 퍼센트), disk(남은용량)

2026-09-25 대화.

요구사항

  1. R1. 홈 기능 그리드에 "프로파일링" 카드가 있고, 지표 여섯 줄을 이 순서로 보인다: CPU, 메모리, GPU, 네트워크, 디스크 읽기·쓰기, 디스크 남은 용량.
  2. R2. CPU·GPU 는 사용률(%)이다. 메모리는 사용량 / 전체와 그 비율, 네트워크는 받기·보내기 속도(초당 바이트), 디스크 읽기·쓰기는 읽기가 디스크를 차지한 시간 비율(%)과 쓰기가 차지한 시간 비율(%), 디스크 남은 용량은 남은 바이트 / 전체다.
  3. R3. 값은 카드가 보이는 동안 1초(ProfilingPollInterval)마다 다시 읽는다. 이 지표들은 시스템이 변경을 알려주지 않으므로 상태 조회 규칙 R2 의 폴링이다. 카드가 화면에서 사라지거나 앱이 백그라운드로 가면 읽기를 멈춘다(R11, R14).
  4. R4. 두 표본의 차이로 구하는 지표(CPU, 네트워크, 디스크 읽기·쓰기)는 첫 표본에 "측정 중" 을 보이고, 다음 표본부터 값을 보인다.
  5. R5. 플랫폼이 줄 수 없거나 읽기에 실패한 지표는 "측정 불가" 로 보인다. 카드 전체가 숨거나 앱이 죽지 않는다.
  6. R6. 기기 전체가 아니라 이 앱(Android CPU, Web 메모리)이나 이 사이트(Web 저장 공간)만 잰 값은 줄 이름 뒤에 "(이 앱)" 을 붙여 기기 전체 값과 구분한다.
  7. R7. 첫 프레임부터 카드의 모양이 흔들리지 않는다. 이 플랫폼이 지원하지 않는 지표는 첫 프레임부터 "측정 불가", 지원하는 지표는 "측정 중" 으로 시작한다.
스코프에서 뺀 것
  • 값의 이력(그래프). 카드는 지금 값만 보인다. 상태 조회 규칙의 한계대로 중간 값은 건너뛴다.
  • 프로세스별 목록(가장 CPU 를 많이 쓰는 앱 등). 대부분의 플랫폼이 다른 앱을 들여다보지 못하게 막는다.
  • 연결된 기기(에뮬레이터·실물 기기)의 지표. 이 카드는 Jarvis 가 떠 있는 기기만 잰다.
  • 경고·알림(예: CPU 90% 이상). 보여 주기만 한다.

  • 바이트는 1000 단위(B, KB, MB, GB, TB)로 적는다. macOS·Android 의 파일 크기 표기와 같다. 100 미만이면 소수 한 자리까지 적고 .0 은 뗀다(1.2 MB, 27.6 GB, 30 KB, 494 GB).
  • 퍼센트는 0–100 으로 자른다. 두 디스크가 동시에 바쁘거나 요청이 겹치면 합이 100 을 넘을 수 있어서다(한계).
결정: "disk read/write 퍼센트" 는 시간 비율이다 디스크 읽기·쓰기에는 전체라는 것이 없어서 바이트 속도로는 퍼센트를 만들 수 없다. iostat·Windows 작업 관리자의 "활성 시간" 처럼, 표본 간격 동안 디스크가 읽기(쓰기) 요청을 처리하던 시간의 비율로 정했다. 읽기·쓰기를 합친 활성 시간 하나로 줄이는 안은 지시가 둘을 나눠 적어서 버렸다.
결정: 새로 고침은 1초다 top 과 Android Studio 프로파일러가 1초, macOS 활동 모니터 기본값이 5초다. 이 카드는 "지금 얼마나 바쁜가" 를 보는 용도라 짧은 쪽을 골랐다. JVM 은 한 번 읽는 데 명령 넷을 띄우며 개발 머신에서 합쳐 약 50ms 가 걸렸다(jvm.html). 카드가 보이는 동안에만 돈다.

공통 구현

기능 하나가 :feature:profiling:domain · :feature:profiling:data · :feature:profiling:ui 셋을 갖는다(모듈 구조 R1). 패키지는 domain.profiling · data.profiling · ui.profiling 이다.

모델
domain/profiling/Profiling.kt — 지표 여섯을 담는 data class Profiling. 지표마다 Reading<T>(Measuring · Unavailable · Available(value)). 값은 Usage(percent, scope), MemoryUsage(usedBytes, totalBytes, scope), NetworkThroughput(receivedBytesPerSecond, sentBytesPerSecond), DiskActivity(readPercent, writePercent), DiskSpace(freeBytes, totalBytes, scope). scope 는 ProfilingScope.DEVICE / APP(R6)
계약
domain/profiling/ProfilingRepository.kt — supportedMetrics: Set<ProfilingMetric>(실행 중에 바뀌지 않는 값, 상태 조회 규칙 R10), observeProfiling(): Flow<Profiling>(cold, R11)
유스케이스
ObserveProfilingUseCase(scope): StateFlow<Profiling>. observeProfiling().stateIn(scope, WhileSubscribed(), Profiling.initial(supportedMetrics)) 다(R7)
상태
data/profiling/DefaultProfilingRepository.kt. 수집 하나마다 ProfilingSource.openSampler() 로 표본기를 새로 열고 observeByPolling(ProfilingPollInterval) { sampler.sample() } 로 흘린다
공급
internal expect fun createProfilingSource(context: PlatformContext): ProfilingSource (data.profiling). ProfilingSource 는 supportedMetrics 와 openSampler(): ProfilingSampler 를, ProfilingSampler 는 suspend fun sample(): Profiling 하나를 가진다
차이 계산
data/profiling/CounterDelta.kt — 누적 카운터(바이트, CPU 틱, 디스크 사용 시간)를 직전 표본과의 차이와 경과 시간으로 바꾼다. 첫 표본은 null(R4), 카운터가 줄어들면(재부팅·인터페이스 교체·32비트 넘침) 그 표본의 차이는 0 이다
UI
ui/profiling/ProfilingCard.kt(카드), ui/profiling/ProfilingViewModel.kt, ui/profiling/ProfilingFormat.kt(바이트·퍼센트 표기)
// :feature:profiling:data — 수집 하나마다 표본기를 새로 연다
override fun observeProfiling(): Flow<Profiling> = flow {
    val sampler = source.openSampler()
    emitAll(observeByPolling(ProfilingPollInterval) { sampler.sample() })
}
결정: 표본기는 수집마다 새로 연다 속도 지표는 직전 표본을 기억해야 한다. 리포지토리가 표본기 하나를 들고 있으면 구독자 둘이 번갈아 읽을 때 서로의 직전 표본을 빼앗아 간격이 절반인 값이 나온다. 수집마다 openSampler() 로 새 상태를 만들면 구독자마다 제 간격으로 잰다. 대신 구독자가 둘이면 읽기도 두 벌이다. 지금 구독자는 카드 하나뿐이라 상태 조회 규칙 R12 의 shareIn 은 쓰지 않는다.
결정: 지원 여부는 상태가 아니라 값이다 어떤 지표를 줄 수 있는지는 플랫폼이 정하고 실행 중에 바뀌지 않는다(상태 조회 규칙 R10). 그래서 supportedMetrics 는 Flow 가 아니라 일반 프로퍼티이고, 첫 프레임의 초기값(R7)을 만드는 데만 쓴다. 읽기에 실패한 지표는 지원 목록에 있어도 Unavailable 을 흘린다(R5).

한계

  • 1초 간격의 평균이다. 그 사이의 짧은 치솟음은 보이지 않는다.
  • 디스크 읽기·쓰기 퍼센트는 요청이 겹치면 실제 활성 시간보다 크게 잡히고, 디스크가 여럿이면 합쳐 센다. 그래서 100 으로 자른다. 정확한 "활성 시간" 이 아니라 부하의 눈대중이다.
  • 플랫폼마다 재는 범위가 다르다(판정 표). 같은 "CPU 23%" 라도 Android 는 이 앱, JVM 은 기기 전체다. 줄 이름의 "(이 앱)" 이 그 차이를 알린다.
  • 카드를 보고 있지 않은 동안은 재지 않는다. 다시 보면 속도 지표는 한 번 "측정 중" 을 거친다.
