터미널 휠 스크롤

셸·Claude 탭에서 마우스 휠·트랙패드·드래그로 스크롤한다. 셸 출력은 스크롤백을 움직이고, 전체 화면 프로그램(Claude Code 의 전체 화면 모드, vim, less)에서는 휠을 그 프로그램에 휠 이벤트나 방향키로 넘겨서 프로그램이 스스로 스크롤하게 한다.

사용자 지시

지금 터미널이나 Claude에서 scroll 지원해?

2026-09-25 대화. 조사해서 "셸의 스크롤백은 휠로 되지만, 대체 화면을 쓰는 전체 화면 프로그램에서는 스크롤백이 0 이고 마우스 보고(DECSET 1000 계열)를 해석하지 않아 휠이 아무 일도 하지 않는다" 고 답했다. 그러면서 (1) 스펙에 휠 스크롤 요구사항을 적고, (2) 마우스 보고 1000/1002/1006 을 넣어 휠을 SGR 로 보내고, (3) 마우스 보고가 꺼진 대체 화면에서는 xterm 의 alternateScroll(1007)처럼 휠을 ↑/↓ 로 바꾸자고 제안했다.

진행해줘.

2026-09-25 대화. 위 제안 세 가지를 그대로 받아들였다.

조사하다 보니 사용자의 Claude Code 설정(~/.claude/settings.json)이 "tui": "fullscreen" 이었다. Claude Code 2.1.282 는 이 모드(환경 변수 CLAUDE_CODE_NO_FLICKER=1 과 같다)에서 켜자마자 ESC[?1049h(대체 화면)와 ESC[?1000h ESC[?1002h ESC[?1003h ESC[?1006h(마우스 보고, SGR 인코딩)를 보낸다(pty 로 띄워 출력을 받아 확인). 대화 기록은 Claude Code 가 대체 화면 안에서 직접 그리고, 휠 이벤트를 받아야 스스로 스크롤한다. 그래서 Jarvis 의 Claude 탭에서 휠이 아무 일도 하지 않았다. 기본 모드(tui 설정이 없을 때)는 메인 화면에 그리고 마우스 보고를 켜지 않아, 지나간 출력이 스크롤백에 쌓인다.

요구사항

"한 줄" 은 휠·트랙패드·드래그가 움직인 거리를 창의 줄 높이(칸 높이)로 나눈 것이다. 줄 높이보다 작은 움직임은 모아 두었다가 한 줄이 되면 쓴다. 위로 굴리거나 손가락을 아래로 끄는 것이 "위로" 다.

  1. R1. 휠은 창의 모드에 따라 아래 셋 중 하나만 한다. 위에 있는 것이 먼저다.
    1. 프로그램이 마우스 보고(?9·?1000·?1002·?1003)를 켰으면 → 휠 이벤트를 보낸다(R2, R3).
    2. 대체 화면이고 alternateScroll(?1007)이 켜져 있으면 → 방향키를 보낸다(R4).
    3. 그 밖에는 → 스크롤백을 움직인다(R5). 대체 화면에서는 스크롤백이 없어 아무 일도 없다.
  2. R2. 휠 이벤트는 한 줄마다 한 번 보낸다. 위는 버튼 64, 아래는 버튼 65(xterm 의 휠 버튼 4·5)이고 수정자 비트는 붙이지 않는다. 좌표는 마우스가 있는 칸(1부터 센 열·행)이다. 마우스 위치를 모르면(터치 드래그) 커서 칸이다.
  3. R3. 프로그램이 ?1006 을 켰으면 SGR 인코딩 ESC [ < 버튼 ; 열 ; 행 M, 아니면 X10 인코딩 ESC [ M 뒤에 32+버튼·32+열·32+행 세 바이트다. X10 은 한 바이트라 열·행을 223 으로 자른다.
  4. R4. 방향키는 한 줄마다 ↑ 또는 ↓ 하나다. 바이트는 키보드의 방향키와 같다 — DECCKM(?1)이 켜져 있으면 ESC O A, 아니면 ESC [ A. alternateScroll 은 처음에 켜져 있고 프로그램이 ?1007l 로 끌 수 있다.
  5. R5. 스크롤백은 터미널 R14 그대로다 — 창마다 2,000줄까지 거슬러 올라가 볼 수 있고, 키를 누르면 맨 아래로 돌아온다.
  6. R6. 휠을 셸로 보낼 때(R2, R4)는 키 입력과 같이 보던 스크롤백이 맨 아래로 돌아온다.
  7. R7. 스크롤백을 거슬러 올라가 있는 동안 스크롤백이 줄면(ESC[3J, 대체 화면 진입, 창 크기 변경) 보는 위치도 남은 스크롤백 안으로 줄어든다. 화면 위쪽이 빈 줄로 보이는 일이 없다.
  8. R8. 마우스 보고가 켜져 있어도 보내는 것은 휠뿐이다. 누르기·끌기·움직임은 보내지 않고, 누르면 지금처럼 창 포커스와 링크로, 끌면 글자 선택으로 간다.
  9. R9. 마우스 보고 모드는 켰던 것과 무관하게 ?9·?1000·?1002·?1003 중 어느 것이든 l 로 끄면 꺼진다(xterm 과 같다). ESC c(RIS)는 마우스 보고·SGR 인코딩을 끄고 alternateScroll 을 켠다.
  10. R10. Claude Code 의 전체 화면 모드("tui": "fullscreen")가 도는 Claude 탭에서 휠을 굴리면 Claude Code 의 대화 기록이 스크롤된다(R1a). 기본 모드에서는 스크롤백이 움직인다(R1c).
스코프에서 뺀 것
  • 누르기·끌기·움직임 보고(R8). Claude Code 전체 화면 모드의 마우스 글자 선택, htop·vim mouse=a 의 클릭은 되지 않는다. 휠만 지시 범위다.
  • UTF-8(?1005)·urxvt(?1015)·SGR 픽셀(?1016) 인코딩. 켜도 무시하고, 마우스 보고가 켜져 있으면 X10 이나 SGR 로 보낸다.
  • Shift+휠로 마우스 보고를 건너뛰고 스크롤백 보기(xterm·iTerm2). macOS 는 Shift+휠을 가로 스크롤로 바꿔 보내서 세로 휠로 받을 수 없다.
  • 휠 이벤트의 수정자 비트(Shift 4·Alt 8·Ctrl 16), 가로 휠(버튼 66·67).
  • 스크롤백을 거슬러 올라가 있는 동안 새 출력이 와도 보던 내용에 머물기. 지금처럼 보는 위치(맨 아래에서 센 줄 수)가 그대로라 내용이 밀린다.
  • 휠 속도 조정, ⌘↑ / ⌘↓ 스크롤(터미널 결정).

화면·동작

새 화면 요소는 없다. 창(terminal:pane:<id>) 위의 휠·드래그 동작만 바뀐다.

공통 구현

플랫폼 코드는 없다. 휠·트랙패드·드래그를 한 경로(Compose Modifier.scrollable 의 delta)로 받고, 그 다음은 전부 domain 규칙이다.

에뮬레이터
TerminalEmulator 에 mouseTracking: Boolean(?9·?1000·?1002·?1003), sgrMouse: Boolean(?1006), alternateScroll: Boolean(?1007, 처음 true)을 더한다(R1, R9)
도메인 규칙
fun encodeTerminalWheel(emulator: TerminalEmulator, lines: Int, column: Int, row: Int): ByteArray? — feature/terminal/domain/.../TerminalWheel.kt. lines 는 양수가 위, column·row 는 0부터. 셸로 보낼 바이트(R2–R4)를 돌려주고, null 이면 창이 스크롤백을 움직인다(R1c)
상태
TerminalPaneState.scrollBy(pixels, lineHeight, column, row) — 픽셀을 줄로 모으고(기존), encodeTerminalWheel 이 바이트를 주면 input 으로 보내고(R6), 아니면 scrollOffset 을 움직인다. 출력이 올 때마다 scrollOffset 을 emulator.scrollbackSize 로 묶는다(R7)
UI
TerminalPane — 기존 scrollable 의 delta 와 마우스 위치(호버에서 이미 받는 pointer)를 칸으로 바꿔 넘긴다. 위치를 모르면 커서 칸(R2)
결정: Termux 처럼 "마우스 보고 → 대체 화면이면 방향키 → 스크롤백" 순서로 고른다 xterm 은 마우스 보고가 켜져 있으면 휠을 보고하고, alternateScroll 리소스가 켜져 있으면 대체 화면에서 방향키를 보낸다. Termux(TerminalView.doScroll)·iTerm2("Scroll wheel sends arrow keys when in alternate screen mode")·VTE(GNOME Terminal)도 같은 순서다. 대체 화면에는 스크롤백이 없으므로 휠을 버리는 것보다 방향키로 바꾸는 편이 less·man·마우스를 끈 vim 에서 쓸모가 있다.
alternateScroll 의 처음 값은 켜짐으로 했다. xterm 은 꺼짐이 기본이지만 iTerm2·VTE·Termux 는 켜져 있어 macOS 사용자가 익숙한 쪽이다. 방향키가 거슬리는 프로그램은 ?1007l 로 끌 수 있다.
결정: 휠 이벤트·방향키를 한 줄마다 하나씩 보낸다 xterm 은 휠 한 칸(notch)마다 보고 하나를 보낸다. 트랙패드는 한 칸이 없고 작은 delta 가 잇따라 오는데, delta 마다 보고 하나를 보내면 손가락을 조금만 움직여도 수십 개가 가서 Claude Code 가 수십 줄씩 뛴다. 그렇다고 한 번 굴림에 하나만 보내면 트랙패드의 긴 밀기가 한 번이 된다. Termux·Ghostty 처럼 움직인 거리를 줄로 바꿔 줄 수만큼 보내면 트랙패드·휠·터치 드래그가 스크롤백을 굴릴 때와 같은 속도가 된다. 이미 있는 "줄 높이보다 작은 움직임은 모아 둔다" 경로를 그대로 쓴다.
결정: 휠만 보고하고 누르기는 창이 계속 받는다 누르기를 프로그램에 보내면 링크 열기(터미널 링크)와 창 포커스가 마우스 보고를 켠 프로그램(Claude Code 전체 화면 모드 전부)에서 막힌다. 끌기·움직임까지 보내면 Claude Code 가 마우스로 글자를 고르게 되지만, 지시 범위 밖이고 링크·포커스와의 우선순위를 따로 정해야 한다. 휠만 보내면 둘이 겹칠 일이 없다.
결정: 좌표는 호버에서 받은 마우스 위치를 쓴다 Modifier.scrollable 의 delta 에는 위치가 없다. 창은 링크 밑줄 때문에 이미 pointerInput 으로 Move·Enter·Exit 를 받아 마우스 위치(pointer)를 들고 있다. 휠을 굴리기 전에 마우스는 창 위에 들어와 있으므로 그 값이 곧 휠 위치다. 터치 드래그는 호버가 없고, 누른 자리 대신 커서 칸을 쓴다 — Claude Code 는 휠 좌표로 어느 영역을 굴릴지만 고르고, 커서는 늘 입력 칸(대화 영역 아래)에 있다.
버린 후보: 휠 이벤트를 pointerInput 에서 직접 받기(PointerEventType.Scroll) — 위치는 정확하지만 휠 delta 를 플랫폼별로 픽셀로 바꾸는 규칙(macOS 10dp 배수, 부드러운 스크롤 애니메이션)과 터치 드래그·플링을 새로 짜야 한다. scrollable 이 이미 하는 일이다.

R10 은 실제 Claude Code 가 필요해 자동으로 확인하지 못한다. 2026-09-25 에 Claude Code 2.1.282 를 전체 화면 모드로 pty(100×30)에 띄워 1–120 을 한 줄씩 찍게 한 뒤, 이 구현이 만드는 바이트(ESC[<64;50;10M 15개, 이어서 ESC[<65;50;10M 15개)를 보냈다. 가만히 있을 때는 출력이 없고, 위로 보내자 80–90번대 줄이 다시 그려지고 아래로 보내자 108–112 가 돌아왔다. 앱 창 안에서 실제 휠·트랙패드로 굴리는 것은 아직 손으로 확인하지 않았다 — ./gradlew :desktopApp:run 으로 띄워 "tui": "fullscreen" 인 Claude 탭에서 확인한다.

한계

  • 마우스 보고를 켠 프로그램에서 휠 말고는 마우스가 가지 않는다(R8). Claude Code 전체 화면 모드의 마우스 글자 선택·클릭이 되지 않는다.
  • 메인 화면에서 마우스 보고를 켠 프로그램이 돌면 휠이 그 프로그램으로 가서 Jarvis 의 스크롤백을 휠로 볼 수 없다(Shift+휠 우회가 없다).
  • macOS 에서 칸이 있는 마우스 휠 한 칸은 Compose 가 10dp × scrollAmount 로 바꾼다(JVM). 줄 높이보다 작을 수 있어, 천천히 한 칸씩 굴리면 몇 칸에 한 줄꼴로 움직인다.
  • X10 인코딩은 223 열·행을 넘는 칸을 나타낼 수 없어 가장자리 칸으로 보낸다.
