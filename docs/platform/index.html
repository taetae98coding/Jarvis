공통 스펙의 각 기능이 이 플랫폼에서 가능한지 조사하고, 어떻게 구현했거나 왜 못 했는지 기록한다. 플랫폼 하나에 문서 하나다.

플랫폼 목록

  • Android

    :androidApp + :shared. compileSdk 37, minSdk 33

  • iOS

    iosApp Xcode 프로젝트 + Shared static framework. iOS 16.0+, arm64 전용

  • JVM (Desktop)

    :desktopApp + :shared. Java 21, macOS만 지원

  • Web (Wasm)

    :webApp + :shared. Kotlin/Wasm, WasmGC 브라우저 필요

앱 모듈이 직접 의존하는 것은 :shared 하나다. 공용 코드는 그 아래 기능마다 domain · data · ui 모듈로 나뉘어 있고, 플랫폼 API를 부르는 actual은 기능의 data 모듈(과 :core:data)에 모인다. 어느 파일이 어느 모듈에 있는지는 모듈 구조에 있다.

기능 섹션 하나는 다음 소제목을 순서대로 갖는다. 비어 있는 소제목은 지우지 말고 "해당 없음"이라고 적는다. 다음 사람이 조사를 안 한 것인지 조사했는데 없는 것인지 구분할 수 있어야 한다.

  1. 기술 조사 — 이 플랫폼이 제공하는 API, 그 API의 전제 조건과 제약. Compose Multiplatform이 대신 부르는 것이 있으면 그것도 적는다.
  2. 판정 — 범례의 다섯 가지 중 하나.
  3. 구현 또는 우회 — 무엇을 어떻게 했는지. 우회라면 무엇이 막혔고 어디로 돌아갔는지. 불가라면 어떤 대체 동작을 하는지.
  4. 한계 — 이 구현이 동작하지 않는 조건과 그때의 증상.
  5. 검증 — 어떤 테스트가 이 플랫폼에서 이 기능을 확인하는지. 없으면 왜 없는지.

판정 기준

판정은 "지금 코드가 어떻게 되어 있나"가 아니라 "요구사항을 이 플랫폼에서 충족하는가"에 대한 답이다.

  • 정식 API로 요구사항을 그대로 채웠으면 구현. Compose가 대신 불러 주는 경우도 여기 든다.
  • 정식 경로가 없거나 비어 있어 다른 길로 갔으면 우회. JVM의 caffeinate 자식 프로세스, SDK 도구 폴링이 그렇다.
  • 구현은 했지만 실행 환경이 조건을 만족해야 동작하면 조건부. Web의 Screen Wake Lock이 그렇다.
  • 플랫폼이 원리적으로 막고 있어 구현하지 않았으면 불가. 반드시 대체 동작을 적는다.
  • 구현했지만 자동 테스트가 없으면 판정 옆에 미검증을 덧붙인다.
