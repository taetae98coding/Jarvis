모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
모듈마다 wasmJs { browser() }필수다. browser()를 빠뜨린 모듈은 wasmJs 타깃의 테스트·번들 설정이 없어 의존하는 쪽에서 링크가 깨진다. 컨벤션 플러그인이 선언하므로 모듈을 추가할 때 빠뜨릴 수 없다
binaries.executable()Compose 를 쓰는 모듈(:core:ui, 기능의 ui 다섯, :app:ui, :shared)에 컨벤션 플러그인이 넣는다. 실행 바이너리가 없으면 webpack 번들에 Skiko 런타임이 들어가지 않아 브라우저 UI 테스트가 렌더링하지 못하고, Compose 플러그인의 checkComposeUiTestConfigurationForWasmJs가 테스트가 없는 모듈에도 예외 없이 요구한다(CMP-4906). domain·data 모듈은 Compose 를 쓰지 않아 검사 대상이 아니다
번들 개수하나다. :webApp의 outputModuleName = "webApp"이 의존 klib 열여섯 개를 한 webApp.js로 묶는다. 기능을 나눠도 브라우저가 받는 파일 수는 그대로다
kotlinx.browser(window, localStorage, fetch)기능의 data 모듈 wasmJsMain에서만 쓴다. ui 모듈은 브라우저 API를 직접 부르지 않고 Compose의 Modifier.keepScreenOn()만 쓴다
Wasm 코드 분할(기능별 지연 로딩)버렸다. Kotlin/Wasm에는 아직 klib 단위 코드 분할이 없다. 기능 분리는 소스 구조에만 영향을 주고 번들 크기·로딩 방식은 바뀌지 않는다

구현

파일
shared/src/wasmJsMain/.../JarvisKoin.wasmJs.kt, core/data/src/wasmJsMain/.../PlatformContext.wasmJs.kt
동작
브라우저에는 넘길 플랫폼 핸들이 없어 PlatformContext는 빈 클래스다. main()은 startJarvisKoin() 후 ComposeViewport(document.body!!) { App() }
실패
해당 없음

한계

  • 번들이 하나라 기능 하나만 고쳐도 브라우저는 전체를 다시 받는다. 기능 분리 전과 같다.
  • Compose 라이브러리 모듈에 binaries.executable()을 두는 것은 테스트와 플러그인 검사를 위한 설정이다. 라이브러리에 실행 바이너리를 두는 것이 어색하고, 쓰지도 않는 webpack 번들을 모듈마다 하나씩 만든다. CMP-4906이 닫히면 걷어낸다.
  • 기능 분리 후 :app:ui의 wasmJs 테스트 실행 바이너리 컴파일이 Kotlin 컴파일러 힙 3G 에서 OutOfMemoryError: GC overhead limit exceeded 로 죽었다. 링크되는 klib 수가 늘어난 탓이고, kotlin.daemon.jvmargs 를 6G 로 올려 해결했다. 모듈이 더 늘면 다시 조정해야 한다.

검증

./gradlew :app:ui:wasmJsBrowserTest가 브라우저에서 화면을 렌더링해 확인한다(33개). 기능 모듈의 wasmJsBrowserTest는 화면 없이 도메인·데이터 테스트만 돈다.

화면 상태 소유 (ViewModel) 구현

공통 스펙: 화면 상태 소유 (ViewModel)

기술 조사

후보결과
Compose Multiplatform 의 기본 owner채택. skiko compose-ui의 findComposeDefaultViewModelStoreOwner()를 ComposeViewport 컴포지션이 제공한다
lifecycle-viewmodel-compose의 wasmJs 아티팩트org.jetbrains.androidx.lifecycle 2.11.0 이 wasm-js 변형을 퍼블리시한다
Dispatchers.setMain으로 ViewModel 단위 테스트쓸 수 없다. Wasm 의 메인 디스패처를 테스트에서 갈아끼울 수 없어 viewModelScope를 제어할 수 없다. 그래서 ViewModel 상태 테스트는 JVM에만 두고, Wasm 에서는 화면 테스트로 확인한다

구현

파일
공용이다. Web 전용 코드는 없다
동작
탭이 살아 있는 동안 앱 수명 ViewModel 이 살아 있다. 화면 수명 ViewModel 은 엔트리가 빠질 때 정리된다
실패
없다

한계

  • 탭을 닫거나 새로 고치면 프로세스째로 사라진다. onCleared()가 불릴 보장이 없고, 그래서 정리 코드에 기대는 동작을 두지 않는다.
  • 단일 스레드라 viewModelScope에서 무거운 일을 하면 화면이 멈춘다. 프레임 디코딩을 별도 디스패처로 보내지 않는 이유와 같은 제약이다(기기 화면).

검증

:app:ui의 wasmJsBrowserTest에서 JarvisAppTest가 돈다.

화면 이동 (Navigation3) 조건부

공통 스펙: 화면 이동 (Navigation3)

기술 조사

후보결과
NavDisplay(JetBrains navigation3-ui의 wasm-js 변형)채택. 앱 안의 뒤로 아이콘 버튼로 백스택을 줄인다
브라우저 뒤로 버튼연결되지 않는다. 브라우저 뒤로는 history 항목을 되돌리는 것이고, 우리 백스택은 그 히스토리에 아무 항목도 넣지 않았다. 지금 누르면 앱 화면이 아니라 페이지를 벗어난다
window.history.pushState + popstate 브리지후보로 남긴다. 화면을 옮길 때 pushState로 항목을 쌓고 popstate에서 백스택을 줄이면 브라우저 뒤로가 앱 뒤로가 된다. kotlinx-browser로 가능하다. 두 스택을 동기화하는 규칙(중복 push, 새로고침 후 복원)이 새 스펙 하나만큼 되어 이번 스코프에서 뺐다
해시 라우팅(#/devices)버렸다. URL 이 앱 상태를 나르게 되면 딥링크 스펙이 먼저 필요하다
백스택 저장·복원저장은 되지만 새로고침을 넘지 못한다. 컴포지션 저장 상태가 sessionStorage 같은 곳으로 나가지 않는다

대체 동작

파일
공용이다. Web 전용 코드는 없다
동작
앱 안의 뒤로 아이콘 버튼이 유일한 뒤로 경로다
실패
브라우저 뒤로를 누르면 앱을 벗어난다. 이전 페이지가 없으면 아무 일도 일어나지 않는다

한계

  • 브라우저 뒤로 버튼이 앱 화면을 되돌리지 않는다. 사용자가 기기 화면에서 뒤로를 누르면 앱이 사라진다.
  • 새로고침하면 항상 홈에서 시작한다.

검증

:app:ui의 wasmJsBrowserTest가 앱 안의 이동 경로를 본다. 브라우저 뒤로는 테스트하지 않는다(연결하지 않은 동작이다).

재생성을 넘기는 상태 (retain) 조건부

공통 스펙: 재생성을 넘기는 상태 (retain)

기술 조사

후보결과
retain + 플랫폼이 제공하는 RetainedValuesStore저장소가 없다. runtime-retain의 wasm-js 변형은 퍼블리시되지만 skiko compose-ui에 보관 구현이 없다. 기본값 ForgetfulRetainedValuesStore가 쓰인다
재생성 경로 자체없다. 창 크기 변경은 컴포지션을 다시 만들지 않고, 새로고침은 프로세스를 끝낸다. retain이 개입할 구간이 없다
sessionStorage에 프레임 보관버렸다. 그것은 retain이 아니라 직렬화다. 마지막 프레임을 저장해 둘 이유도 없다 — 새로고침 후 0.5초 안에 새 프레임이 온다(에이전트가 살아 있다면)

대체 동작

파일
공용이다. Web 전용 코드는 없다
동작
retain은 remember와 같게 동작한다
실패
없다

한계

  • 보관이 일어나지 않으므로 이 플랫폼에서 retain과 remember의 차이를 관찰할 수 없다.

검증

앱 정보 우회

공통 스펙: 앱 정보 카드

기술 조사

브라우저·OS 정보는 navigator.userAgent로 얻을 수 있지만 문자열 파싱이 필요하고 브라우저마다 다르다. Kotlin/Wasm 자체를 나타내는 정보는 런타임에 없다.

기기 이름·식별자(공통 R5·R6) 후보. 브라우저는 추적을 막으려고 기기 식별자를 일부러 주지 않는다. 그래서 식별자는 앱이 스스로 만들어 보관하는 우회다.

후보결과
navigator.platform채택(이름). MacIntel·Win32·Linux x86_64·iPhone. 표준에서 "레거시" 로 표시됐지만 모든 브라우저가 계속 준다. Apple Silicon 에서도 MacIntel 이다
navigator.userAgentData.platform버림. Chromium 계열만 있다(Safari·Firefox 는 undefined)
navigator.userAgent버림. 카드 한 줄에 넣기에는 길고, 브라우저가 값을 얼리고 있다(UA reduction)
기기 식별자 API없음. navigator.deviceMemory·hardwareConcurrency 같은 값은 기기를 가리지 못한다
처음 열 때 만든 UUID 를 localStorage 에 보관채택(식별자, 우회). kotlin.uuid.Uuid.random()(브라우저의 crypto.getRandomValues)으로 만들고 jarvis.deviceId 키에 둔다. 같은 오리진의 같은 브라우저 프로필에서 같은 값이다

우회

actual val platformName: String = "Wasm (Kotlin/Wasm)"

actual fun readDeviceIdentity(context: PlatformContext): DeviceIdentity =
    DeviceIdentity(
        name = window.navigator.platform,
        id = localStorage.getItem(DeviceIdKey)
            ?: Uuid.random().toString().also { localStorage.setItem(DeviceIdKey, it) },
    )

플랫폼 이름은 고정 문자열이다. 브라우저 종류나 OS는 넣지 않는다. 기기 이름은 navigator.platform, 식별자는 처음 열 때 만든 UUID 다(feature/appinfo/data/src/wasmJsMain/.../DeviceIdentity.wasmJs.kt). localStorage 를 쓸 수 없으면(사생활 보호 모드의 일부 브라우저) 매번 새 UUID 다.

한계

  • 브라우저를 구분해야 하면 navigator.userAgent를 붙여야 한다.
  • 식별자는 기기가 아니라 브라우저 프로필과 오리진에 묶인다. 저장소를 지우거나 다른 브라우저로 열면 새 값이다. 다른 타깃과 달리 밖에서 이 값으로 기기를 찾을 길이 없다.

검증

PlatformNameTest, DeviceIdentityTest, JarvisAppTest.showsAppVersion, JarvisAppTest.showsCurrentPlatformName, JarvisAppTest.showsDeviceNameAndId, JarvisAppTest.hidesBlankDeviceRows 가 wasmJsBrowserTest에서 돈다.

앱 업데이트 불가

공통 스펙: 앱 업데이트

기술 조사

테스트 구현

CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  ./gradlew wasmJsBrowserTest

유스케이스 테스트(기능의 domain), PlatformNameTest·ScreenAwakeSettingsRepositoryTest·HostAgentTest(기능의 data), ObserveSystemStateTest(:core:data), JarvisAppTest(:app:ui, Compose UI)가 헤드리스 Chrome에서 돈다. CHROME_BIN을 지정하지 않으면 Karma가 브라우저를 찾지 못한다.

UI 테스트에서 waitUntil 로 Flow 전파를 기다리지 않는다 스레드가 하나뿐이라 waitUntil 의 폴링 루프가 이벤트 루프를 잡고 있으면, 그동안 stateIn 같은 중간 단계를 거치는 Flow 가 화면까지 전파되지 못한다. 가짜 저장소의 값을 바꾸고 그 결과가 목록에 나타나기를 waitUntil 로 기다리는 테스트가 세 번에 한 번꼴로 10초 타임아웃에 걸렸다. 그런 규칙은 화면을 그리지 않는 EmulatorDevicesViewModelTest(JVM)에서 runTest 로 확인한다. 프레임 디코딩에 같은 제약이 걸리는 이야기는 기기 목록·화면·제스처에 있다.
결정: :app:ui 의 Wasm 테스트도 Dispatchers.Main 을 Unconfined 로 둔다 위 제약 때문에 0440c28 까지 :app:ui:wasmJsBrowserTest 가 실패하고 있었다. JarvisAppTerminalClaudeStatusTest 에서 창 포커스를 바꾸면 setWindowFocused 는 불렸지만 viewModelScope 의 combine 이 다시 돌지 않았다(임시 로그로 확인) — Main 이 곧 막힌 이벤트 루프라서다. 앞 테스트가 끝나지 못하면 Karma 가 나머지를 돌리지 않아 172개 중 수십 개만 돌고 있었다. JVM 처럼 installTestMainDispatcher() 가 Dispatchers.setMain(Dispatchers.Unconfined) 을 하자 이벤트 루프를 기다리지 않고 그 자리에서 이어져 172개가 끝까지 돈다. 남는 제약은 실제 시간 타이머(delay, withTimeout)다 — 이벤트 루프가 막혀 끝나지 못하므로, 그것을 기다리는 줄 코멘트 보내기 테스트 둘에만 @IgnoreOnWasm(Wasm 에서만 kotlin.test.Ignore)을 붙였다. 패널 줄 흐르기 테스트는 한글 폰트가 없는 Wasm 에서 한글 폭이 작게 재져 실패해서, 폭을 라틴 글자로 채웠다(release 빌드의 한글 폰트와 같은 원인).
결정: Karma·mocha 제한 시간을 늘리고, 터미널 UI 테스트 일곱은 Wasm 에서 건너뛴다 (2026-09-25) 테스트가 220개를 넘기자 :app:ui:wasmJsBrowserTest 가 다시 수십 개째에서 Disconnected … reconnect failed before timeout of 2000ms (ping timeout) 로 끊겼다. 앱 전체를 띄우는 테스트 하나가 이벤트 루프를 2초 넘게 잡으면 Karma(browserDisconnectTimeout)와 mocha(테스트마다)의 기본 2초에 걸린다. app/ui/karma.config.d/timeouts.js 가 둘을 늘리자 221개가 끝까지 돈다. 끝까지 돌자 결정적으로 실패하는 일곱이 드러났다. 모두 이벤트 루프가 막힌 동안 끝나야 하는 일을 기다린다. 파일 탭 자동 저장 둘은 delay(FileAutoSaveDelay) 를, 마크다운 미리보기를 여는 둘(markdownOpensAsAPreview…, 사이드 바의 clickingAFileOpens…)은 withContext(Dispatchers.Default) 의 파싱·색칠을 기다린다(Wasm 에서는 Default 도 같은 이벤트 루프다). 휠 셋은 휠 입력이 scrollBy 에 닿기를 기다리다 10초·waitForIdle 1분 제한에 걸린다. 휠 쪽의 정확한 원인은 미검증이다. 웹에서는 터미널 자체가 불가라 이 화면들이 뜨지 않으므로 앱 코드를 Wasm 에 맞춰 바꾸지 않고 @IgnoreOnWasm 을 붙였다. 같은 테스트는 JVM·iOS 에서 돈다.

Compose 를 쓰는 모듈의 wasmJs 타깃에 binaries.executable()이 있는 이유도 이 테스트 때문이다. 실행 바이너리가 없으면 webpack 번들에 Skiko 런타임이 들어가지 않아 UI 테스트가 렌더링하지 못한다.
