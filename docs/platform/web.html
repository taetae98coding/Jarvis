모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
모듈마다 wasmJs { browser() }필수다. browser()를 빠뜨린 모듈은 wasmJs 타깃의 테스트·번들 설정이 없어 의존하는 쪽에서 링크가 깨진다. 컨벤션 플러그인이 선언하므로 모듈을 추가할 때 빠뜨릴 수 없다
binaries.executable()Compose 를 쓰는 모듈(:core:ui, 기능의 ui 다섯, :app:ui, :shared)에 컨벤션 플러그인이 넣는다. 실행 바이너리가 없으면 webpack 번들에 Skiko 런타임이 들어가지 않아 브라우저 UI 테스트가 렌더링하지 못하고, Compose 플러그인의 checkComposeUiTestConfigurationForWasmJs가 테스트가 없는 모듈에도 예외 없이 요구한다(CMP-4906). domain·data 모듈은 Compose 를 쓰지 않아 검사 대상이 아니다
번들 개수하나다. :webApp의 outputModuleName = "webApp"이 의존 klib 열여섯 개를 한 webApp.js로 묶는다. 기능을 나눠도 브라우저가 받는 파일 수는 그대로다
kotlinx.browser(window, localStorage, fetch)기능의 data 모듈 wasmJsMain에서만 쓴다. ui 모듈은 브라우저 API를 직접 부르지 않고 Compose의 Modifier.keepScreenOn()만 쓴다
Wasm 코드 분할(기능별 지연 로딩)버렸다. Kotlin/Wasm에는 아직 klib 단위 코드 분할이 없다. 기능 분리는 소스 구조에만 영향을 주고 번들 크기·로딩 방식은 바뀌지 않는다

구현

파일
shared/src/wasmJsMain/.../JarvisKoin.wasmJs.kt, core/data/src/wasmJsMain/.../PlatformContext.wasmJs.kt
동작
브라우저에는 넘길 플랫폼 핸들이 없어 PlatformContext는 빈 클래스다. main()은 startJarvisKoin() 후 ComposeViewport(document.body!!) { App() }
실패
해당 없음

한계

  • 번들이 하나라 기능 하나만 고쳐도 브라우저는 전체를 다시 받는다. 기능 분리 전과 같다.
  • Compose 라이브러리 모듈에 binaries.executable()을 두는 것은 테스트와 플러그인 검사를 위한 설정이다. 라이브러리에 실행 바이너리를 두는 것이 어색하고, 쓰지도 않는 webpack 번들을 모듈마다 하나씩 만든다. CMP-4906이 닫히면 걷어낸다.
  • 기능 분리 후 :app:ui의 wasmJs 테스트 실행 바이너리 컴파일이 Kotlin 컴파일러 힙 3G 에서 OutOfMemoryError: GC overhead limit exceeded 로 죽었다. 링크되는 klib 수가 늘어난 탓이고, kotlin.daemon.jvmargs 를 6G 로 올려 해결했다. 모듈이 더 늘면 다시 조정해야 한다.

검증

./gradlew :app:ui:wasmJsBrowserTest가 브라우저에서 화면을 렌더링해 확인한다(33개). 기능 모듈의 wasmJsBrowserTest는 화면 없이 도메인·데이터 테스트만 돈다.

화면 상태 소유 (ViewModel) 구현

공통 스펙: 화면 상태 소유 (ViewModel)

기술 조사

후보결과
Compose Multiplatform 의 기본 owner채택. skiko compose-ui의 findComposeDefaultViewModelStoreOwner()를 ComposeViewport 컴포지션이 제공한다
lifecycle-viewmodel-compose의 wasmJs 아티팩트org.jetbrains.androidx.lifecycle 2.11.0 이 wasm-js 변형을 퍼블리시한다
Dispatchers.setMain으로 ViewModel 단위 테스트쓸 수 없다. Wasm 의 메인 디스패처를 테스트에서 갈아끼울 수 없어 viewModelScope를 제어할 수 없다. 그래서 ViewModel 상태 테스트는 JVM에만 두고, Wasm 에서는 화면 테스트로 확인한다

구현

파일
공용이다. Web 전용 코드는 없다
동작
탭이 살아 있는 동안 앱 수명 ViewModel 이 살아 있다. 화면 수명 ViewModel 은 엔트리가 빠질 때 정리된다
실패
없다

한계

  • 탭을 닫거나 새로 고치면 프로세스째로 사라진다. onCleared()가 불릴 보장이 없고, 그래서 정리 코드에 기대는 동작을 두지 않는다.
  • 단일 스레드라 viewModelScope에서 무거운 일을 하면 화면이 멈춘다. 프레임 디코딩을 별도 디스패처로 보내지 않는 이유와 같은 제약이다(기기 화면).

검증

:app:ui의 wasmJsBrowserTest에서 JarvisAppTest가 돈다.

화면 이동 (Navigation3) 조건부

공통 스펙: 화면 이동 (Navigation3)

기술 조사

후보결과
NavDisplay(JetBrains navigation3-ui의 wasm-js 변형)채택. 앱 안의 뒤로 아이콘 버튼로 백스택을 줄인다
브라우저 뒤로 버튼연결되지 않는다. 브라우저 뒤로는 history 항목을 되돌리는 것이고, 우리 백스택은 그 히스토리에 아무 항목도 넣지 않았다. 지금 누르면 앱 화면이 아니라 페이지를 벗어난다
window.history.pushState + popstate 브리지후보로 남긴다. 화면을 옮길 때 pushState로 항목을 쌓고 popstate에서 백스택을 줄이면 브라우저 뒤로가 앱 뒤로가 된다. kotlinx-browser로 가능하다. 두 스택을 동기화하는 규칙(중복 push, 새로고침 후 복원)이 새 스펙 하나만큼 되어 이번 스코프에서 뺐다
해시 라우팅(#/devices)버렸다. URL 이 앱 상태를 나르게 되면 딥링크 스펙이 먼저 필요하다
백스택 저장·복원저장은 되지만 새로고침을 넘지 못한다. 컴포지션 저장 상태가 sessionStorage 같은 곳으로 나가지 않는다

대체 동작

파일
공용이다. Web 전용 코드는 없다
동작
앱 안의 뒤로 아이콘 버튼이 유일한 뒤로 경로다
실패
브라우저 뒤로를 누르면 앱을 벗어난다. 이전 페이지가 없으면 아무 일도 일어나지 않는다

한계

  • 브라우저 뒤로 버튼이 앱 화면을 되돌리지 않는다. 사용자가 기기 화면에서 뒤로를 누르면 앱이 사라진다.
  • 새로고침하면 항상 홈에서 시작한다.

검증

:app:ui의 wasmJsBrowserTest가 앱 안의 이동 경로를 본다. 브라우저 뒤로는 테스트하지 않는다(연결하지 않은 동작이다).

재생성을 넘기는 상태 (retain) 조건부

공통 스펙: 재생성을 넘기는 상태 (retain)

기술 조사

후보결과
retain + 플랫폼이 제공하는 RetainedValuesStore저장소가 없다. runtime-retain의 wasm-js 변형은 퍼블리시되지만 skiko compose-ui에 보관 구현이 없다. 기본값 ForgetfulRetainedValuesStore가 쓰인다
재생성 경로 자체없다. 창 크기 변경은 컴포지션을 다시 만들지 않고, 새로고침은 프로세스를 끝낸다. retain이 개입할 구간이 없다
sessionStorage에 프레임 보관버렸다. 그것은 retain이 아니라 직렬화다. 마지막 프레임을 저장해 둘 이유도 없다 — 새로고침 후 0.5초 안에 새 프레임이 온다(에이전트가 살아 있다면)

대체 동작

파일
공용이다. Web 전용 코드는 없다
동작
retain은 remember와 같게 동작한다
실패
없다

한계

  • 보관이 일어나지 않으므로 이 플랫폼에서 retain과 remember의 차이를 관찰할 수 없다.

검증

화면 꺼짐 방지 조건부

공통 스펙: 화면 꺼짐 방지

기술 조사

후보결과
Screen Wake Lock API (navigator.wakeLock.request('screen'))유일한 정식 API. 보안 컨텍스트(HTTPS 또는 localhost) 필수. Chrome/Edge 84+, Safari 16.4+, Firefox 126+. 해제하려면 request가 돌려준 WakeLockSentinel이 그대로 필요하고, 탭이 숨겨지면 브라우저가 lock을 회수한다
보이지 않는 <video> 반복 재생구형 우회. 자동 재생 정책에 막히고 배터리를 쓴다. 제외
Compose Modifier.keepScreenOn()CMP 1.12.1 Web 구현의 WakeLockManager가 sentinel 보관과 visibilitychange 재요청을 내부에서 처리한다

구현

공통 코드의 Modifier.keepScreenAwake(enabled)가 Compose의 keepScreenOn()을 붙인다. Web 전용 코드는 없다. :feature:screen:data의 createIdleInhibitor()는 wasmJs에서 NoIdleInhibitor를 돌려준다.

예전에는 @JsFun 브릿지로 sentinel과 visibilitychange 리스너를 globalThis 전역 세 개에 들고 있었다. Compose 구현으로 넘기면서 전부 걷어냈고, 컴포지션보다 오래 살던 리스너도 함께 사라졌다.

한계

  • 보안 컨텍스트 필요. HTTP로 서빙하면 navigator.wakeLock이 존재하지 않아 토글이 no-op이 된다.
  • 브라우저 지원 필요. 미지원 브라우저에서는 조용히 아무 일도 일어나지 않는다.
  • 실패가 드러나지 않는다. 배터리 절약 모드처럼 브라우저가 wake lock을 거부해도 UI는 켜진 상태로 보인다.
  • 탭을 닫으면 끝. 다른 플랫폼과 마찬가지로 페이지가 살아 있는 동안만 유효하다.

검증

JarvisAppTest의 토글·저장 테스트 4개가 헤드리스 Chrome에서 돈다. wake lock이 실제로 잡히는지는 미검증이다. 헤드리스 환경에서는 보안 컨텍스트 조건을 만족해도 화면이 없다.

화면 꺼짐 방지 (시스템 전역) 불가

공통 스펙: 화면 꺼짐 방지 (시스템 전역)

기술 조사

후보결과
Screen Wake Lock API페이지가 살아 있는 동안만 유효하고, 탭이 숨겨지면 브라우저가 회수한다. 앱 수명 내 기능이 이미 쓰고 있다
OS 전원 설정 API없다. 브라우저는 OS의 자동 잠금·디스플레이 슬립 설정에 닿는 API를 웹에 노출하지 않는다
Service Worker탭이 없어도 코드를 돌릴 수 있지만 화면 전원과는 무관하다. wake lock은 문서(document)가 있어야 요청할 수 있다
확장 프로그램 + Native Messaging호스트 프로그램을 통해 OS 설정을 바꿀 수는 있다. 다만 웹앱이 아니라 확장 프로그램을 따로 배포해야 해서 이 앱의 범위 밖이다

대체 동작

internal actual fun createSystemScreenAwakeDataSource(
    context: PlatformContext,
): SystemScreenAwakeDataSource = UnsupportedSystemScreenAwakeDataSource

카드는 같은 자리에 남고 잠긴 상태로 이유를 보여준다.

한계

해당 없음. 기능 자체가 없다.

검증

JarvisAppTest.systemScreenAwakeIsLockedWhereItIsNotSupported와 systemScreenAwakeExplainsWhyItIsUnavailable이 wasmJsBrowserTest에서 잠긴 카드와 설명을 검증한다.

변경 감지
merge(localChanges, remoteChanges). remoteChanges는 window의 storage 이벤트, localChanges는 putBoolean이 직접 tryEmit하는 MutableSharedFlow
자체 쓰기는 직접 신호를 낸다 storage 이벤트는 같은 오리진의 다른 문서가 쓴 변경에만 발생한다. 이 문서 자신이 쓴 변경은 이벤트가 없어서, putBoolean에서 localChanges로 직접 신호를 낸다. 이 줄을 지우면 토글을 눌러도 화면이 바뀌지 않는다.

한계

  • 오리진 단위다. 같은 오리진의 다른 페이지가 값을 읽거나 덮어쓸 수 있다.
  • 시크릿 모드나 저장소 차단 설정에서는 접근이 예외를 던질 수 있다. 지금은 잡지 않는다.
  • 문자열이 "true"/"false"가 아니면 기본값으로 돌아간다.

검증

ScreenAwakeSettingsRepositoryTest와 JarvisAppTest의 저장 테스트가 InMemorySettingsStore로 돈다. localStorage 왕복은 미검증이다.

에뮬레이터 개수 조건부

공통 스펙: 에뮬레이터 개수

기술 조사

  • 브라우저 샌드박스에는 파일 시스템 접근도 프로세스 실행도 없다. File System Access API는 사용자가 고른 디렉터리만 열어 주고, 실행은 어떤 경우에도 불가하다.
  • 호스트의 SDK를 읽으려면 짝이 되는 로컬 서버가 필요하다. 데스크톱 앱이 띄우는 로컬 에이전트가 그 서버다.
  • localhost는 페이지를 띄운 머신이다. 개발 서버와 에이전트가 같은 머신에 있으면 그게 곧 개발자 머신이다.
  • 포트가 달라 교차 출처가 된다. 단순 GET이라 preflight는 없고, 에이전트의 Access-Control-Allow-Origin: * 하나로 응답을 읽을 수 있다.

우회

파일
feature/emulator/data/src/wasmJsMain/.../emulator/agent/HostAgent.wasmJs.kt
동작

타입 인자
await의 타입 인자를 적어 준다. Promise가 out 변성이어서 반환 타입만으로는 추론되지 않는다

  • 데스크톱 앱이 떠 있어야 한다. 꺼져 있으면 "셀 수 없음"이다.

화면 회전 조건부 미검증

공통 스펙: 화면 회전

기술 조사

후보결과
screen.orientation.lock(type) / unlock()채택. 잠금과 회전이 한 호출이다. 인자는 각도가 아니라 portrait-primary 같은 이름이고, Promise를 돌려준다. 실패는 예외가 아니라 거절로 온다
screen.orientation.angle / .type, change 이벤트채택(관찰). angle이 공통 각도 기준과 그대로 같다. 콜백이 있으므로 폴링하지 않는다(상태 조회 규칙)
전체화면 없이 lock()브라우저마다 다르다. Chrome/Android는 문서가 전체화면일 때만 허용하고 아니면 NotSupportedError로 거절한다. 데스크톱 브라우저는 전체화면이어도 거절한다. iOS Safari는 API 자체가 없다
잠글 때 자동으로 requestFullscreen()버렸다. 성공률은 오르지만 버튼 하나가 화면 전체를 덮어 버린다. 사용자가 요청하지 않은 모드 전환이라 카드 하나의 권한을 넘는다. 대신 거절당하면 그 사실을 설명에 적는다
kotlinx-browser의 Screen0.5.0의 org.w3c.dom.Screen에는 orientation이 없다. external interface와 js("…")로 직접 잡는다. 설정 저장이 localStorage를 쓰는 것과 같은 모듈 안이지만 선언은 이 파일에서만 쓴다
CSS transform: rotate() 로 캔버스를 돌리기버렸다. JVM의 창 변환과 같은 이유다. 브라우저 UI와 입력 좌표가 따라오지 않는다

구현

파일
feature/rotation/data/src/wasmJsMain/.../rotation/DeviceRotation.wasmJs.kt
잠금
현재 각도의 방향 이름으로 lock(), 해제는 unlock()
각도
목표 각도를 방향 이름으로 바꿔 lock(). natural이 세로인지는 지금의 type과 angle 조합에서 역산한다(세로 이름인데 각도가 90·270이면 natural은 가로다)
읽기
screen.orientation.angle. screen.orientation이 없으면 supported = false
실패
lock()의 Promise가 거절되면 permitted = false로 흘려 카드 설명을 바꾼다. 거절 사유(전체화면 필요, 데스크톱 미지원)는 브라우저마다 달라 그대로 옮기지 않는다

권한이라는 말은 여기서 브라우저 정책을 가리킨다. Android의 WRITE_SETTINGS처럼 사용자가 허용할 대상이 아니라서, 카드는 권한 화면을 여는 대신 왜 거절됐는지만 보여준다(requestPermission()이 no-op이다).

한계

  • 데스크톱 브라우저에서는 거의 항상 거절된다. 카드는 현재 각도(대개 0°)를 보여주고, 버튼을 누르면 설명이 "브라우저가 회전 고정을 거부했습니다"로 바뀐다.
  • iOS Safari에는 API가 없다. screen.orientation은 있어도 lock이 없어 supported = false로 떨어진다.
  • 전체화면을 벗어나면 잠금이 풀린다. 브라우저가 자동으로 해제하고, change 이벤트로 그 사실이 카드에 반영된다.
  • natural이 가로인 기기에서 각도와 이름의 대응이 어긋날 수 있다. lock()이 각도를 받지 않아서 생기는 한계다. 역산이 틀리면 90°와 270°가 뒤바뀐다.
  • 돌아가는 것은 브라우저 문서(탭)지 기기가 아니다. OS 회전잠금은 그대로다.

검증

자동 테스트가 없다. wasmJsTest는 헤드리스 Chrome에서 도는데 데스크톱 브라우저라 lock()이 거절되고, 돌아갈 화면도 없다. 규칙과 카드 표시는 :feature:rotation:domain·:app:ui 테스트가 검증한다(:app:ui의 wasmJsBrowserTest도 그 중 하나다). 실제 회전은 안드로이드 크롬에서 전체화면으로 열어 수동 확인한다.

fetch GET·POST, 본문은 문자열채택. 본문이 문자열이면 text/plain 단순 요청이라 CORS 사전 요청이 붙지 않는다. 페어링은 응답 본문을 읽는다. fetch 에는 기본 타임아웃이 없어서 에이전트가 끝낼 때까지 기다린다

우회

파일
feature/emulator/data/src/wasmJsMain/.../emulator/agent/HostAgent.wasmJs.kt, .../emulator/DevicePairing.wasmJs.kt
동작
GET http://localhost:47890/emulators/pairing/services, POST …/pairing/pair
실패
fetch 가 거절되면 목록은 찾을 수 없음, 페어링은 개발자 머신의 에이전트에 닿지 못했습니다.

한계

  • 페이지를 띄운 머신에 데스크톱 앱이 떠 있어야 한다.
  • HTTPS 로 연 페이지에서는 막힌다. 혼합 콘텐츠 차단이다. 에뮬레이터 개수와 같은 조건이다.

검증

HostAgentTest 의 pairing 테스트가 wasmJsBrowserTest 에서 경로·본문·결과 해석을 확인한다. 실제 fetch 왕복은 미검증이다.

디자인 시스템 구현

공통 스펙: 디자인 시스템

기술 조사

후보결과
isSystemInDarkTheme()채택. skiko 공통 구현이 LocalSystemTheme 을 읽고, Web 의 ComposeWindow 가 SystemThemeObserver 로 window.matchMedia("(prefers-color-scheme: dark)") 의 change 이벤트를 받아 갱신한다
벡터·Style 렌더링Skiko(WebGL 캔버스) 가 Skia Path 로 그린다. CSS 와 무관하다. 플랫폼 코드는 없다
Style API(androidx.compose.foundation.style)채택. Compose Multiplatform foundation 1.12.1 의 commonMain 에 있어 이 타깃에도 같은 코드가 퍼블리시된다. 실험 API 라 컨벤션 플러그인이 opt-in 을 켠다
addPathNodes + ImageVector.Builder채택. ui-graphics commonMain 이라 플랫폼 차이가 없다

구현

파일
core/designsystem/src/commonMain/.../designsystem/ — 이 플랫폼 전용 파일은 없다
동작
시스템이 다크 모드면 다크 색 두 벌을 공급하고, 설정이 바뀌면 다시 그린다
실패
해당 없음. 다크 모드를 읽지 못하는 경로는 라이트로 떨어진다

한계

  • 페이지 배경(body)은 CSS 이고 Compose 캔버스가 덮는다. 캔버스가 그려지기 전 잠깐은 브라우저 기본 흰 배경이다.

검증

:core:designsystem:wasmJsBrowserTest 가 테마·Style·아이콘 테스트를 돌린다. 다크 모드 전환은 미검증이라 개발자 도구의 Rendering → prefers-color-scheme 에뮬레이션으로 본다.

빌드·실행

./gradlew :webApp:wasmJsBrowserDevelopmentRun   # http://localhost:8080
./gradlew :webApp:wasmJsBrowserDistribution     # 배포 번들

에뮬레이터 개수를 보려면 데스크톱 앱을 함께 띄워 둬야 한다. 개발 서버가 HTTP라 에이전트 요청이 mixed content로 막히지 않는다.

한계

  • Kotlin/Wasm은 WasmGC를 지원하는 브라우저가 필요하다 (Chrome/Edge 119+, Firefox 120+, Safari 18.2+).
  • Skiko wasm이 8 MB를 넘어 첫 로딩이 무겁다. 캐시 헤더를 신경 써야 한다.
  • 렌더링이 canvas라 브라우저 텍스트 선택·검색·접근성 트리가 DOM 앱과 다르게 동작한다.

기기 목록 좌우 분할 구현

한계

  • 좁은 창에서는 열 하나가 좁아 이름이 여러 줄로 접힌다.

검증

JarvisAppTest 가 wasmJsTest(skikoTest) 에서 열 분리와 빈 열 문구를 확인한다. 너비와 휠 스크롤은 미검증이고 브라우저에서 수동 확인한다.

테스트 구현

CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  ./gradlew wasmJsBrowserTest

유스케이스 테스트(기능의 domain), PlatformNameTest·ScreenAwakeSettingsRepositoryTest·HostAgentTest(기능의 data), ObserveSystemStateTest(:core:data), JarvisAppTest(:app:ui, Compose UI)가 헤드리스 Chrome에서 돈다. CHROME_BIN을 지정하지 않으면 Karma가 브라우저를 찾지 못한다.

UI 테스트에서 waitUntil 로 Flow 전파를 기다리지 않는다 스레드가 하나뿐이라 waitUntil 의 폴링 루프가 이벤트 루프를 잡고 있으면, 그동안 stateIn 같은 중간 단계를 거치는 Flow 가 화면까지 전파되지 못한다. 가짜 저장소의 값을 바꾸고 그 결과가 목록에 나타나기를 waitUntil 로 기다리는 테스트가 세 번에 한 번꼴로 10초 타임아웃에 걸렸다. 그런 규칙은 화면을 그리지 않는 EmulatorDevicesViewModelTest(JVM)에서 runTest 로 확인한다. 프레임 디코딩에 같은 제약이 걸리는 이야기는 기기 목록·화면·제스처에 있다.

Compose 를 쓰는 모듈의 wasmJs 타깃에 binaries.executable()이 있는 이유도 이 테스트 때문이다. 실행 바이너리가 없으면 webpack 번들에 Skiko 런타임이 들어가지 않아 UI 테스트가 렌더링하지 못한다.
