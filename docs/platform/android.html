앱 정보 구현

공통 스펙: 앱 정보 카드

기술 조사

android.os.Build.VERSION이 SDK_INT(API 레벨 정수)와 RELEASE(예: "17")를 제공한다. 마케팅 이름은 시스템이 주지 않는다.

구현

actual val platformName: String = "Android ${Build.VERSION.SDK_INT}"

API 레벨을 그대로 보여준다. 마케팅 버전이 아니라 37 같은 정수다. 앱 버전은 versionName = libs.versions.appVersion으로 공용 원본을 읽는다.

한계

해당 없음.

검증

PlatformTest가 testAndroidHostTest에서 돈다. 화면 표시(AppTest)는 Android UI 테스트가 없어 검증하지 않는다.

화면 꺼짐 방지 구현

공통 스펙: 화면 꺼짐 방지

기술 조사

후보결과
View.keepScreenOn / 윈도우 FLAG_KEEP_SCREEN_ON권한 불필요. 윈도우가 보이는 동안만 유효하다. 정식 권장 경로
PowerManager.SCREEN_BRIGHT_WAKE_LOCKAPI 17에서 deprecated된 뒤 실제로 화면을 켜 두지 못한다. WAKE_LOCK 권한도 필요하다
foreground service + wake lockCPU는 깨워 두지만 화면은 켜 두지 못한다. 백그라운드 화면 유지는 플랫폼 정책상 불가
Compose Modifier.keepScreenOn()CMP 1.12.0 Android 구현은 AndroidComposeView가 요청 수를 세어 View.setKeepScreenOn(count > 0)을 부른다. 첫 후보를 그대로 쓴다

구현

공통 코드의 Modifier.keepScreenAwake(enabled)가 Compose의 keepScreenOn()을 붙이고, Compose가 View.keepScreenOn을 부른다. Android 전용 코드는 없다. PlatformIdleInhibitor의 Android actual은 = Unit이다.

한계

  • 윈도우가 보이는 동안만 유효하다. 홈으로 나가거나 앱을 종료하면 시스템이 플래그를 무시하고 화면은 평소대로 꺼진다.
  • 백그라운드에서 화면을 켜 둘 방법이 없다. 위 조사대로 구현 누락이 아니라 플랫폼 정책이다.
  • 화면 분할·PiP처럼 앱이 부분적으로만 보이는 상태의 동작은 OS 재량이라 보장하지 않는다.
  • Compose 밖에서 같은 View의 keepScreenOn을 직접 건드리면 Compose의 카운트와 어긋난다. 지금은 그런 코드가 없다.

검증

Android에서 돌아가는 UI 테스트가 없다. 토글·저장 로직은 skikoTest가 다른 타깃에서 검증하고, Android에서는 컴파일로만 보장된다.

설정 영구 저장 구현

공통 스펙: 설정 영구 저장

기술 조사

후보결과
SharedPreferences동기 읽기, apply()로 비동기 쓰기, OnSharedPreferenceChangeListener로 변경 알림. boolean 몇 개에 충분하다
androidx.datastore비동기·트랜잭션·Flow 지원. KMP 변형이 있지만 Web 쪽 Storage 구현을 직접 넣어야 해서 지금은 채택하지 않았다

구현

파일
shared/src/androidMain/.../SettingsStore.android.kt
저장소
context.getSharedPreferences("jarvis.settings", MODE_PRIVATE)
컨텍스트
LocalContext.current.applicationContext. Activity 재생성과 무관하게 같은 파일을 본다
쓰기
edit().putBoolean(key, value).apply()
변경 감지
callbackFlow + registerOnSharedPreferenceChangeListener
리스너는 약한 참조로만 잡힌다 SharedPreferences는 리스너를 WeakHashMap에 보관한다. awaitClose { unregister(listener) } 람다가 리스너를 붙들고 있어야 수집 중에 GC로 사라지지 않는다. 람다를 없애면 알림이 어느 순간 조용히 끊긴다.

한계

  • 첫 접근 시 getSharedPreferences가 디스크를 읽는다. boolean 하나라 무시할 수준이지만 값이 늘면 프레임을 막을 수 있다.
  • apply()는 커밋을 보장하지 않는다. 쓰기 직후 프로세스가 강제 종료되면 마지막 값이 유실될 수 있다.
  • 백업 대상이다(android:allowBackup="true"). 기기 이전 시 설정이 따라간다.

검증

AppSettingsTest가 testAndroidHostTest에서 InMemorySettingsStore로 돈다. SharedPreferences 왕복 자체는 미검증이다.

에뮬레이터 개수 불가

공통 스펙: 에뮬레이터 개수

기술 조사

  • 에뮬레이터 목록을 아는 도구(emulator, adb, simctl)는 개발자 머신에 있다. 앱은 기기 샌드박스 안에 있다.
  • Runtime.exec는 쓸 수 있지만 기기 안의 바이너리만 실행할 수 있고, 호스트의 SDK에는 닿지 않는다.
  • 앱이 돌고 있는 기기가 세려는 에뮬레이터 자신일 수도 있다. 그 경우에도 게스트에서 호스트를 들여다보는 API는 없다.
  • 호스트에 짝이 되는 서버를 두고 네트워크로 물어보는 방법은 있지만, 이 앱의 범위 밖이다.

대체 동작

internal actual val emulatorProbe: EmulatorProbe = EmulatorProbe { flowOf(EmulatorStatus()) }

항상 0개를 즉시 낸다. 카드는 다른 플랫폼과 같은 자리에 같은 모양으로 남는다.

한계

"0개"가 "셀 수 없음"을 뜻한다. 공통 한계 참고.

검증

AppTest.showsZeroEmulatorsWhenThePlatformCannotCountThem이 0개 프로브의 표시를 검증하지만 Android에서는 돌지 않는다.

빌드·실행

./gradlew :androidApp:assembleDebug     # APK 빌드
./gradlew :androidApp:installDebug      # 기기/에뮬레이터 설치

MainActivity는 configChanges를 넓게 선언해 회전·다크모드 전환 시 Activity가 재생성되지 않는다. Compose가 직접 변경을 처리한다.

테스트 UI 테스트 불가

테스트실행
PlatformTest, AppSettingsTest./gradlew :shared:testAndroidHostTest (호스트 JVM)
Compose UI 테스트 (AppTest)없음

기술 조사

Compose UI 테스트는 Skiko로 렌더링하는 타깃에서만 돌고 Android는 빠져 있다. 호스트 JVM에는 렌더링할 Android 런타임이 없다. 두 가지 대안을 조사했고 둘 다 지금은 막혀 있다.

대안결과
Robolectric4.17 + JDK 25 조합에서 FileDescriptor 내부 접근이 깨져 부팅하지 못했다
계측 테스트 (withDeviceTest)Compose Gradle 플러그인 1.12.0과 AGP KMP withDeviceTest를 함께 쓰면 copyAndroidDeviceTestComposeResourcesToAndroidAssets 태스크의 outputDirectory가 설정되지 않아 빌드가 깨진다

둘 중 하나가 풀리면 Android도 UI 테스트에 넣을 수 있다. 그때까지 Android의 화면 동작은 컴파일과 수동 확인으로 보장된다.
