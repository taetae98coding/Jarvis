모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
com.android.kotlin.multiplatform.library를 모듈마다 적용채택. 컨벤션 플러그인 jarvis.kmp.library가 적용한다. 모듈이 16개라 각 빌드 파일이 같은 선언을 반복할 수 없다
namespace를 어떻게 정하나프로젝트 경로에서 만든다(:feature:emulator:data → io.github.taetae98coding.jarvis.feature.emulator.data). 두 라이브러리가 같은 namespace를 쓰면 R 클래스가 같은 좌표에 두 번 생성되어 AGP가 빌드를 멈추므로 유일성이 요구사항이다. 패키지(…jarvis.data.emulator)와 순서가 다른데, AGP 는 namespace 를 R 클래스 좌표로만 쓰고 패키지 이름을 바꾸지 않은 이유는 공통 스펙의 결정에 있다
withHostTest {}commonTest가 있는 모듈에만 선언한다. 컨벤션 플러그인 jarvis.kmp.test를 적용하면 함께 붙는다. 화면 테스트는 Skiko가 필요해 Android 호스트 테스트로는 돌지 않는다(테스트)
actual typealias PlatformContext = Context안 된다. Context가 abstract 클래스라 final인 expect class와 modality가 어긋나고 EXPECT_ACTUAL_INCOMPATIBLE_MODALITY로 컴파일이 깨진다. expect abstract class로 맞추면 나머지 세 타깃에서 인스턴스를 만들 수 없다. 그래서 별칭 대신 한 겹 감싸는 클래스를 :core:data에 둔다
Application 서브클래스 또는 androidx.startup으로 전역 컨텍스트 보관버렸다. 매니페스트에 무언가를 등록해야 앱이 뜨는 구조가 되고 초기화 순서가 코드에서 사라진다. 지금은 MainActivity가 startJarvisKoin(applicationContext)로 명시적으로 넘긴다(의존성 주입)
앱 모듈이 기능 모듈을 직접 의존버렸다. :androidApp은 implementation(projects.shared) 하나만 둔다. 기능 모듈 열여섯은 전이 의존으로 APK에 들어가지만 컴파일 타임에는 보이지 않아, 앱 코드가 리포지토리를 직접 만드는 길이 막힌다

구현

파일
core/data/src/androidMain/.../PlatformContext.android.kt, shared/src/androidMain/.../JarvisKoin.android.kt
동작
actual class PlatformContext(val context: Context)에 애플리케이션 컨텍스트를 담는다. 리포지토리가 앱 수명 동안 살아 있는 single 이므로 Activity 컨텍스트를 넣지 않는다
실패
없다. MainActivity가 넘기는 applicationContext는 항상 값이 있다

한계

  • AGP가 모듈마다 R 클래스와 매니페스트를 만든다. 열여섯 모듈 모두 리소스가 없어서 실제 비용은 빈 클래스 열여섯 개뿐이지만, android.nonTransitiveRClass=true가 켜져 있으므로 리소스를 넣게 되면 모듈별로 R을 import해야 한다.
  • INTERNET·WRITE_SETTINGS 권한 선언은 :androidApp의 매니페스트에 있고, 그 권한을 쓰는 코드는 :feature:emulator:data·:feature:screen:data·:feature:rotation:data에 흩어져 있다. 라이브러리 매니페스트로 옮기면 코드와 붙지만, 앱이 어떤 권한을 요구하는지 한곳에서 읽을 수 없게 되어 옮기지 않았다.

검증

./gradlew testAndroidHostTest가 :core:data와 기능 모듈들의 commonTest를 호스트 JVM에서 돌린다(도메인 유스케이스 34개, 데이터 27개). 모듈 그래프와 Android 링크는 ./gradlew :androidApp:assembleDebug로 확인한다.

의존성 주입 구현

공통 스펙: 의존성 주입

기술 조사

후보결과
koin-core + MainActivity.onCreate에서 startKoin채택. setContent 전에 startJarvisKoin(applicationContext)를 부른다. Android 에서만 인자가 하나 더 붙고, 그 인자가 PlatformContext로 감싸여 기능의 data 모듈들에 들어간다
koin-android의 androidContext() + Application 서브클래스버렸다. Koin 모듈 선언이 Android 전용 API 를 쓰게 되어 네 타깃이 같은 모듈을 공유할 수 없다(R6). 매니페스트에 android:name을 등록해야 하고, 그러면 앱이 뜨는 방식이 플랫폼마다 또 갈라진다. PlatformContext가 이미 컨텍스트를 나르고 있다
KoinComponent + by inject()버렸다. 클래스가 자기 의존을 스스로 찾아오게 되어 생성자만 보고 무엇이 필요한지 알 수 없다. 생성자 주입으로 통일한다
androidx.startup(Initializer)로 시작버렸다. 모듈 구조에서 전역 컨텍스트 보관을 버린 것과 같은 이유다. 매니페스트에 프로바이더가 등록되어야 앱이 뜨는 구조가 되고, 초기화 순서가 코드에서 사라진다
Activity 컨텍스트를 그대로 넘기기안 된다. 리포지토리는 single이라 앱 수명 동안 산다. Activity 컨텍스트를 넣으면 Activity 가 끝난 뒤에도 붙들려 있는다. applicationContext만 넘긴다

구현

파일
androidApp/src/main/.../MainActivity.kt, shared/src/androidMain/.../JarvisKoin.android.kt
동작
startJarvisKoin(context: Context)가 PlatformContext(context.applicationContext)를 만들어 공용 모듈 목록과 함께 startKoin에 넘긴다. 이미 시작돼 있으면 그 Koin 을 돌려준다 — Activity 는 다시 만들어질 수 있고 onCreate도 다시 돈다
실패
정의가 빠져 있으면 첫 koinViewModel()에서 NoDefinitionFoundException으로 앱이 죽는다. 화면 일부만 비는 형태로 숨지 않는다

한계

  • Koin 을 시작하는 곳이 MainActivity 하나다. 브로드캐스트 리시버·위젯·워커 같은 다른 진입점을 추가하면 그쪽에서도 startJarvisKoin()을 불러야 한다. 지금은 진입점이 액티비티 하나뿐이라 이 사실이 드러날 자리가 없다.
  • android.app.Application을 서브클래스하지 않으므로, Koin 이 필요한 코드가 액티비티보다 먼저 도는 경우(예: ContentProvider)에는 쓸 수 없다.

검증

정의가 전부 해석되는지는 :shared의 jvmTest(JarvisKoinTest)가 본다. Android 에서는 같은 모듈 선언이 컴파일되는 것과 앱을 띄워 보는 것으로만 확인한다. Android UI 테스트가 없는 이유는 아래에 있다.

화면 상태 소유 (ViewModel) 구현

공통 스펙: 화면 상태 소유 (ViewModel)

기술 조사

후보결과
ComponentActivity가 제공하는 ViewModelStoreOwner채택. androidx.activity.compose.setContent가 LocalViewModelStoreOwner에 액티비티를 넣어 준다. lifecycle-viewmodel-compose의 viewModel()과 Koin 의 koinViewModel()이 그것을 그대로 쓴다
구성 변경 생존액티비티의 NonConfigurationInstances가 ViewModelStore를 넘긴다. 다만 이 앱의 매니페스트는 configChanges에 회전·크기·테마 등을 모두 선언해서 액티비티가 재생성되지 않는다. 즉 Android 에서도 재생성을 실제로 넘는 경우는 "활동 유지 안함"이나 프로세스 복귀처럼 드문 경로뿐이다
AndroidViewModel(Application 주입)버렸다. ViewModel 이 플랫폼 타입을 알게 되고 기능의 ui 모듈이 Android 에만 컴파일된다. ViewModel 은 유스케이스만 받는다
SavedStateHandle지금은 쓰지 않는다. 프로세스를 넘겨 복원할 값이 백스택뿐이다

구현

파일
공용이다. 기능마다 자기 ui 모듈에 있다 — feature/screen/ui/.../ScreenAwakeEffectViewModel.kt, feature/emulator/ui/.../EmulatorDevicesViewModel.kt 등 일곱
동작
Android 전용 코드는 없다. 앱 수명 owner 는 액티비티, 화면 수명 owner 는 rememberViewModelStoreNavEntryDecorator()가 만든다
실패
LocalViewModelStoreOwner가 비어 있으면 koinViewModel()이 예외를 던진다. setContent 안에서는 항상 채워져 있다

한계

  • onCleared()는 액티비티가 finish될 때 불린다. 시스템이 프로세스를 죽일 때는 불리지 않으므로, 그때 화면 꺼짐 방지의 정리 코드도 돌지 않는다. 다만 Android 에서 그 효과는 창에 붙어 있어 프로세스와 함께 사라진다.
  • 매니페스트의 configChanges 때문에 "ViewModel 이 구성 변경을 넘는다"는 성질이 이 앱에서는 거의 쓰이지 않는다. configChanges를 걷어내면 그때 실제로 쓰이게 된다.

검증

ViewModel 상태 규칙은 :feature:emulator:ui의 jvmTest(EmulatorDevicesViewModelTest)가, 화면과의 연결은 skiko UI 테스트가 본다. Android 에서는 컴파일과 수동 실행뿐이다.

화면 이동 (Navigation3) 구현 미검증

공통 스펙: 화면 이동 (Navigation3)

기술 조사

후보결과
NavDisplay + rememberNavBackStack채택. navigation3-runtime은 androidx 가 직접 퍼블리시하는 KMP 아티팩트라 Android 에서는 원본 구현이 그대로 돈다
시스템 뒤로NavDisplay 내부가 navigationevent-compose의 NavigationBackHandler를 부르고, Android 에서는 activity-compose의 back 브리지가 그것을 OnBackPressedDispatcher(API 33+ 에서는 OnBackInvokedCallback)에 연결한다. 앱 코드가 BackHandler를 따로 붙이지 않는다
예측 뒤로 애니메이션안 켰다. 매니페스트에 android:enableOnBackInvokedCallback="true"가 없다. 뒤로 동작 자체는 오지만 스와이프 진행에 맞춘 전환은 나오지 않는다. 켜면 NavDisplay의 predictivePopTransitionSpec이 살아난다
백스택 저장rememberNavBackStack이 rememberSerializable로 SavedStateRegistry에 넣는다. 액티비티 재생성과 프로세스 복귀를 모두 넘는다. 키가 @Serializable이어야 하고 NavKey 다형성을 직접 등록해야 한다(공통 스펙)
androidx.navigation:navigation-compose(Navigation2)버렸다. 지시가 Navigation3 이고, 문자열 라우트와 NavHost 대신 타입 있는 키와 백스택 직접 조작이 이 앱의 이동 방식(카드 → 목록 → 화면)에 더 가깝다

구현

파일
공용이다. app/ui/.../app/JarvisApp.kt, core/ui/.../navigation/Navigator.kt, 기능마다 자기 라우트(feature/emulator/ui/.../EmulatorRoute.kt)
동작
Android 전용 코드는 없다. 시스템 뒤로가 NavDisplay의 onBack으로 들어와 백스택을 한 칸 줄인다
실패
백스택이 비면 뒤로 콜백이 등록되지 않아 시스템 뒤로가 액티비티를 끝낸다. 홈에서 뒤로 누르면 앱이 닫히는 Android 의 기본 동작과 같다

한계

  • 예측 뒤로 애니메이션이 없다(위 조사 참고).
  • 딥링크가 없다. 매니페스트에 intent-filter를 붙이지 않았고 navigation3-runtime의 DeepLinkMatcher도 쓰지 않는다.

검증

이동 자체는 skiko UI 테스트가 본다. Android 의 시스템 뒤로와 백스택 복원은 자동 테스트가 없어 미검증이다. 수동으로는 기기 화면까지 들어간 뒤 시스템 뒤로 제스처로 두 번 나오고, 개발자 옵션의 "활동 유지 안함"을 켠 상태에서 앱을 내렸다 올려 같은 화면으로 돌아오는지 본다.

재생성을 넘기는 상태 (retain) 구현 미검증

공통 스펙: 재생성을 넘기는 상태 (retain)

기술 조사

후보결과
androidx.compose.runtime:runtime-retain의 retain채택. Android 에서는 compose-ui가 LifecycleRetainedValuesStore를 깔아 두고, 그 저장소가 Activity 재생성 구간에 retain 값을 보관한다. 앱 코드가 저장소를 제공하지 않는다
실제로 보관되는 경로이 앱의 매니페스트는 configChanges에 회전·크기·테마·폰트 등을 선언해서 그 변화로는 액티비티가 재생성되지 않는다. 남는 경로는 선언하지 않은 구성 변경, 개발자 옵션의 "활동 유지 안함", 그리고 시스템이 액티비티만 되살리는 경우다
rememberSaveable로 프레임 저장안 된다. 저장 상태는 Bundle로 시스템 프로세스를 거친다. 기기 해상도 PNG 를 넣으면 TransactionTooLargeException으로 앱이 죽는다
ViewModel 에 ImageBitmap 보관버렸다. 수명은 맞지만 화면 계층의 그래픽 객체가 상태 계층으로 올라간다(공통 스펙의 결정)

구현

파일
공용이다. feature/emulator/ui/.../emulator/EmulatorStreamScreen.kt, feature/emulator/ui/.../emulator/EmulatorFrameState.kt
동작
retain(deviceId) { EmulatorFrameState() }. 재생성 구간을 넘으면 같은 인스턴스가 돌아오고, 기기 화면 엔트리가 백스택에서 빠지면 저장소가 값을 버린다
실패
없다. 저장소가 보관하지 않으면 새 인스턴스가 만들어지고 화면은 "화면을 가져오는 중…"부터 시작한다

한계

  • 프로세스가 죽으면 프레임은 사라진다. retain은 직렬화하지 않는다.
  • configChanges 선언 때문에 실제로 보관이 일어나는 경우가 드물다. 이 기능의 값은 대부분 "이 상태의 수명이 컴포지션보다 길다"는 표시에 있다.

검증

미검증. Android 에는 UI 테스트가 없고(테스트), 재생성을 넘는 보관을 확인할 수 있는 플랫폼도 Android 하나다. 수동으로는 "활동 유지 안함"을 켠 채 기기 화면에서 홈으로 나갔다 돌아와 마지막 프레임이 그대로인지 본다.

앱 정보 구현

공통 스펙: 앱 정보 카드

기술 조사

IWindowManager.freezeRotation() / thawRotation()버렸다. 시스템이 실제로 쓰는 경로지만 @hide라 리플렉션이 필요하고, 호출에 SET_ORIENTATION 서명 권한이 필요하다. 사용자가 허용할 수 있는 권한이 아니다
DevicePolicyManager (device owner)버렸다. adb shell dpm set-device-owner로 공장초기화 상태에서만 프로비저닝된다. 시스템 전역 화면 유지의 조사와 같은 결론
DisplayManager.getDisplay(DEFAULT_DISPLAY).rotation채택(읽기). 자동 회전 중에는 USER_ROTATION이 갱신되지 않으므로 "지금 실제 각도"는 디스플레이에서 읽어야 한다. Context.getDisplay()는 API 30+에서 visual context를 요구해 애플리케이션 컨텍스트로는 예외가 나지만, DisplayManager 경로에는 그 제약이 없다
DisplayManager.DisplayListener.onDisplayChanged채택(관찰). 회전은 콜백이 있으므로 상태 조회 규칙의 폴링 쪽으로 가지 않는다. 잠금 여부는 ACCELEROMETER_ROTATION의 ContentObserver가 알려준다
OrientationEventListener버렸다. 센서 각도(0~359)를 알려줄 뿐 화면이 실제로 돌았는지는 모른다. 잠긴 동안에도 계속 방출된다
