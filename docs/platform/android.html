모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
com.android.kotlin.multiplatform.library를 모듈마다 적용채택. namespace가 모듈마다 달라야 한다. 두 라이브러리가 같은 namespace를 쓰면 R 클래스가 같은 좌표에 두 번 생성되어 AGP가 빌드를 멈춘다. 그래서 …jarvis.domain / .data / .ui / .shared로 나눴고, 이는 패키지 루트와 같다
withHostTest {}commonTest가 있는 모듈(:domain, :data)에만 선언한다. :ui의 UI 테스트는 Skiko가 필요해 Android 호스트 테스트로는 돌지 않는다(테스트)
LocalContext + PlatformContext채택. SharedPreferences와 Settings.System이 Context를 요구하는데 :data에는 Compose가 없다. Compose 트리를 볼 수 있는 :shared가 LocalContext.current.applicationContext를 PlatformContext로 감싸 넘긴다
actual typealias PlatformContext = Context안 된다. Context가 abstract 클래스라 final인 expect class와 modality가 어긋나고 EXPECT_ACTUAL_INCOMPATIBLE_MODALITY로 컴파일이 깨진다. expect abstract class로 맞추면 나머지 세 타깃에서 인스턴스를 만들 수 없다. 그래서 별칭 대신 한 겹 감싸는 클래스를 쓴다
Application 서브클래스 또는 androidx.startup으로 전역 컨텍스트 보관버렸다. :data가 초기화 순서에 의존하게 되고, 앱 모듈이 매니페스트에 무언가를 등록해야 앱이 뜨는 구조가 된다. 컨텍스트를 요구하는 생성자가 하나뿐이라 이득이 없다
앱 모듈이 :ui·:data를 직접 의존버렸다. :androidApp은 implementation(projects.shared) 하나만 둔다. 세 모듈은 전이 의존으로 APK에 들어가지만 컴파일 타임에는 보이지 않아, 앱 코드가 리포지토리를 직접 만드는 길이 막힌다

구현

파일
data/src/androidMain/.../PlatformContext.android.kt, shared/src/androidMain/.../PlatformContext.android.kt
동작
actual class PlatformContext(val context: Context)에 애플리케이션 컨텍스트를 담는다. 리포지토리가 컴포지션보다 오래 살 수 있으므로 Activity 컨텍스트를 넣지 않는다
실패
없다. LocalContext는 Compose 트리 안에서 항상 값을 갖는다

한계

  • AGP가 모듈마다 R 클래스와 매니페스트를 만든다. 네 모듈 모두 리소스가 없어서 실제 비용은 빈 클래스 넷뿐이지만, android.nonTransitiveRClass=true가 켜져 있으므로 리소스를 넣게 되면 모듈별로 R을 import해야 한다.
  • INTERNET·WRITE_SETTINGS 권한 선언은 :androidApp의 매니페스트에 있고, 그 권한을 쓰는 코드는 :data에 있다. 라이브러리 매니페스트로 옮기면 코드와 붙지만, 앱이 어떤 권한을 요구하는지 한곳에서 읽을 수 없게 되어 옮기지 않았다.

검증

./gradlew :domain:testAndroidHostTest :data:testAndroidHostTest가 호스트 JVM에서 돈다. 모듈 그래프와 Android 링크는 ./gradlew :androidApp:assembleDebug로 확인한다.

화면 꺼짐 방지 구현

공통 스펙: 화면 꺼짐 방지

기술 조사

후보결과
View.keepScreenOn / 윈도우 FLAG_KEEP_SCREEN_ON권한 불필요. 윈도우가 보이는 동안만 유효하다. 정식 권장 경로
PowerManager.SCREEN_BRIGHT_WAKE_LOCKAPI 17에서 deprecated된 뒤 실제로 화면을 켜 두지 못한다. WAKE_LOCK 권한도 필요하다
foreground service + wake lockCPU는 깨워 두지만 화면은 켜 두지 못한다. 앱 권한으로 백그라운드 화면을 유지하는 길은 없고, 시스템 설정을 바꾸는 별도 기능으로 돌아갔다
Compose Modifier.keepScreenOn()CMP 1.12.0 Android 구현은 AndroidComposeView가 요청 수를 세어 View.setKeepScreenOn(count > 0)을 부른다. 첫 후보를 그대로 쓴다

구현

공통 코드의 Modifier.keepScreenAwake(enabled)가 Compose의 keepScreenOn()을 붙이고, Compose가 View.keepScreenOn을 부른다. Android 전용 코드는 없다. :data의 createIdleInhibitor()는 Android에서 NoIdleInhibitor를 돌려준다.

한계

  • 윈도우가 보이는 동안만 유효하다. 홈으로 나가거나 앱을 종료하면 시스템이 플래그를 무시하고 화면은 평소대로 꺼진다.
  • 이 기능만으로는 백그라운드에서 화면을 켜 둘 수 없다. 앱에 주어지는 권한으로는 길이 없다. 시스템 전역 설정을 바꾸는 시스템 전역 토글이 그 자리를 맡는다.
  • 화면 분할·PiP처럼 앱이 부분적으로만 보이는 상태의 동작은 OS 재량이라 보장하지 않는다.
  • Compose 밖에서 같은 View의 keepScreenOn을 직접 건드리면 Compose의 카운트와 어긋난다. 지금은 그런 코드가 없다.

검증

Android에서 돌아가는 UI 테스트가 없다. 토글·저장 로직은 skikoTest가 다른 타깃에서 검증하고, Android에서는 컴파일로만 보장된다.

화면 꺼짐 방지 (시스템 전역) 우회 미검증

공통 스펙: 화면 꺼짐 방지 (시스템 전역)

기술 조사

앱에 주어지는 권한으로는 앱이 물러난 뒤의 화면을 지킬 수 없다. 마켓 배포를 포기하면 네 가지 길이 열리고, 전부 마켓 심사와는 양립하지 않는다.

후보결과
WRITE_SETTINGS + Settings.System.SCREEN_OFF_TIMEOUT채택. 사용자가 설정 화면에서 직접 허용하고 언제든 회수할 수 있는 appop이다. 시스템 전역 값이라 앱이 없어도 유지된다. 남의 설정을 바꾸므로 되돌릴 책임이 생긴다
SYSTEM_ALERT_WINDOW 오버레이 + foreground service1×1 오버레이 윈도우에 FLAG_KEEP_SCREEN_ON을 걸면 다른 앱이 떠 있어도 유효하다. 전역 설정을 건드리지 않아 깔끔하지만 프로세스가 계속 살아 있어야 하고 알림이 상주한다
DeviceOwner (DevicePolicyManager.setMaximumTimeToLock, lock task)가장 확실하다. 다만 adb shell dpm set-device-owner로 공장초기화 상태에서만 프로비저닝되어, 설치만으로는 켤 수 없다
WRITE_SECURE_SETTINGS + Settings.Global.STAY_ON_WHILE_PLUGGED_IN서명 권한이라 adb shell pm grant로만 부여된다. 앱 안에서 사용자가 허용할 방법이 없다
PowerManager.SCREEN_BRIGHT_WAKE_LOCKAPI 17에서 deprecated된 뒤 화면을 켜 두지 못한다. 앱 수명 내 기능의 조사와 같은 결론

우회

파일
data/src/androidMain/.../screen/SystemScreenAwake.android.kt
동작
토글이 켜지면 현재 SCREEN_OFF_TIMEOUT을 저장한 뒤 Int.MAX_VALUE(약 24.8일)로 덮어쓴다. 꺼지면 저장값으로 되돌린다
권한
Settings.System.canWrite(context)로 읽고, 없으면 ACTION_MANAGE_WRITE_SETTINGS 화면을 연다. 애플리케이션 컨텍스트로 띄우므로 FLAG_ACTIVITY_NEW_TASK가 필요하다
되돌릴 값
jarvis.screen_off_timeout SharedPreferences 파일. boolean만 다루는 SettingsStore에 Int를 넣을 수 없고, 사용자 설정이 아니라 내부 기록이라 jarvis.settings와도 섞지 않았다
실패
canWrite를 확인한 뒤에도 그 사이 권한이 회수되면 putInt가 SecurityException을 던진다. runCatching으로 삼켜 no-op이 된다
재적용이 원본을 덮어쓰지 않아야 한다 앱을 껐다 켜면 저장된 토글 값에 따라 효과가 다시 적용된다. 그때 이미 늘려 둔 Int.MAX_VALUE를 "원래 값"으로 저장해 버리면 되돌릴 곳을 영구히 잃는다. 그래서 저장값이 있으면 쓰지 않는다.

권한 상태와 현재 타임아웃은 상태 조회 규칙을 따라 관찰한다. 권한은 콜백이 없어 폴링, 타임아웃 값은 ContentObserver다.

한계

  • 권한을 잃으면 되돌릴 수 없다. 사용자가 설정에서 권한을 끈 뒤 토글을 끄면 늘려 둔 값이 남는다. 저장값은 지우지 않으므로 권한이 돌아오면 복원된다.
  • 앱을 삭제하면 늘려 둔 값이 남는다. 삭제 시점에 실행되는 훅이 없다. 토글을 끄고 지워야 한다.
  • 제조사 ROM이 값을 줄일 수 있다. 전력 관리 정책이 자체적으로 개입하는 경우까지는 막지 못한다.
  • 소유권을 다투지 않는다. 설정 앱이나 다른 앱이 같은 값을 바꾸면 마지막에 쓴 쪽이 이긴다. ContentObserver로 변화를 보고 화면에만 반영한다.
  • 권한이 없는 동안 토글은 켜진 채로 남는다. 설명이 "권한이 필요합니다"로 바뀌지만 스위치만 보면 동작 중인 것처럼 보인다.

검증

자동 테스트가 없다. 시스템 설정을 실제로 바꾸고 권한 화면을 여는 경로는 기기에서만 돌고, Android에는 UI 테스트가 없다. 설정값과 카드 표시는 commonTest·skikoTest가 다른 타깃에서 검증한다. SCREEN_OFF_TIMEOUT 왕복은 개발 기기에서 수동으로 확인한다.

설정 영구 저장 구현

공통 스펙: 설정 영구 저장

기술 조사

후보결과
SharedPreferences동기 읽기, apply()로 비동기 쓰기, OnSharedPreferenceChangeListener로 변경 알림. boolean 몇 개에 충분하다
androidx.datastore비동기·트랜잭션·Flow 지원. KMP 변형이 있지만 Web 쪽 Storage 구현을 직접 넣어야 해서 지금은 채택하지 않았다

구현

파일
data/src/androidMain/.../settings/SettingsStore.android.kt
저장소
context.getSharedPreferences("jarvis.settings", MODE_PRIVATE)
컨텍스트
LocalContext.current.applicationContext. Activity 재생성과 무관하게 같은 파일을 본다
쓰기
edit().putBoolean(key, value).apply()
변경 감지
callbackFlow + registerOnSharedPreferenceChangeListener
리스너는 약한 참조로만 잡힌다 SharedPreferences는 리스너를 WeakHashMap에 보관한다. awaitClose { unregister(listener) } 람다가 리스너를 붙들고 있어야 수집 중에 GC로 사라지지 않는다. 람다를 없애면 알림이 어느 순간 조용히 끊긴다.

한계

  • 첫 접근 시 getSharedPreferences가 디스크를 읽는다. boolean 하나라 무시할 수준이지만 값이 늘면 프레임을 막을 수 있다.
  • apply()는 커밋을 보장하지 않는다. 쓰기 직후 프로세스가 강제 종료되면 마지막 값이 유실될 수 있다.
  • 백업 대상이다(android:allowBackup="true"). 기기 이전 시 설정이 따라간다.

검증

ScreenAwakeSettingsRepositoryTest가 testAndroidHostTest에서 InMemorySettingsStore로 돈다. SharedPreferences 왕복 자체는 미검증이다.

상태 조회 규칙 구현

공통 스펙: 상태 조회 규칙

기술 조사

상태콜백
설정값OnSharedPreferenceChangeListener. 있다
Settings.System.SCREEN_OFF_TIMEOUTContentObserver + Settings.System.getUriFor(…). 있다. 바뀐 값은 주지 않고 URI만 준다

구현

  • ContentObserver의 Handler를 null로 두어 콜백이 바인더 스레드에서 온다. trySend만 부르므로 문제가 없지만, 여기서 다른 일을 하면 안 된다.

검증

ObserveSystemStateTest가 testAndroidHostTest에서 돈다. Android 콜백을 실제로 받는 부분(ContentObserver, 권한 폴링)은 기기가 필요해 미검증이다.

에뮬레이터 개수 우회

공통 스펙: 에뮬레이터 개수

기술 조사

  • 에뮬레이터 목록을 아는 도구(emulator, adb, simctl)는 개발자 머신에 있다. 앱은 기기 샌드박스 안에 있다.
  • Runtime.exec는 쓸 수 있지만 기기 안의 바이너리만 실행할 수 있고, 호스트의 SDK에는 닿지 않는다.
  • 앱이 돌고 있는 기기가 세려는 에뮬레이터 자신일 수도 있다. 그 경우에도 게스트에서 호스트를 들여다보는 API는 없다.
  • 네트워크는 닿는다. 에뮬레이터에서 10.0.2.2는 호스트 머신의 루프백이다. 호스트에 짝이 되는 서버가 있으면 물어볼 수 있다. 이 경로를 택했다.

우회

파일
data/src/androidMain/.../emulator/agent/HostAgent.android.kt
동작

주소
10.0.2.2 → 127.0.0.1 순서로 시도해 처음 응답한 쪽을 쓴다. 뒤쪽은 실물 기기에서 adb reverse tcp:47890 tcp:47890을 걸었을 때의 경로다
타임아웃
연결·읽기 각 1초. 에이전트는 미리 세 둔 값을 주므로 그보다 오래 걸리면 없는 것으로 본다
실패
예외와 200 이외의 응답을 모두 null로 묶는다. 카드는 "셀 수 없음"을 보여준다

평문 HTTP라 res/xml/network_security_config.xml에서 이 두 주소에만 cleartext를 허용한다. 개발자 머신마다 TLS 인증서를 심을 수 없어 암호화를 포기하는 대신, 예외 범위를 호스트 루프백으로 좁혔다. INTERNET 권한도 이 요청 때문에 필요하다.

한계

  • 데스크톱 앱이 떠 있어야 한다. 꺼져 있으면 연결이 거절되고 "셀 수 없음"이 된다.
  • 실물 기기는 adb reverse가 필요하다. 매번 수동으로 걸어야 하고 USB를 뽑으면 끊긴다.
  • 5초 폴링이라 최대 5초 늦는다.
  • 에이전트에 인증이 없다. 공통 스펙 참고.

검증

HostAgentTest가 testAndroidHostTest에서 가짜 조회 함수로 폴링과 "셀 수 없음" 처리를 검증한다. HttpURLConnection으로 실제 요청을 보내는 부분은 에뮬레이터와 데스크톱 앱이 함께 있어야 해서 미검증이다. 개발 머신에서 curl로 에이전트 왕복을 확인했다.

화면 회전 우회 미검증

공통 스펙: 화면 회전

기술 조사

네 플랫폼 중 유일하게 기기 전역 회전을 바꿀 수 있다. 앱 창만 돌리는 정식 경로(requestedOrientation)가 따로 있지만, 이 기능이 요구하는 것은 기기 쪽이다.

후보결과
WRITE_SETTINGS + Settings.System.ACCELEROMETER_ROTATION · USER_ROTATION채택. 자동 회전 on/off가 ACCELEROMETER_ROTATION(1/0), 고정 각도가 USER_ROTATION(Surface.ROTATION_*, 0~3)이다. 기기 전역이라 홈 화면과 다른 앱도 따라 돈다. 시스템 전역 화면 유지가 이미 쓰는 권한이라 매니페스트에 추가할 것이 없다
Activity.requestedOrientation (ActivityInfo.SCREEN_ORIENTATION_*)버렸다. 권한이 필요 없고 정식 API지만 우리 Activity만 돈다. 홈으로 나가면 사라지고 회전잠금 토글의 뜻도 기기가 아니라 앱이 된다. 게다가 :data가 들고 있는 것은 애플리케이션 컨텍스트뿐이라(모듈 구조) Activity를 잡으려면 수명 추적을 새로 들여야 한다
IWindowManager.freezeRotation() / thawRotation()버렸다. 시스템이 실제로 쓰는 경로지만 @hide라 리플렉션이 필요하고, 호출에 SET_ORIENTATION 서명 권한이 필요하다. 사용자가 허용할 수 있는 권한이 아니다
DevicePolicyManager (device owner)버렸다. adb shell dpm set-device-owner로 공장초기화 상태에서만 프로비저닝된다. 시스템 전역 화면 유지의 조사와 같은 결론
DisplayManager.getDisplay(DEFAULT_DISPLAY).rotation채택(읽기). 자동 회전 중에는 USER_ROTATION이 갱신되지 않으므로 "지금 실제 각도"는 디스플레이에서 읽어야 한다. Context.getDisplay()는 API 30+에서 visual context를 요구해 애플리케이션 컨텍스트로는 예외가 나지만, DisplayManager 경로에는 그 제약이 없다
DisplayManager.DisplayListener.onDisplayChanged채택(관찰). 회전은 콜백이 있으므로 상태 조회 규칙의 폴링 쪽으로 가지 않는다. 잠금 여부는 ACCELEROMETER_ROTATION의 ContentObserver가 알려준다
OrientationEventListener버렸다. 센서 각도(0~359)를 알려줄 뿐 화면이 실제로 돌았는지는 모른다. 잠긴 동안에도 계속 방출된다

우회

파일
data/src/androidMain/.../rotation/DeviceRotation.android.kt
잠금
ACCELEROMETER_ROTATION에 0(잠금) 또는 1(자동)을 쓴다
각도
USER_ROTATION에 degrees / 90을 쓴다. 자동 회전이 켜진 채로 쓰면 값만 남고 화면은 돌지 않아서, 규칙상 항상 잠금이 먼저 걸린다(공통 스펙 R5)
읽기
각도는 DisplayManager의 Display.rotation, 잠금은 ACCELEROMETER_ROTATION == 0
권한
Settings.System.canWrite(context). 없으면 ACTION_MANAGE_WRITE_SETTINGS 화면을 연다. 시스템 전역 화면 유지와 같은 권한이라 한쪽을 허용하면 둘 다 열린다
실패
canWrite 확인 뒤 권한이 회수되면 putInt가 SecurityException을 던진다. runCatching으로 삼켜 no-op이 된다

각도 상수는 Surface.ROTATION_*와 RotationAngle.degrees / 90이 그대로 일치한다(각도 기준). 변환표를 따로 두지 않는 이유다.

한계

  • 고정된 방향을 선언한 앱이 이긴다. android:screenOrientation으로 방향을 못박은 앱을 열면 그 앱 화면은 우리가 건 각도를 무시한다. 홈 화면으로 돌아오면 다시 우리 각도다.
  • 앱을 종료해도 잠금이 남는다. 시스템 전역 값이라 그것이 이 기능의 목적이지만, 되돌리려면 토글을 끄거나 시스템 설정에서 자동 회전을 켜야 한다.
  • 제조사 ROM이 개입할 수 있다. 일부 ROM은 180°(ROTATION_180)를 허용하지 않거나 잠금 상태를 자체 UI로 덮어쓴다.
  • 기본 디스플레이만 다룬다. 폴더블의 두 번째 화면이나 외부 디스플레이는 DEFAULT_DISPLAY가 아니라서 읽지도 쓰지도 않는다.
  • 권한이 없는 동안 카드의 컨트롤은 눌리지만 회전 대신 권한 화면이 열린다. 설명이 그 사실을 적는다.

검증

자동 테스트가 없다. Settings.System을 실제로 쓰고 화면이 도는 경로는 기기에서만 돌고, Android에는 UI 테스트가 없다. 규칙(잠근 뒤 각도를 쓴다, 권한이 없으면 권한 화면을 연다)은 :domain commonTest가, 카드 표시는 :ui skikoTest가 다른 타깃에서 검증한다. 기기에서는 카드의 버튼을 누른 뒤 설정 > 디스플레이 > 화면 자동 회전이 꺼지고 홈 화면까지 같이 도는지로 확인한다.

에뮬레이터 목록·화면·제스처 우회

공통 스펙: 에뮬레이터 목록·화면·제스처

기술 조사

  • 개수를 셀 때와 전제가 같다. adb 도 simctl 도 호스트 머신에 있고 앱은 기기 샌드박스 안이다(에뮬레이터 개수).
  • 화면 픽셀과 입력은 개수보다 무거울 뿐 성질이 같다. 이미 뚫려 있는 10.0.2.2 HTTP 경로에 엔드포인트를 더하는 것으로 끝난다.
  • HttpURLConnection 은 바이너리 응답도 그대로 준다. PNG 는 inputStream.readBytes() 로 받는다.
  • 제스처는 POST 다. 본문을 text/plain 으로 보내 브라우저 클라이언트와 같은 형식을 쓴다(Android 에서는 사전 요청이 없어 형식이 자유롭지만, 에이전트 쪽 분기를 하나로 두려고 맞췄다).

우회

파일
data/src/androidMain/.../emulator/agent/HostAgent.android.kt
동작
GET /emulators/devices, GET /emulators/screen?id=…, POST /emulators/gesture. 전부 Dispatchers.IO
주소
개수와 같다. 10.0.2.2 → 127.0.0.1 순서로 시도한다
타임아웃
목록·제스처는 2초. 프레임은 호스트가 화면을 찍는 시간을 기다려야 해서 5초
실패
목록은 빈 목록, 프레임은 null, 제스처는 조용히 버린다. 화면에는 공통 스펙의 문구가 나온다

평문 HTTP 라 network_security_config.xml 의 cleartext 예외를 그대로 쓴다. 호스트가 두 개뿐이라 파일은 고치지 않는다.

한계

  • 데스크톱 앱이 떠 있어야 한다. 꺼져 있으면 목록이 빈다.
  • 실물 기기는 adb reverse tcp:47890 tcp:47890 이 필요하다. 이때 프레임(400KB 안팎)이 USB 포워딩을 타서 에뮬레이터에서보다 눈에 띄게 느리다.
  • 기기 화면 위에서 다른 기기 화면을 보는 구조라, 프레임 크기가 화면보다 크면 축소되어 글자가 작아진다.

검증

HostAgentTest 가 testAndroidHostTest 에서 가짜 전송 함수로 목록·프레임·제스처의 실패 처리를 확인한다. 실제 10.0.2.2 왕복은 에뮬레이터와 데스크톱 앱이 함께 있어야 해서 미검증이다.

빌드·실행

./gradlew :androidApp:assembleDebug     # APK 빌드
./gradlew :androidApp:installDebug      # 기기/에뮬레이터 설치

adb reverse tcp:47890 tcp:47890         # 실물 기기에서 에뮬레이터 개수를 보려면

Android SDK 위치는 local.properties의 sdk.dir 또는 ANDROID_HOME으로 알려줘야 한다.

MainActivity는 configChanges를 넓게 선언해 회전·다크모드 전환 시 Activity가 재생성되지 않는다. Compose가 직접 변경을 처리한다.

테스트 UI 테스트 불가

기술 조사

Compose UI 테스트는 Skiko로 렌더링하는 타깃에서만 돌고 Android는 빠져 있다. 호스트 JVM에는 렌더링할 Android 런타임이 없다. 두 가지 대안을 조사했고 둘 다 지금은 막혀 있다.

대안결과
Robolectric4.17 + JDK 25 조합에서 FileDescriptor 내부 접근이 깨져 부팅하지 못했다
계측 테스트 (withDeviceTest)Compose Gradle 플러그인 1.12.0과 AGP KMP withDeviceTest를 함께 쓰면 copyAndroidDeviceTestComposeResourcesToAndroidAssets 태스크의 outputDirectory가 설정되지 않아 빌드가 깨진다

둘 중 하나가 풀리면 Android도 UI 테스트에 넣을 수 있다. 그때까지 Android의 화면 동작은 컴파일과 수동 확인으로 보장된다.

이 문서에서 미검증으로 남는 경로는 셋이다. SharedPreferences 왕복, WRITE_SETTINGS로 시스템 설정을 바꾸는 경로, 그리고 10.0.2.2로 에이전트에 요청하는 경로. 전부 기기가 필요하다.
