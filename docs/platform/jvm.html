화면 꺼짐 방지 우회

공통 스펙: 화면 꺼짐 방지

기술 조사

후보결과
Compose Modifier.keepScreenOn()JVM에서는 no-op. CMP 1.12.0의 PlatformContext.setKeepScreenOnEnabled는 본문이 return 하나인 빈 기본 구현이고, Swing/AWT 씬 중 이를 오버라이드하는 것이 없다
JVM 표준 API유휴 타이머를 막는 이식 가능한 API가 없다. java.awt.Robot으로 입력을 흉내 내는 방법은 사용자 입력을 방해해 제외
macOS caffeinate시스템 기본 탑재. -d는 디스플레이 슬립, -i는 시스템 유휴 슬립을 막는다. 프로세스가 살아 있는 동안만 유효하다
macOS IOPMAssertionCreateWithName정식 API지만 JNA/Panama 바인딩이 필요하다. 의존성 추가 없이 되는 caffeinate를 택했다
Linux systemd-inhibit, Windows SetThreadExecutionState동작하지만 지원 범위 밖. 반만 동작하는 코드를 남기지 않기 위해 제거했다

우회

파일
shared/src/jvmMain/.../ScreenAwake.jvm.kt
훅
PlatformIdleInhibitor(enabled)의 JVM actual만 본문이 있다
동작
DisposableEffect(enabled)에서 켜지면 ProcessBuilder("caffeinate", "-di").start(), 꺼지거나 컴포지션이 사라지면 process.destroy()
실패
runCatching { ... }.getOrNull(). 명령이 없으면 null이 되고 토글은 조용히 no-op이다

Compose가 비워 둔 자리를 이 한 칸으로 메운다. CMP가 데스크톱 경로를 구현하면 PlatformIdleInhibitor expect/actual은 통째로 걷어낸다.

한계

  • macOS 외 no-op. 실행은 되지만 화면 꺼짐 방지는 동작하지 않는다. 의도된 범위다.
  • 강제 종료 시 자식 프로세스가 남는다. 창을 닫으면 컴포지션이 정리되며 destroy()가 불리지만, JVM이 SIGKILL로 죽으면 caffeinate가 살아남아 화면이 계속 켜져 있을 수 있다. 셧다운 훅을 걸면 SIGTERM까지는 막을 수 있다.
  • 실패를 알 수 없다. 명령이 없거나 실행이 막혀도 UI는 켜진 상태로 보인다.

검증

AppTest의 토글·저장 테스트 4개가 jvmTest에서 돈다. caffeinate가 실제로 뜨는지는 미검증이다. 개발 머신에서 pmset -g assertions로 확인할 수 있다.

에뮬레이터 개수 우회

공통 스펙: 에뮬레이터 개수

기술 조사

대상명령세는 방법
Android 설치<sdk>/emulator/emulator -list-avds비어 있지 않은 줄 수. 진단 메시지는 stderr로 간다
Android 실행<sdk>/platform-tools/adb devicesemulator-로 시작하는 시리얼 수. USB(39061FDJH00CNS)와 무선(192.168.0.10:5555) 기기는 형태가 달라 걸리지 않는다
iOS 설치xcrun simctl list devices availableUDID ([0-9A-F-]{36})가 붙은 줄 수
iOS 실행같은 출력상태가 Booted인 줄 수

기기 줄은 iPhone 17 (66C9B671-…) (Shutdown) 꼴이다. 이름이 아니라 UDID를 기준으로 잡는데, iPad mini (A17 Pro)처럼 이름 자체에 괄호가 들어가기 때문이다.

변경 이벤트를 조사했지만 쓸 수 없었다. adb track-devices는 있지만 simctl에는 대응물이 없다. 그래서 주기적으로 다시 세는 쪽으로 갔다.

우회

파일

실패

xcrun이 아니라 Xcode.app을 직접 보는 경우

xcrun simctl은 xcode-select가 정식 Xcode를 가리킬 때만 동작한다. Command Line Tools만 선택된 머신에서는 xcrun: error: unable to find utility "simctl"로 실패하지만, Xcode.app 안의 simctl은 그대로 있다. 그래서 시뮬레이터가 없다고 답하기 전에 기본 설치 경로를 한 번 더 본다.

출력을 파이프가 아니라 임시 파일로 받는 이유

adb는 데몬을 fork 하면서 부모의 표준 출력을 물려받는다. 파이프로 읽으면 adb devices가 끝난 뒤에도 데몬이 쓰기 끝을 잡고 있어 읽기가 끝나지 않고, 그러면 10초 타임아웃도 걸리지 않는다. redirectOutput(File)로 받으면 그런 독자가 없다. stderr는 DISCARD한다.

한계

  • 최대 5초 늦다. 폴링 주기 안에서 바뀐 것은 다음 주기에 반영된다.
  • macOS 전제다. iOS 시뮬레이터는 macOS에만 있고 SDK 기본 경로도 macOS 것만 넣었다.
  • 실패와 0개를 구분하지 않는다. SDK가 없거나 명령이 실패하면 화면에는 0개로 보인다.
  • Android 실행 개수는 adb에 묶여 있다. platform-tools가 없으면 에뮬레이터가 떠 있어도 0이 된다.
  • 첫 호출이 느릴 수 있다. adb devices가 데몬을 띄워야 하면 1초쯤 걸린다. 그동안 카드는 "확인 중…"이다.

검증

EmulatorParsingTest(jvmTest)가 세 명령의 출력 문자열 파싱과, 폴링 프로브가 주기마다 다시 세고 같은 결과를 걸러내는 것을 검증한다. 명령을 실제로 띄우는 부분은 테스트하지 않는다. 머신에 SDK가 깔려 있는지에 결과가 달라지기 때문이다. AppTest의 에뮬레이터 카드 테스트 4개도 jvmTest에서 돈다.
