모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
호스트 에이전트를 :feature:emulator:data의 jvmMain에 둔다채택. com.sun.net.httpserver와 SDK 도구 실행은 바깥 세계에 닿는 일이라 data 계층이고, 에뮬레이터 기능의 일부다. :desktopApp은 :shared가 재노출한 startEmulatorHostAgent()만 부른다
:desktopApp이 기능 모듈을 직접 의존버렸다. 앱 모듈이 :shared 하나만 알게 두면, 기능 모듈이 늘거나 이름이 바뀌어도 앱 진입점은 고치지 않는다. 대가는 :shared의 재노출 한 줄이다
에뮬레이터 폴링 Flow의 위치:feature:emulator:data의 jvmMain 최상위 val(프로세스 싱글턴)로 둔다. 데스크톱 UI의 리포지토리와 로컬 에이전트가 같은 shareIn Flow를 구독해야 adb·simctl이 5초마다 한 번만 돈다. 에이전트는 Koin(emulatorDataModule)을 거치지 않고 이 데이터 소스를 직접 구독한다
compose.desktop.currentOs:desktopApp과 :app:ui의 jvmTest에만 넣는다. 기능의 ui 모듈에는 Skiko 화면 테스트가 없고, data·domain은 Skiko 네이티브 런타임이 필요 없다
jvmToolchain(21)컨벤션 플러그인 jarvis.kmp.library가 선언한다. 툴체인은 모듈 단위 설정이라 상속되지 않으므로, 모듈 열여섯이 각자 적는 것을 피하려면 플러그인이 유일한 방법이다. :desktopApp은 KMP 모듈이 아니라 자기 빌드 파일에 남아 있다
kotlinx-coroutines-swing:shared의 jvmMain에 넣는다. viewModelScope 가 Dispatchers.Main.immediate 이고 JVM 에서 그 디스패처는 이 아티팩트가 있어야 존재한다. 없으면 viewModelScope 가 조용히 EDT 밖에서 돈다. Compose Desktop 이 데려온다고 보고 넣지 않았다가, 그때 있던 앱 수명 스코프를 만드는 순간 죽었다(의존성 주입)

구현

파일
feature/emulator/data/src/jvmMain/.../emulator/agent/HostAgentServer.kt, shared/src/jvmMain/.../EmulatorHostAgent.kt, shared/src/jvmMain/.../JarvisKoin.jvm.kt
동작
:shared의 startEmulatorHostAgent()가 :feature:emulator:data의 같은 이름 함수를 부른다. main()은 startEmulatorHostAgent().use { startJarvisKoin(); application { … } }
실패
포트가 이미 쓰이면 조용히 no-op. 기능 분리 전과 같다

한계

  • 에이전트는 Koin 을 거치지 않고 데이터 소스를 직접 구독한다. 그래서 main()이 화면보다 먼저 에이전트를 띄울 수 있지만, 개수를 세는 경로가 주입 그래프 밖에도 하나 있다는 뜻이기도 하다. 에뮬레이터 데이터 소스가 PlatformContext나 다른 상태를 요구하게 되면 이 경로부터 깨진다.
  • :shared의 재노출 함수는 :feature:emulator:data의 시그니처를 그대로 베낀다. 시그니처가 바뀌면 두 곳을 고쳐야 한다.

검증

./gradlew jvmTest. 에이전트 서버 테스트(HostAgentServerTest)는 :feature:emulator:data:jvmTest, ViewModel 상태 테스트는 :feature:emulator:ui:jvmTest, Skiko 화면이 필요한 UI 테스트는 :app:ui:jvmTest, Koin 해석 테스트는 :shared:jvmTest에 있다.

의존성 주입 구현

공통 스펙: 의존성 주입

기술 조사

후보결과
main()에서 startJarvisKoin()채택. 호스트 에이전트를 띄운 뒤, application { } 앞에서 시작한다. PlatformContext는 빈 상자다
앱 수명 CoroutineScope걷어냈다. 리포지토리가 앱 수명 StateFlow 를 만들던 때 넘기던 스코프다. 상태 조회 규칙 R12 로 리포지토리가 cold Flow 만 내놓게 되면서 받을 곳이 없어졌다. 상태는 viewModelScope(EDT)에서 모이므로 스레드는 예전과 같다
호스트 에이전트를 Koin 에서 꺼내기버렸다. 에이전트는 에뮬레이터 데이터 소스를 직접 구독한다. 그 데이터 소스는 :feature:emulator:data jvmMain의 프로세스 싱글턴이고, 조립을 거치지 않는다는 기존 결정을 그대로 둔다. 에이전트가 Koin 을 요구하면 시작 순서가 뒤엉킨다(에이전트 → Koin → 데이터 소스 → 에이전트)

구현

파일
desktopApp/src/main/.../main.kt, shared/src/jvmMain/.../JarvisKoin.jvm.kt
동작
startEmulatorHostAgent().use { startJarvisKoin(); application { Window { JarvisApp() } } } 순서다. 에이전트가 먼저 떠서 다른 타깃이 개수를 물어볼 수 있고, Koin 은 첫 화면보다 먼저 선다
실패
정의가 빠져 있으면 창이 뜨기 전에 예외로 종료된다. 로그는 표준 출력에 남는다

한계

  • 기능의 data 모듈은 스코프를 받지 않으므로 Swing 없는 JVM 프로그램(예: 헤드리스 CLI)에서도 그대로 쓸 수 있다. kotlinx-coroutines-swing 이 필요한 것은 화면을 띄우는 :shared 뿐이다.

검증

:shared의 jvmTest(JarvisKoinTest)가 네 모듈을 실제로 시작해 정의를 전부 해석하고, 리포지토리가 싱글턴인지와 시작이 두 번 불려도 안전한지를 본다. 이 테스트가 도는 곳이 JVM 뿐이라는 것이 공통 한계에 적혀 있다.

기술 조사

기술 조사

후보결과
retain + 플랫폼이 제공하는 RetainedValuesStore저장소가 없다. runtime-retain의 desktop 변형은 있지만 skiko 쪽 compose-ui에 Android 의 LifecycleRetainedValuesStore에 해당하는 구현이 없다. 기본값 ForgetfulRetainedValuesStore가 쓰인다

화면 꺼짐 방지 우회

공통 스펙: 화면 꺼짐 방지

기술 조사

후보결과
Compose Modifier.keepScreenOn()JVM에서는 no-op. CMP 1.12.1의 PlatformContext.setKeepScreenOnEnabled는 본문이 return 하나인 빈 기본 구현이고, Swing/AWT 씬 중 이를 오버라이드하는 것이 없다
JVM 표준 API유휴 타이머를 막는 이식 가능한 API가 없다. java.awt.Robot으로 입력을 흉내 내는 방법은 사용자 입력을 방해해 제외
macOS caffeinate시스템 기본 탑재. -d는 디스플레이 슬립, -i는 시스템 유휴 슬립을 막는다. 프로세스가 살아 있는 동안만 유효하다
macOS IOPMAssertionCreateWithName정식 API지만 JNA/Panama 바인딩이 필요하다. 의존성 추가 없이 되는 caffeinate를 택했다
Linux systemd-inhibit, Windows SetThreadExecutionState동작하지만 지원 범위 밖. 반만 동작하는 코드를 남기지 않기 위해 제거했다

우회

파일
feature/screen/data/src/jvmMain/.../screen/IdleInhibitor.jvm.kt
훅
createIdleInhibitor()의 JVM actual만 본문이 있다
동작
setKeepScreenAwake(true)면 ProcessBuilder("caffeinate", "-di").start(), false거나 화면이 사라져 ApplyKeepScreenAwakeUseCase가 취소되면 process.destroy()
정리
프로세스를 띄울 때 Runtime.addShutdownHook도 함께 건다. 자식 프로세스는 JVM이 죽어도 살아남으므로, 앱이 없는데 화면이 계속 켜져 있는 상태를 막는다. 토글을 끌 때는 훅을 떼고 죽인다
실패
runCatching { ... }.getOrNull(). 명령이 없으면 null이 되고 토글은 조용히 no-op이다

Compose가 비워 둔 자리를 이 한 칸으로 메운다. CMP가 데스크톱 경로를 구현하면 createIdleInhibitor() expect/actual과 ApplyKeepScreenAwakeUseCase는 통째로 걷어낸다.

한계

  • macOS 외 no-op. 실행은 되지만 화면 꺼짐 방지는 동작하지 않는다. 의도된 범위다.
  • SIGKILL은 못 막는다. 정상 종료와 SIGTERM은 셧다운 훅이 정리하지만, SIGKILL로 죽으면 훅이 돌지 않아 caffeinate가 살아남고 화면이 계속 켜져 있을 수 있다.
  • 실패를 알 수 없다. 명령이 없거나 실행이 막혀도 UI는 켜진 상태로 보인다.

검증

JarvisAppTest의 토글·저장 테스트 4개가 jvmTest에서 돈다. caffeinate가 실제로 뜨는지는 미검증이다. 개발 머신에서 pmset -g assertions로 확인할 수 있다.

타임아웃
명령마다 10초. 넘기면 강제 종료하고 없는 것으로 답한다
스레드
촬영을 포함해 모든 명령이 withContext(Dispatchers.IO) 에서 돈다. 촬영은 한때 수집하는 쪽(Swing EDT)에서 돌아 한 장마다 0.3~0.6초씩 UI 를 멈췄다(결정). 프레임 디코딩은 FrameDecodeContext = Dispatchers.Default

대체 동작

iOS 시뮬레이터 항목은 canControl = false 로 내려간다. 화면은 보이고, 탭·드래그는 화면에서부터 막혀 요청 자체가 나가지 않는다. 사용자에게는 왜 안 되는지 한 줄이 보인다.

실물 iOS 기기 항목은 canStream 도 false 다. 목록에는 이름과 "화면을 볼 수 없음" 이 보이고 줄을 누를 수 없다. 목록에서 아예 빼면 "USB 로 꽂았는데 왜 없지" 가 되고, 누를 수 있게 두면 빈 화면만 보게 된다.

한계

  • macOS 만. Android SDK 경로 탐색과 simctl 경로가 macOS 기준이다. 다른 OS 에서는 목록이 비고 조용히 no-op 이 된다.
  • 시뮬레이터의 프레임률이 낮다. simctl io screenshot 한 장이 0.2~0.5초다. Android 기기는 영상 스트림이라 해당 없다.
  • 시리얼 ↔ AVD 이름 매핑에 명령이 한 번 더 든다. 실행 중인 에뮬레이터 수만큼 adb emu avd name 이 돈다. 폴링 주기가 5초라 감당 가능한 수준으로 봤다.
  • 실물 iOS 기기를 찾는 데 xctrace 가 느리다. 기기를 스캔하느라 수 초가 걸리고, 그만큼 목록 폴링 한 바퀴가 길어진다. 명령 타임아웃(10초)을 넘기면 그 바퀴에서는 실물 iOS 기기가 없는 것으로 답한다.
  • USB 디버깅을 허용하지 않은 Android 기기는 보이지 않는다. adb devices 에 unauthorized 로 남는 동안은 목록에서 빠진다. 기기 화면의 확인 대화상자를 누르면 다음 폴링에 나타난다.
  • 에뮬레이터를 켜고 끄거나 USB 를 꽂고 뽑는 순간에는 목록과 실제가 최대 5초 어긋난다.

꺼진 에뮬레이터 실행 우회

공통 스펙: 꺼진 에뮬레이터 실행

실제로 에뮬레이터를 띄우는 것은 여기뿐이다. 다른 세 타깃의 실행 버튼은 에이전트를 거쳐 이 코드에 닿는다.

기술 조사

후보결과
$SDK/emulator/emulator -avd <이름>채택. AVD 이름 하나로 띄운다. 에뮬레이터가 꺼질 때까지 살아 있는 프로세스라 기다리지 않고 떼어 놓는다. 절대 경로로 불러도 자기 위치를 찾아 SDK 를 잡는다(옛 tools/emulator 와 달리 emulator/ 안의 바이너리는 ANDROID_SDK_ROOT 가 없어도 된다)
avdmanager버렸다. AVD 를 만들고 지우는 도구이고 띄우지는 못한다.
adb -s emulator-5554 emu kill조사만 했다. 끄는 명령이고 스코프 밖이다. 켜는 것과 달리 되돌릴 수 없어서 지시에 없는 이상 넣지 않는다.
simctl boot <UDID>채택. 시뮬레이터를 부팅한다. 바로 반환되고, 창은 뜨지 않는다.
open -a Simulator채택. simctl boot 다음에 부른다. 이것만 부르면 마지막으로 쓴 기기가 뜨므로 사용자가 고른 기기와 다를 수 있다. 순서가 뒤집히면 안 된다.
open -a Simulator --args -CurrentDeviceUDID <UDID>버렸다. 창까지 한 번에 열리지만 문서화되지 않은 인자이고, 이미 Simulator.app 이 떠 있으면 무시된다. boot + open 두 단계가 어느 경우에도 같게 동작한다.
실행 결과를 기다려서 돌려주기버렸다. emulator 는 끝나지 않는 프로세스라 종료 코드를 볼 수 없고, adb wait-for-device 는 어느 기기를 기다릴지 지정할 수 없다. 목록 폴링에 맡겼다(공통 스펙의 결정).

  • 이미 뜨는 중인 AVD 를 다시 실행하면 emulator 가 "이미 실행 중" 으로 끝난다. 목록이 5초 늦으므로 그 사이에 한 번 더 눌릴 수 있다.

Wi-Fi 기기 페어링 우회

공통 스펙: Wi-Fi 기기 페어링

실제로 adb 를 부르는 것은 여기뿐이다. 다른 세 타깃은 에이전트를 거쳐 이 코드에 닿는다. Android Studio 는 adblib 으로 adb 서버와 소켓으로 말하지만, 이 앱은 다른 기기 기능과 같이 adb 명령을 실행한다. 그래서 판정이 우회다.

기술 조사

후보결과
adb mdns services채택. 머리 줄 List of discovered mdns services 뒤에 <이름>\t<종류>\t<IPv4>:<포트> 가 한 줄씩 온다. 종류가 _adb-tls-pairing._tcp 인 줄이 페어링 대기 기기다. 옛 버전은 종류 끝에 점(_adb-tls-pairing._tcp.)을 붙였으므로 점을 떼고 비교한다. 이름이 겹치면 adb-… (2) 처럼 공백이 들어가므로 탭으로만 자른다. adb 37.0.1 에서 무선 기기 네 대의 _adb-tls-connect._tcp 줄을 확인했다
adb track-mdns-services(adblib 의 trackMdnsServices())버렸다. 변경을 밀어 주는 호스트 서비스지만 명령줄에는 없고, 서버 기능 목록에 있을 때만 된다. Android Studio 도 그게 없으면 1초 폴링으로 떨어진다. 1초 폴링만 둔다

adb pair <IP:포트> <코드>채택. 성공하면 Successfully paired to <IP:포트> [guid=<guid>]. 실패 문구는 Failed: Wrong password or connection was dropped. 등이다. 종료 코드는 버전마다 다르다 — android-14 까지의 서버는 실패해도 0 이고, 15 부터는 error: Failed: … 를 stderr 로 내고 1 이다. 그래서 종료 코드가 아니라 Successfully paired to 로 시작하는 줄로만 성공을 가리고, 두 스트림을 합쳐 읽는다. 코드를 인자로 주지 않으면 stdin 에서 기다리므로 늘 인자로 준다

adb connect <IP:포트>버렸다. 페어링에 성공하면 서버가 곧바로 그 guid 로 연결하고, 알려진 기기는 mDNS 자동 연결(ADB_MDNS_AUTO_CONNECT=adb-tls-connect)로도 붙는다. 우리가 더 부르면 같은 기기가 IP:포트 시리얼로 한 번 더 붙을 수 있다
adb devices 로 연결 확인채택. 페어링 뒤 1초마다 최대 10초 동안, guid 로 시작하는 시리얼(adb-R54T202XEHN-Y2yH0N._adb-tls-connect._tcp)이나 그 IP 로 시작하는 시리얼이 device 상태로 생기는지 본다. Android Studio 는 같은 조건을 120초 기다린다. 우리는 목록이 늦은 연결을 알아서 보여 주므로 응답을 짧게 끊는다

기술 조사

셸이 "터미널에 붙어 있다" 고 믿게 하려면 pty 가 있어야 한다. pty 가 없으면 zsh 가 프롬프트 편집(ZLE)을 끄고, vim·less 가 화면 크기를 모르고, Ctrl+C 가 신호가 되지 않는다. JDK 에는 pty 를 여는 API 가 없다.

PtyProcess.setWinSize() 가 ioctl(TIOCSWINSZ) 를 불러 셸에 SIGWINCH 가 간다. Maven Central 에 있다. 런타임 의존은 JNA 5.14, slf4j-api(바인딩이 없으면 경고 한 줄만 찍는다)
JediTerm(org.jetbrains.jediterm) + SwingPanel버렸다. 해석기와 그리기를 통째로 얻지만 Swing 위젯이 포커스를 쥐어 분할·탭 단축키가 Compose 에 오지 않는다. 이유는 공통 스펙의 결정에 있다
/usr/bin/script -q /dev/null $SHELL버렸다. 네이티브 의존 없이 pty 를 얻지만 그 pty 의 마스터가 script 안에 있어 창 크기를 바꿀 방법이 없다. 분할할 때마다 크기가 바뀌므로 치명적이다
ProcessBuilder 파이프버렸다. pty 가 아니라 위의 증상이 전부 난다. Android 가 어쩔 수 없이 이 길을 간다(Android)

테스트 구현

./gradlew jvmTest

유스케이스 테스트(기능의 domain), PlatformNameTest·ScreenAwakeSettingsRepositoryTest·HostAgentTest·EmulatorParsingTest·HostAgentServerTest(기능의 data), ObserveSystemStateTest(:core:data), EmulatorDevicesViewModelTest·EmulatorStatusViewModelTest(:feature:emulator:ui), JarvisAppTest·JarvisAppLaunchLockTest(:app:ui, Compose UI), JarvisKoinTest(:shared)가 돌아간다. runComposeUiTest가 Skiko 네이티브 런타임을 필요로 해서 :app:ui의 jvmTest에만 compose.desktop.currentOs를 넣는다.

결정: 화면 테스트의 Dispatchers.Main 은 Unconfined 다 collectAsStateWithLifecycle 은 수명 관찰자를 Dispatchers.Main 에서 등록하므로 Main 이 없으면 화면 테스트가 전부 죽는다. 앱처럼 kotlinx-coroutines-swing 을 넣어 Main 을 EDT 로 두는 길은 버렸다. JVM 의 runComposeUiTest 는 EDT 가 아닌 스레드에서 컴포지션을 돌려서, viewModelScope(EDT)의 상태 전파와 클릭 처리가 테스트가 기다리지 않는 스레드에서 일어나 단언을 앞지른다(회전 카드 테스트 셋이 그렇게 실패했다). TestJarvisApp 이 installTestMainDispatcher() 로 JVM 에서만 Dispatchers.setMain(Dispatchers.Unconfined) 를 건다. 앱에서는 컴포지션과 viewModelScope 가 둘 다 EDT 라 이 문제가 없다.

이 플랫폼만 에이전트 HTTP 왕복을 실제로 테스트한다. 서버가 여기 있기 때문이다. caffeinate 실행과 java.util.prefs 왕복은 미검증이다.
