모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
호스트 에이전트를 :data의 jvmMain에 둔다채택. com.sun.net.httpserver와 SDK 도구 실행은 바깥 세계에 닿는 일이라 data 계층이다. :desktopApp은 :shared가 재노출한 startEmulatorHostAgent()만 부른다
:desktopApp이 :data를 직접 의존버렸다. 앱 모듈이 조립 모듈 하나만 알게 두면, 데이터 계층 API가 바뀌어도 앱 진입점은 고치지 않는다. 대가는 :shared의 재노출 한 줄이다
에뮬레이터 폴링 Flow의 위치:data의 jvmMain 최상위 val(프로세스 싱글턴)로 둔다. 데스크톱 UI의 리포지토리와 로컬 에이전트가 같은 shareIn Flow를 구독해야 adb·simctl이 5초마다 한 번만 돈다. 에이전트는 DataModule을 거치지 않고 이 데이터 소스를 직접 구독한다
compose.desktop.currentOs:desktopApp과 :ui의 jvmTest에만 넣는다. :data·:domain은 Skiko 네이티브 런타임이 필요 없다
jvmToolchain(21)네 모듈과 :desktopApp에 각각 선언한다. 툴체인은 모듈 단위 설정이라 상속되지 않는다

구현

파일
data/src/jvmMain/.../emulator/agent/HostAgentServer.kt, shared/src/jvmMain/.../EmulatorHostAgent.kt, shared/src/jvmMain/.../PlatformContext.jvm.kt
동작
:shared의 startEmulatorHostAgent()가 :data의 같은 이름 함수를 부른다. main()은 분리 전과 똑같이 startEmulatorHostAgent().use { application { … } }
실패
포트가 이미 쓰이면 조용히 no-op. 분리 전과 같다

한계

  • 에이전트는 조립을 거치지 않고 :data의 데이터 소스를 직접 구독한다. 그래서 main()이 App()보다 먼저 에이전트를 띄울 수 있지만, 개수를 세는 경로가 컨테이너 밖에도 하나 있다는 뜻이기도 하다. 에뮬레이터 데이터 소스가 PlatformContext나 다른 상태를 요구하게 되면 이 경로부터 깨진다.
  • :shared의 재노출 함수는 :data의 시그니처를 그대로 베낀다. 시그니처가 바뀌면 두 곳을 고쳐야 한다.

검증

./gradlew :domain:jvmTest :data:jvmTest :ui:jvmTest. 에이전트 서버 테스트(HostAgentServerTest)는 :data:jvmTest에 있고, Skiko 화면이 필요한 UI 테스트는 :ui:jvmTest에 있다.

화면 꺼짐 방지 우회

공통 스펙: 화면 꺼짐 방지

기술 조사

후보결과
Compose Modifier.keepScreenOn()JVM에서는 no-op. CMP 1.12.0의 PlatformContext.setKeepScreenOnEnabled는 본문이 return 하나인 빈 기본 구현이고, Swing/AWT 씬 중 이를 오버라이드하는 것이 없다
JVM 표준 API유휴 타이머를 막는 이식 가능한 API가 없다. java.awt.Robot으로 입력을 흉내 내는 방법은 사용자 입력을 방해해 제외
macOS caffeinate시스템 기본 탑재. -d는 디스플레이 슬립, -i는 시스템 유휴 슬립을 막는다. 프로세스가 살아 있는 동안만 유효하다
macOS IOPMAssertionCreateWithName정식 API지만 JNA/Panama 바인딩이 필요하다. 의존성 추가 없이 되는 caffeinate를 택했다
Linux systemd-inhibit, Windows SetThreadExecutionState동작하지만 지원 범위 밖. 반만 동작하는 코드를 남기지 않기 위해 제거했다

우회

파일
data/src/jvmMain/.../screen/IdleInhibitor.jvm.kt
훅
createIdleInhibitor()의 JVM actual만 본문이 있다
동작
setKeepScreenAwake(true)면 ProcessBuilder("caffeinate", "-di").start(), false거나 화면이 사라져 ApplyKeepScreenAwakeUseCase가 취소되면 process.destroy()
정리
프로세스를 띄울 때 Runtime.addShutdownHook도 함께 건다. 자식 프로세스는 JVM이 죽어도 살아남으므로, 앱이 없는데 화면이 계속 켜져 있는 상태를 막는다. 토글을 끌 때는 훅을 떼고 죽인다
실패
runCatching { ... }.getOrNull(). 명령이 없으면 null이 되고 토글은 조용히 no-op이다

Compose가 비워 둔 자리를 이 한 칸으로 메운다. CMP가 데스크톱 경로를 구현하면 createIdleInhibitor() expect/actual과 ApplyKeepScreenAwakeUseCase는 통째로 걷어낸다.

한계

  • macOS 외 no-op. 실행은 되지만 화면 꺼짐 방지는 동작하지 않는다. 의도된 범위다.
  • SIGKILL은 못 막는다. 정상 종료와 SIGTERM은 셧다운 훅이 정리하지만, SIGKILL로 죽으면 훅이 돌지 않아 caffeinate가 살아남고 화면이 계속 켜져 있을 수 있다.
  • 실패를 알 수 없다. 명령이 없거나 실행이 막혀도 UI는 켜진 상태로 보인다.

검증

JarvisAppTest의 토글·저장 테스트 4개가 jvmTest에서 돈다. caffeinate가 실제로 뜨는지는 미검증이다. 개발 머신에서 pmset -g assertions로 확인할 수 있다.

화면 꺼짐 방지 (시스템 전역) 불가

공통 스펙: 화면 꺼짐 방지 (시스템 전역)

기술 조사

후보결과
caffeinate -di프로세스가 살아 있는 동안만 유효하다. 앱이 종료되면 셧다운 훅이 정리하므로 앱 없는 시간을 덮지 못한다
caffeinate를 고아 프로세스로 남기기기술적으로는 화면이 켜져 있지만, 앱 없이 도는 프로세스를 사용자가 끌 방법이 없다. 토글을 끄려면 앱을 다시 띄워야 하고 그 사이 프로세스를 잃으면 영구히 남는다. 제외
pmset -a displaysleep 0시스템 전원 설정을 실제로 바꾼다. 다만 root 권한이 필요하다. 앱이 관리자 인증을 요구하는 쪽으로 가지 않기로 했다
IOPMAssertionCreateWithName프로세스 수명에 묶인 assertion이다. caffeinate와 성질이 같다

대체 동작

@Composable
internal actual fun createSystemScreenAwakeDataSource(
    context: PlatformContext,
): SystemScreenAwakeDataSource = UnsupportedSystemScreenAwakeDataSource

카드는 같은 자리에 남고 잠긴 상태로 이유를 보여준다.

한계

해당 없음. 기능 자체가 없다.

검증

JarvisAppTest.systemScreenAwakeIsLockedWhereItIsNotSupported와 systemScreenAwakeExplainsWhyItIsUnavailable이 jvmTest에서 잠긴 카드와 설명을 검증한다.

에뮬레이터 개수 우회

공통 스펙: 에뮬레이터 개수

기술 조사

대상명령세는 방법
Android 설치<sdk>/emulator/emulator -list-avds비어 있지 않은 줄 수. 진단 메시지는 stderr로 간다
Android 실행<sdk>/platform-tools/adb devicesemulator-로 시작하는 시리얼 수. USB(39061FDJH00CNS)와 무선(192.168.0.10:5555) 기기는 형태가 달라 걸리지 않는다
iOS 설치xcrun simctl list devices availableUDID ([0-9A-F-]{36})가 붙은 줄 수
iOS 실행같은 출력상태가 Booted인 줄 수

기기 줄은 iPhone 17 (66C9B671-…) (Shutdown) 꼴이다. 이름이 아니라 UDID를 기준으로 잡는데, iPad mini (A17 Pro)처럼 이름 자체에 괄호가 들어가기 때문이다.

변경 이벤트를 조사했지만 쓸 수 없었다. adb track-devices는 있지만 simctl에는 대응물이 없다. 그래서 주기적으로 다시 세는 쪽으로 갔다.

우회

파일
data/src/jvmMain/.../emulator/Emulator.jvm.kt
주기
observeByPolling(interval = 5.seconds). 5초마다 다시 세고 바뀐 결과만 흘려보낸다. 상태 조회 규칙 참고
공유
shareIn(WhileSubscribed(), replay = 1). UI와 에이전트가 같은 값을 본다
스레드
withContext(Dispatchers.IO). UI를 막지 않는다
SDK 탐색
ANDROID_HOME → ANDROID_SDK_ROOT → ~/Library/Android/sdk (macOS의 Android Studio 기본 경로)
simctl 탐색
xcrun --find simctl이 성공하면 xcrun simctl, 아니면 /Applications/Xcode.app/Contents/Developer/usr/bin/simctl
타임아웃
명령당 10초. 넘으면 destroyForcibly()
실패
종료 코드 ≠ 0, 타임아웃, 예외 모두 null → 해당 항목 0개. 단 SDK 디렉터리나 simctl 자체를 못 찾으면 그 종류의 요약이 null이 되어 "셀 수 없음"으로 나간다

xcrun이 아니라 Xcode.app을 직접 보는 경우

xcrun simctl은 xcode-select가 정식 Xcode를 가리킬 때만 동작한다. Command Line Tools만 선택된 머신에서는 xcrun: error: unable to find utility "simctl"로 실패하지만, Xcode.app 안의 simctl은 그대로 있다. 그래서 시뮬레이터가 없다고 답하기 전에 기본 설치 경로를 한 번 더 본다.

로컬 에이전트

세어 둔 값을 같은 머신의 다른 타깃에 넘겨준다. 개수를 셀 수 있는 타깃이 여기뿐이라, 공통 스펙의 에이전트를 이 문서가 구현한다.

파일
data/src/jvmMain/.../emulator/agent/HostAgentServer.kt
서버
JDK 내장 com.sun.net.httpserver.HttpServer. 의존성을 더하지 않는다
수명
startEmulatorHostAgent()를 desktopApp의 main()이 use {}로 감싼다. 창을 닫으면 닫힌다
바인딩
InetAddress.getLoopbackAddress(). 에뮬레이터의 10.0.2.2와 adb reverse는 호스트 루프백으로 들어오므로 충분하고, LAN에는 열리지 않는다
응답
프로브를 구독해 AtomicReference에 담아 둔 최신 값을 직렬화한다. 요청마다 세지 않으므로 즉시 끝나고, 핸들러에 스레드 풀이 필요 없다
실패
포트가 이미 쓰이면 HttpServer.create가 던지고, 그 예외를 삼켜 아무것도 하지 않는 AutoCloseable을 돌려준다

본문 길이에 -1을 넘기는 자리가 있다. sendResponseHeaders에 0을 주면 chunked로 열려서 클라이언트가 오지 않는 본문을 기다리기 때문에, 본문 없는 응답은 반드시 -1이어야 한다.

출력을 파이프가 아니라 임시 파일로 받는 이유

adb는 데몬을 fork 하면서 부모의 표준 출력을 물려받는다. 파이프로 읽으면 adb devices가 끝난 뒤에도 데몬이 쓰기 끝을 잡고 있어 읽기가 끝나지 않고, 그러면 10초 타임아웃도 걸리지 않는다. redirectOutput(File)로 받으면 그런 독자가 없다. stderr는 DISCARD한다.

한계

  • 최대 5초 늦다. 폴링 주기 안에서 바뀐 것은 다음 주기에 반영된다.
  • macOS 전제다. iOS 시뮬레이터는 macOS에만 있고 SDK 기본 경로도 macOS 것만 넣었다.
  • SDK는 있는데 개별 명령이 실패하면 0개로 보인다. SDK 디렉터리나 simctl이 아예 없는 경우만 "셀 수 없음"으로 구분한다.
  • 에이전트에 인증이 없다. 같은 머신의 다른 프로세스는 누구나 개수를 읽을 수 있다. 공통 스펙 참고.
  • Android 실행 개수는 adb에 묶여 있다. platform-tools가 없으면 에뮬레이터가 떠 있어도 0이 된다.
  • 첫 호출이 느릴 수 있다. adb devices가 데몬을 띄워야 하면 1초쯤 걸린다. 그동안 카드는 "확인 중…"이다.

검증

EmulatorParsingTest가 세 명령의 출력 문자열 파싱을 검증한다. 폴링의 주기와 중복 제거는 상태 조회 규칙의 ObserveSystemStateTest로 옮겼다. 명령을 실제로 띄우는 부분은 테스트하지 않는다. 머신에 SDK가 깔려 있는지에 결과가 달라지기 때문이다.

에이전트는 HostAgentServerTest가 빈 포트에 실제로 띄워 HttpURLConnection으로 왕복한다. 정상 응답, 첫 집계 전 503, GET 이외 405, CORS 헤더, 포트 충돌 시 no-op을 확인한다. 고정 포트를 쓰면 개발자 머신에서 도는 실제 에이전트와 부딪히므로 ServerSocket(0)으로 빈 포트를 받아 쓴다. 포트를 놓아준 뒤 에이전트가 잡기까지 이론적인 경합이 있다.

빌드·실행

./gradlew :desktopApp:run                  # 실행. 에뮬레이터 개수 에이전트도 함께 뜬다
./gradlew :desktopApp:createDistributable  # 네이티브 번들 (Dmg)

Android·iOS·Web에서 에뮬레이터 개수를 보려면 이 앱을 함께 띄워 둬야 한다.

테스트 구현

./gradlew :domain:jvmTest :data:jvmTest :ui:jvmTest

유스케이스 테스트(:domain), PlatformNameTest·ScreenAwakeSettingsRepositoryTest·ObserveSystemStateTest·HostAgentTest·EmulatorParsingTest·HostAgentServerTest(:data), JarvisAppTest(:ui, Compose UI)가 돌아간다. runComposeUiTest가 Skiko 네이티브 런타임을 필요로 해서 :ui의 jvmTest에만 compose.desktop.currentOs를 넣는다.

이 플랫폼만 에이전트 HTTP 왕복을 실제로 테스트한다. 서버가 여기 있기 때문이다. caffeinate 실행과 java.util.prefs 왕복은 미검증이다.
