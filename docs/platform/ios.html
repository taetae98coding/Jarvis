모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
프레임워크를 :shared 하나만 만든다 (umbrella)채택. isStatic = true 정적 프레임워크는 의존 klib(:domain, :data, :ui)을 모두 링크해 들어간다. Xcode 프로젝트는 :shared:embedAndSignAppleFrameworkForXcode 하나만 부르면 되고, 스크립트 단계를 고칠 필요가 없었다
모듈마다 프레임워크를 만들어 Xcode에 넷 다 넣기버렸다. 정적 프레임워크 넷이 Kotlin 런타임과 공통 klib을 각자 품어 심볼이 중복되고, Xcode 쪽 임베드 설정이 모듈 수만큼 늘어난다. KMP가 권장하는 형태도 umbrella 하나다
export(projects.domain)지금은 넣지 않는다. Swift가 부르는 것은 MainViewControllerKt.MainViewController()뿐이고, 링크에는 export가 필요 없다. export는 Objective-C 헤더에 그 모듈의 public 선언을 내보낼 때만 필요하다. Swift에서 도메인 모델을 직접 다루게 되면 그때 export(projects.domain)을 추가한다
타깃 선언네 모듈이 모두 iosArm64와 iosSimulatorArm64를 선언해야 한다. 의존 모듈에 없는 타깃은 링크되지 않는다. Compose Multiplatform 1.12+가 iosX64 아티팩트를 더 이상 배포하지 않는 것도 네 모듈에 똑같이 적용된다
cinterop(platform.Foundation, platform.UIKit):data의 iosMain에서만 쓴다. :ui와 :domain의 iosMain은 비어 있다. 플랫폼 API 호출이 :data에 모인다는 규칙이 iOS에서는 "cinterop import가 :data에만 있다"로 그대로 보인다

구현

파일
shared/src/iosMain/.../MainViewController.kt, shared/src/iosMain/.../PlatformContext.ios.kt, data/src/iosMain/.../PlatformContext.ios.kt
동작
MainViewController()는 그대로 ComposeUIViewController { App() }이다. iOS에는 넘길 플랫폼 핸들이 없어 PlatformContext는 빈 클래스다
실패
해당 없음

한계

  • Swift에서 보이는 API는 :shared의 public 선언뿐이다. EmulatorStatus 같은 도메인 모델을 SwiftUI에서 쓰려면 export를 추가해야 하고, 그때 헤더가 커진다.
  • 모듈이 넷이라 linkDebugFrameworkIosSimulatorArm64 전에 klib 넷을 컴파일한다. 클린 빌드 시간이 분리 전보다 늘고, 대신 한 모듈만 고쳤을 때는 나머지가 캐시에서 온다.

검증

./gradlew :shared:linkDebugFrameworkIosSimulatorArm64가 네 모듈의 klib 링크를 확인한다. 테스트는 ./gradlew :domain:iosSimulatorArm64Test :data:iosSimulatorArm64Test :ui:iosSimulatorArm64Test로 모듈마다 돈다.

화면 꺼짐 방지 구현

공통 스펙: 화면 꺼짐 방지

기술 조사

후보결과
UIApplication.sharedApplication.idleTimerDisabled유일한 정식 API. 프로세스 전역 boolean이고, 앱이 foreground일 때만 시스템이 존중한다. 권한도 Info.plist 항목도 필요 없다
백그라운드에서 화면 유지해당 API 자체가 없다. 백그라운드 모드(오디오, 위치 등)도 화면을 켜 두지는 않는다
Compose Modifier.keepScreenOn()CMP 1.12.0 iOS 구현은 UIKitIdleTimerManager가 요청자를 집합으로 들고 있다가 비어 있는지에 따라 idleTimerDisabled를 토글한다

구현

공통 코드의 Modifier.keepScreenAwake(enabled)가 Compose의 keepScreenOn()을 붙인다. iOS 전용 코드는 없다. :data의 createIdleInhibitor()는 iOS에서 NoIdleInhibitor를 돌려준다.

한계

  • 앱이 foreground일 때만 유효하다. 백그라운드로 가면 시스템이 유휴 타이머를 되살리고, 다시 활성화되면 프로퍼티 값에 따라 재적용된다. 앱 종료 후 화면을 켜 둘 방법은 없다.
  • 프로세스 전역 프로퍼티다. Compose를 거치는 요청끼리는 UIKitIdleTimerManager가 조정해 주지만, Compose 밖에서 idleTimerDisabled를 직접 쓰면 마지막에 쓴 쪽이 이긴다.
  • 저전력 모드나 OS 정책에 따라 무시될 수 있다.

검증

JarvisAppTest의 토글·저장 테스트 4개가 iosSimulatorArm64Test에서 돈다. 유휴 타이머가 실제로 멈추는지는 자동으로 확인하지 않는다.

화면 꺼짐 방지 (시스템 전역) 불가

공통 스펙: 화면 꺼짐 방지 (시스템 전역)

기술 조사

후보결과
UIApplication.idleTimerDisabled포그라운드 앱에만 주어진다. 백그라운드로 가면 시스템이 유휴 타이머를 되살린다. 앱 수명 내 기능이 이미 쓰고 있다
자동 잠금 시간 설정 API없다. 사용자의 자동 잠금 시간을 읽는 공개 API도, 쓰는 공개 API도 iOS SDK에 없다
UIBackgroundModes: audio + 무음 재생프로세스는 살아남지만 화면은 그대로 꺼진다. idleTimerDisabled는 여전히 포그라운드 전용이다
SpringBoardServices 계열 비공개 API시스템 권한(entitlement)이 필요하다. Apple이 서명해 주지 않으므로 사이드로드나 개발자 서명으로도 열리지 않는다

중요한 점은 이 판정이 배포 방식과 무관하다는 것이다. 앱스토어 배포를 포기하고 ad-hoc이나 개발자 서명으로 설치해도 앱은 같은 샌드박스에 들어간다. Android와 달리 사이드로드가 새 길을 열어 주지 않는다.

대체 동작

@Composable
internal actual fun createSystemScreenAwakeDataSource(
    context: PlatformContext,
): SystemScreenAwakeDataSource = UnsupportedSystemScreenAwakeDataSource

카드는 같은 자리에 남고 잠긴 상태로 "이 플랫폼에서는 앱이 없는 동안의 화면 꺼짐을 막을 수 없습니다"를 보여준다. 토글을 눌러도 값이 바뀌지 않는다.

한계

해당 없음. 기능 자체가 없다.

검증

JarvisAppTest.systemScreenAwakeIsLockedWhereItIsNotSupported와 systemScreenAwakeExplainsWhyItIsUnavailable이 iosSimulatorArm64Test에서 잠긴 카드와 설명을 검증한다.

설정 영구 저장 구현

공통 스펙: 설정 영구 저장

기술 조사

후보결과
NSUserDefaults.standardUserDefaults앱 샌드박스 단위 키-값 저장소. 별도 네임스페이스가 필요 없다. 변경은 NSUserDefaultsDidChangeNotification으로 알린다
NSUbiquitousKeyValueStoreiCloud 동기화. 기기 간 동기화가 요구사항에 없어 채택하지 않았다

조사 중 두 가지 함정을 확인했다.

  • boolForKey는 키가 없을 때도 false를 돌려준다. 기본값을 지키려면 objectForKey로 존재 여부를 먼저 봐야 한다.
  • NSUserDefaultsDidChangeNotification은 어떤 키가 바뀌었는지 알려주지 않는다. 이 제약이 공통 SettingsStore.changes를 Flow<Unit>으로 설계하게 만들었다.

구현

파일
data/src/iosMain/.../settings/SettingsStore.ios.kt
읽기
if (defaults.objectForKey(key) == null) defaultValue else defaults.boolForKey(key)
쓰기
defaults.setBool(value, key)
변경 감지
NSNotificationCenter.defaultCenter.addObserverForName(NSUserDefaultsDidChangeNotification, object = defaults)를 callbackFlow로 감싼다

한계

  • 앱 삭제 시 함께 지워진다. iCloud 동기화는 하지 않는다.
  • 쓰기는 즉시 디스크에 동기화되지 않는다. 시스템이 알아서 flush 한다.

검증

ScreenAwakeSettingsRepositoryTest와 JarvisAppTest의 저장 테스트가 InMemorySettingsStore로 돈다. NSUserDefaults 왕복 자체는 미검증이다.

에뮬레이터 개수 조건부

공통 스펙: 에뮬레이터 개수

기술 조사

  • NSTask(Process)는 macOS 전용이다. iOS SDK에는 서드파티 앱이 쓸 수 있는 프로세스 실행 API가 없다.
  • 앱이 Mac의 시뮬레이터 안에서 돌고 있어도 마찬가지다. 시뮬레이터 프로세스는 호스트 macOS에서 돌지만 앱은 iOS 샌드박스 규칙을 따르고, simctl과 adb에 닿을 수 없다.
  • 시뮬레이터에서는 네트워크가 호스트와 같다. 127.0.0.1이 시뮬레이터를 띄운 Mac이므로, 그 Mac에서 도는 로컬 에이전트에 물어볼 수 있다. 이 경로를 택했다.
  • 실물 기기에서 127.0.0.1은 기기 자신이다. Mac의 LAN 주소를 쓰려면 에이전트를 루프백 밖으로 열어야 해서 하지 않았다.

우회

파일
data/src/iosMain/.../emulator/agent/HostAgent.ios.kt
동작
NSURLSession.sharedSession.dataTaskWithURL을 suspendCancellableCoroutine으로 감싼다. 코루틴이 취소되면 task.cancel()
본문 디코딩
NSData의 바이트를 readBytes로 읽어 UTF-8로 디코딩한다. NSString으로 감싼 뒤 String으로 캐스팅하는 관용구는 정적 타입이 이어지지 않아 컴파일러가 경고한다
ATS
평문 HTTP라 NSAllowsLocalNetworking으로 예외를 연다. 루프백과 로컬 네트워크에만 적용되고 NSAllowsArbitraryLoads처럼 전체를 열지는 않는다
실패
200 이외의 응답, 오류, 깨진 본문을 모두 null로 묶는다. 카드는 "셀 수 없음"을 보여준다

한계

  • 실물 기기에서는 항상 "셀 수 없음"이다. 호스트가 없다.
  • 시뮬레이터에서도 데스크톱 앱이 떠 있어야 한다.
  • 5초 폴링이라 최대 5초 늦는다.
  • sharedSession을 쓰므로 타임아웃이 기본값(60초)이다. 루프백 연결은 거절이 즉시 오므로 실제로는 문제가 되지 않는다.

화면 회전 우회 미검증

공통 스펙: 화면 회전

기술 조사

시스템 회전잠금(제어 센터)은 앱이 읽지도 쓰지도 못한다. 열려 있는 것은 내 앱 창을 어느 방향으로 둘지뿐이고, 그것도 두 가지를 같이 해야 한다. 어느 방향을 허용할지(supportedInterfaceOrientations)와 지금 어느 방향으로 갈지(requestGeometryUpdate)다.

후보결과
UIWindowScene.requestGeometryUpdate(.iOS(interfaceOrientations:)) (iOS 16+)채택. Kotlin/Native 바인딩은 requestGeometryUpdateWithPreferences(preferences, errorHandler), 선호값은 UIWindowSceneGeometryPreferencesIOS(interfaceOrientations = mask)다. 배포 타깃이 iOS 16.0이라 분기가 필요 없다. 요청한 방향이 앱의 허용 목록에 없으면 errorHandler로 실패가 온다
application(_:supportedInterfaceOrientationsFor:) (UIApplicationDelegate)채택. 회전잠금의 실체다. 이 마스크를 한 방향으로 좁혀야 사용자가 기기를 돌려도 되돌아가지 않는다. 앱 델리게이트의 답이 뷰 컨트롤러의 답보다 우선하므로, SwiftUI WindowGroup이 만든 UIHostingController를 건드리지 않고 여기 한 곳에 게이트를 둔다
UIViewController.supportedInterfaceOrientations 오버라이드버렸다. Compose는 ComposeUIViewController()가 만든 컨트롤러를 SwiftUI UIViewControllerRepresentable 안에 넣는다. 이 컨트롤러는 루트가 아니라 자식이라 UIKit이 방향을 물어보지 않는다. 루트를 바꾸려면 SwiftUI 진입점을 UIKit으로 되돌려야 한다
UIDevice.setValue(_:forKey: "orientation")버렸다. 비공개 KVC다. iOS 16부터는 그나마도 무시되는 경우가 많고 심사에서 걸린다. requestGeometryUpdate가 이 트릭을 대체하려고 나온 API다
UIViewController.attemptRotationToDeviceOrientation()iOS 16에서 deprecated. 마스크를 바꾼 뒤 재평가를 요청하는 용도였고, 지금은 setNeedsUpdateOfSupportedInterfaceOrientations()가 그 자리다. 우리는 마스크를 바꾼 직후 곧바로 requestGeometryUpdate를 부르므로 둘 다 쓰지 않는다
시스템 회전잠금 읽기없다. UIDevice.orientation은 물리적 기기 자세만 알려주고 잠겼는지는 모른다. 그래서 카드의 잠금 상태는 "시스템이 잠겼나"가 아니라 "우리가 마스크를 좁혔나"다
UIDeviceOrientationDidChangeNotification채택(관찰). beginGeneratingDeviceOrientationNotifications() 후 신호를 받아 windowScene.interfaceOrientation을 다시 읽는다(상태 조회 규칙). 우리가 방향을 바꿨을 때는 기기가 움직이지 않아 알림이 오지 않으므로, 자체 신호를 하나 더 흘려 같은 경로로 합류시킨다

우회

파일
data/src/iosMain/.../rotation/DeviceRotation.ios.kt, shared/src/iosMain/.../DeviceRotationGate.kt, iosApp/iosApp/iOSApp.swift, iosApp/iosApp/Info.plist

허용 마스크를 UIInterfaceOrientationMaskAll(자동)과 한 방향(잠금) 사이에서 바꾼다. 마스크는 DeviceRotationGate가 들고 있고, Swift AppDelegate가 supportedInterfaceOrientationsFor에서 그 값을 읽는다
각도
마스크를 목표 방향 하나로 좁힌 뒤 requestGeometryUpdateWithPreferences를 부른다
읽기
UIApplication.sharedApplication.connectedScenes에서 첫 UIWindowScene의 interfaceOrientation
Info.plist
UISupportedInterfaceOrientations에 UIInterfaceOrientationPortraitUpsideDown을 추가했다. 없으면 180° 요청이 무조건 거절된다
실패
errorHandler가 부르는 것은 로그도 남기지 않고 무시한다. 다음 관찰 주기에 실제 방향이 그대로 흘러와 카드가 저절로 사실을 보여준다

Kotlin이 Swift로 값을 내보내는 통로는 :shared뿐이다(:data는 프레임워크로 export되지 않는다). 그래서 MainViewController()와 같은 자리에 supportedInterfaceOrientationMask()를 하나 더 둔다.

// iosApp/iosApp/iOSApp.swift
class AppDelegate: NSObject, UIApplicationDelegate {
    func application(
        _ application: UIApplication,
        supportedInterfaceOrientationsFor window: UIWindow?
    ) -> UIInterfaceOrientationMask {
        UIInterfaceOrientationMask(rawValue: UInt(DeviceRotationGateKt.supportedInterfaceOrientationMask()))
    }
}

한계

  • 기기가 아니라 앱만 돈다. 홈 화면과 다른 앱은 그대로다. 시스템 회전잠금을 켜거나 끄는 공개 API는 없다.
  • 노치가 있는 iPhone은 180°를 거절한다. Info.plist에 허용을 적어도 시스템이 거꾸로 방향을 지원하지 않아 요청이 실패하고 각도가 그대로 남는다. iPad에서는 동작한다.
  • 시스템 회전잠금이 켜져 있으면 사용자의 물리 회전은 무시된다. 우리 requestGeometryUpdate는 그래도 통하므로, 카드로는 돌아가는데 손으로는 안 돌아가는 상태가 된다.
  • iPad 멀티태스킹에서는 요청이 무시될 수 있다. 스플릿 뷰에서는 시스템이 창 방향을 정한다.
  • UIApplicationSupportsMultipleScenes가 켜져 있어 창이 여럿이면 첫 번째 UIWindowScene만 읽고 쓴다.

검증

자동 테스트가 없다. 회전은 실기기·시뮬레이터에서만 일어나고 iosSimulatorArm64Test에는 창이 없다. Kotlin 쪽은 ./gradlew :shared:compileKotlinIosSimulatorArm64로 컴파일까지 확인했지만, AppDelegate가 마스크를 제대로 물어 오는지는 Xcode 빌드에서만 드러난다. 규칙과 카드 표시는 :domain·:ui 테스트가 다른 타깃에서 검증한다. 기기에서는 카드의 각도 버튼을 누른 뒤 기기를 손으로 돌려 되돌아가지 않는지(잠금), 토글을 끄면 다시 따라 도는지로 확인한다.

기기 목록·화면·제스처 조건부

공통 스펙: 기기 목록·화면·제스처

기술 조사

  • iOS 는 서드파티 앱에 프로세스 실행 API 를 주지 않는다. adb 도 simctl 도 부를 수 없다(에뮬레이터 개수와 같은 이유).
  • 시뮬레이터에서는 127.0.0.1 이 이 Mac 이라 데스크톱 앱의 에이전트에 닿는다. 실물 기기에서는 자기 자신이라 닿지 않는다.
  • NSURLSession.dataTaskWithURL 이 주는 NSData 를 readBytes 로 읽으면 PNG 바이트가 그대로 나온다. 개수 응답에서 UTF-8 로 디코딩하던 것과 같은 경로이고, 프레임은 디코딩만 건너뛴다.
  • 제스처는 NSMutableURLRequest 에 HTTPMethod = "POST", HTTPBody 를 실어 dataTaskWithRequest 로 보낸다.
  • 실물 기기를 목록에 넣는 것은 여기서 할 일이 없다. 호스트에 무엇이 연결됐는지는 JVM 이 판정해서 능력 플래그와 함께 내려준다. 이 앱이 실물 iOS 기기에서 돌 때와, 호스트에 실물 iOS 기기가 꽂혀 있을 때는 서로 다른 이야기다.

우회

파일
data/src/iosMain/.../emulator/agent/HostAgent.ios.kt
동작
127.0.0.1:47890 의 목록·프레임·제스처 엔드포인트. 취소되면 NSURLSessionTask.cancel 로 요청도 끊는다
실패
연결 실패와 200 이외 응답을 모두 없는 것으로 본다. 목록은 비고 프레임은 null 이 된다

Info.plist 의 NSAllowsLocalNetworking 예외를 개수 기능과 함께 쓴다. 엔드포인트가 늘어도 호스트와 포트가 같아 새로 추가할 예외가 없다.

한계

  • 실물 기기에서는 목록이 항상 비어 있다. 같은 머신이라는 전제가 깨진다.
  • 시뮬레이터 안에서 시뮬레이터 화면을 본다. 자기 자신을 고르면 화면 안에 화면이 겹쳐 보이고, 거기에 보낸 제스처는 아래대로 iOS 쪽이라 무시된다.
  • iOS 시뮬레이터 항목은 제스처를 받지 못하고, 목록에 섞여 있는 실물 iOS 기기 항목은 화면조차 볼 수 없다. 두 이유 모두 JVM 스펙에 있다.

검증

HostAgentTest 가 iosSimulatorArm64Test 에서 가짜 전송 함수로 실패 처리를 확인한다. NSURLSession 으로 실제 왕복하는 부분은 데스크톱 앱이 함께 떠 있어야 해서 미검증이다.

빌드·실행

open iosApp/iosApp.xcodeproj

Xcode 빌드 시 Compile Kotlin Framework 스크립트 단계가 :shared:embedAndSignAppleFrameworkForXcode를 호출해 프레임워크를 만들고 앱에 임베드한다. 서명 팀은 Config.xcconfig의 TEAM_ID에 넣는다.

한계

  • Xcode 정식 설치가 필요하다. Command Line Tools만 있으면 Kotlin 컴파일은 되지만 프레임워크 링크 단계에서 xcrun이 실패한다.
  • xcode-select가 Command Line Tools를 가리키는 머신에서는 Gradle 태스크에 DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer를 넘겨야 iOS 타깃이 컴파일된다. 머신 전역 설정을 바꾸지 않아도 된다.
  • MARKETING_VERSION은 Gradle과 연동되지 않는다. 앱 정보 참고.

테스트 구현

DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  ./gradlew :domain:iosSimulatorArm64Test :data:iosSimulatorArm64Test :ui:iosSimulatorArm64Test

유스케이스 테스트(:domain), PlatformNameTest·ScreenAwakeSettingsRepositoryTest·ObserveSystemStateTest·HostAgentTest(:data), JarvisAppTest(:ui, Compose UI)가 전부 돌아간다. UI 테스트는 :ui의 skikoTest 소스셋에 있어 JVM·Web과 공유한다. 단, 위와 같은 이유로 Xcode가 있어야 한다.

플랫폼 API를 실제로 부르는 경로(NSUserDefaults 왕복, NSURLSession 요청)는 미검증이다.
