모듈 구조 구현

공통 스펙: 모듈 구조

기술 조사

후보결과
프레임워크를 :shared 하나만 만든다 (umbrella)채택. isStatic = true 정적 프레임워크가 의존 klib 열여섯 개를 모두 링크해 들어간다. 기능 모듈을 늘려도 Xcode 프로젝트는 :shared:embedAndSignAppleFrameworkForXcode 하나만 부르고 스크립트 단계를 고칠 필요가 없다
기능마다 프레임워크를 만들어 Xcode에 넣기버렸다. 정적 프레임워크가 Kotlin 런타임과 공통 klib을 각자 품어 심볼이 중복되고, Xcode 쪽 임베드 설정이 모듈 수만큼 늘어난다. KMP가 권장하는 형태도 umbrella 하나다
export(projects.feature.emulator.domain)지금은 넣지 않는다. Swift가 부르는 것은 MainViewControllerKt.MainViewController()뿐이고, 링크에는 export가 필요 없다. export는 Objective-C 헤더에 그 모듈의 public 선언을 내보낼 때만 필요하다
타깃 선언열여섯 모듈이 모두 iosArm64·iosSimulatorArm64를 선언해야 한다. 의존 모듈에 없는 타깃은 링크되지 않는다. 컨벤션 플러그인이 그 선언을 한곳에서 만들기 때문에 모듈을 추가할 때 빠뜨릴 수 없다
cinterop(platform.Foundation, platform.UIKit)기능의 data 모듈 iosMain에서만 쓴다. ui·domain 모듈의 iosMain은 비어 있다. 플랫폼 API 호출이 data 계층에 모인다는 규칙이 iOS에서는 "cinterop import가 data 모듈에만 있다"로 그대로 보인다

구현

파일
shared/src/iosMain/.../MainViewController.kt, shared/src/iosMain/.../JarvisKoin.ios.kt, core/data/src/iosMain/.../PlatformContext.ios.kt
동작
MainViewController()가 Koin 을 세운 뒤 ComposeUIViewController { App() }를 돌려준다. iOS에는 넘길 플랫폼 핸들이 없어 PlatformContext는 빈 클래스다
실패
해당 없음

한계

  • Swift에서 보이는 API는 :shared의 public 선언뿐이다. EmulatorStatus 같은 도메인 모델을 SwiftUI에서 쓰려면 export를 추가해야 하고, 그때 헤더가 커진다.
  • 링크 전에 klib 열여섯 개를 컴파일한다. 클린 빌드 시간이 기능 분리 전보다 늘고, 대신 한 기능만 고쳤을 때는 나머지가 캐시에서 온다.

검증

./gradlew :shared:linkDebugFrameworkIosSimulatorArm64가 열여섯 모듈의 klib 링크를 확인하고, 테스트는 ./gradlew iosSimulatorArm64Test로 모듈마다 돈다.

이 변경은 iOS 링크를 확인하지 못했다 기능 분리 작업을 한 머신에 Xcode 가 없어(xcode-select가 Command Line Tools 만 가리킨다) xcrun xcodebuild -version 이 실패하고, Kotlin/Native 링크와 시뮬레이터 테스트가 돌지 않았다. 열여섯 모듈의 compileKotlinIosArm64·compileKotlinIosSimulatorArm64 까지는 성공했다. 링크·테스트는 Xcode 가 있는 머신에서 확인해야 한다.

의존성 주입 구현

공통 스펙: 의존성 주입

기술 조사

후보결과
MainViewController()에서 startJarvisKoin()채택. Swift 가 부르는 유일한 공유 코드 진입점이고, 컨트롤러를 만들기 전에 Koin 이 서 있으면 된다. PlatformContext는 빈 상자라 인자가 없다
Swift 쪽(iOSApp.init)에서 시작버렸다. startJarvisKoin()을 Shared 프레임워크의 함수로 내보내면 Swift 에서도 부를 수 있지만, 그러면 시작 시점이 Swift 와 Kotlin 두 곳에 흩어진다. 지금은 Compose 화면이 유일한 소비자다
koin-core의 iOS 아티팩트iosArm64·iosSimulatorArm64 변형이 퍼블리시된다. 이 프로젝트의 타깃 목록(iosX64 제외)과 맞는다
Koin 을 KoinComponent로 Swift 에 노출버렸다. Swift 가 리포지토리를 직접 꺼낼 이유가 없다. 프레임워크 표면에 남는 것은 MainViewController()뿐이다

구현

파일
shared/src/iosMain/.../MainViewController.kt, shared/src/iosMain/.../JarvisKoin.ios.kt
동작
MainViewController()가 startJarvisKoin()을 부른 뒤 ComposeUIViewController { JarvisApp() }를 돌려준다. SwiftUI 가 ComposeView를 다시 만들면 MainViewController()도 다시 불리므로 두 번 시작해도 안전해야 한다
실패
정의가 빠져 있으면 첫 화면에서 Kotlin 예외가 올라오고 앱이 죽는다. Swift 쪽에는 NSException이 아니라 크래시로 보인다

한계

  • Koin 이 Compose 화면보다 먼저 필요해지는 코드(예: 앱 델리게이트가 읽는 값)는 이 시작점보다 앞선다. 지금 그런 코드는 없다. 2026-09-22~24 사이에 있었던 회전 마스크는 Koin 을 거치지 않는 싱글턴으로 풀었고, 걷어낸 뒤에도 같은 방식이 답이다.

검증

정의 해석은 :shared의 jvmTest가 대표로 본다. iOS 에서는 :app:ui의 skiko UI 테스트(iosSimulatorArm64Test)가 가짜 리포지토리를 담은 Koin 으로 화면을 그리는 것으로 확인된다.

화면 상태 소유 (ViewModel) 구현

공통 스펙: 화면 상태 소유 (ViewModel)

기술 조사

후보결과
Compose Multiplatform 의 기본 owner채택. skiko 타깃의 compose-ui에 findComposeDefaultViewModelStoreOwner()가 있고, ComposeUIViewController가 만든 컴포지션이 그것을 LocalViewModelStoreOwner로 제공한다. 앱 코드가 owner 를 만들지 않는다
lifecycle-viewmodel-compose의 iOS 아티팩트org.jetbrains.androidx.lifecycle 2.11.0 이 iosArm64·iosSimulatorArm64를 퍼블리시한다. viewModelScope의 Dispatchers.Main은 메인 큐다
UIKit 호출 스레드확인해 둘 것. 화면 꺼짐 방지는 UIKit 을 부르고 메인 스레드를 요구한다. ViewModel 의 동작과 상태 수집은 viewModelScope(메인 큐)에서 돌아서 예전과 같은 스레드에서 호출된다. 앱 수명 CoroutineScope 는 걷어냈다(상태 조회 규칙 R12)
Swift 가 ViewModel 을 직접 쓰기버렸다. ViewModel을 프레임워크로 내보내면 Swift 화면도 같은 상태를 볼 수 있지만, 이 앱의 화면은 전부 Compose 다

구현

파일
공용이다. iOS 전용 코드는 없다
동작
ComposeUIViewController가 사라질 때 그 컴포지션의 ViewModelStore가 비워지고 onCleared()가 불린다
실패
없다. owner 가 항상 제공된다

한계

  • SwiftUI 가 ComposeView를 다시 만들면(뷰 계층 재구성) 새 ViewModelStore가 만들어져 앱 수명 ViewModel 도 새로 만들어진다. 지금 구조(WindowGroup 하나, ContentView 하나)에서는 일어나지 않는다.
  • iOS 에는 "구성 변경"이 없어 ViewModel 이 재생성을 넘는 성질을 쓸 일이 없다. ViewModel 을 쓰는 이유는 여기서는 수명 분리(화면별 정리)와 주입이다.

검증

:app:ui의 iosSimulatorArm64Test에서 skiko UI 테스트가 돈다. 화면 전환 시 상태가 정리되는 것은 JarvisAppTest.backReturnsToListThenGrid가 본다.

화면 이동 (Navigation3) 조건부

공통 스펙: 화면 이동 (Navigation3)

기술 조사

후보결과
NavDisplay(JetBrains navigation3-ui)채택. iOS 변형이 퍼블리시되고 SinglePaneSceneStrategy가 그대로 돈다. 앱 안의 뒤로 아이콘 버튼로 백스택을 줄인다
화면 가장자리 스와이프(interactivePopGestureRecognizer)오지 않는다. 그 제스처는 UINavigationController가 제공하는데, 이 앱의 컨트롤러 계층은 WindowGroup → ContentView → UIViewControllerRepresentable → ComposeUIViewController라 내비게이션 컨트롤러가 없다
Swift 쪽을 NavigationStack/UINavigationController로 감싸기버렸다. 제스처는 얻지만 화면 스택이 Swift 와 Kotlin 두 곳에 생긴다. 어느 쪽이 사실인지 맞추는 비용이 제스처 하나보다 크다
navigationevent로 제스처를 공급하기후보로 남긴다. NavDisplay는 navigationevent-compose의 상태를 보므로, iOS 쪽에서 NavigationEventDispatcher에 제스처 진행을 밀어 넣으면 예측 뒤로까지 가능하다. 우리 쪽에서 디스패처를 만들어 주는 코드가 필요하고 검증하지 못했다
백스택 저장·복원rememberNavBackStack은 SaveableStateRegistry에 저장한다. iOS 에서 Compose 컴포지션이 프로세스를 넘어 복원되는 경로는 없으므로 실제 복원은 일어나지 않는다

대체 동작

파일
공용이다. iOS 전용 코드는 없다
동작
앱 안의 뒤로 아이콘 버튼이 유일한 뒤로 경로다. 홈에서는 뒤로 갈 곳이 없다
실패
가장자리 스와이프는 아무 일도 하지 않는다. 화면이 반쯤 끌려가다 되돌아오는 식의 어긋난 피드백은 없다

한계

  • iOS 사용자가 기대하는 가장자리 스와이프로 뒤로 갈 수 없다. 화면이 셋뿐이고 상단에 뒤로 아이콘 버튼가 항상 있어서 막히지는 않는다.
  • 앱을 껐다 켜면 항상 홈에서 시작한다.

검증

:app:ui의 iosSimulatorArm64Test에서 카드 → 목록 → 화면 → 뒤로 경로가 검증된다. 가장자리 스와이프가 오지 않는다는 사실은 테스트하지 않는다(없는 입력이다).

재생성을 넘기는 상태 (retain) 조건부

공통 스펙: 재생성을 넘기는 상태 (retain)

기술 조사

후보결과
retain + 플랫폼이 제공하는 RetainedValuesStore저장소가 없다. runtime-retain은 iOS 변형을 퍼블리시하지만, skiko 쪽 compose-ui에는 Android 의 LifecycleRetainedValuesStore에 해당하는 구현이 없다. LocalRetainedValuesStore의 기본값인 ForgetfulRetainedValuesStore가 쓰이고, 컴포지션을 벗어난 값은 바로 버려진다
재생성 경로 자체없다. iOS 에는 구성 변경으로 화면을 다시 만드는 개념이 없고, 회전은 같은 컴포지션이 다시 측정될 뿐이다. 보관할 구간이 없으므로 retain이 remember처럼 움직여도 사용자에게 보이는 차이가 없다
retainManagedRetainedValuesStore()로 루트에 저장소 깔기버렸다. 값이 실제로 보관되게 만들 수는 있지만, 보관해야 할 재생성 구간이 없는데 화면을 떠난 프레임만 메모리에 남는다(R4 위반)

대체 동작

파일
공용이다. iOS 전용 코드는 없다
동작
retain은 컴파일되고 remember와 같게 동작한다. 예외도 경고도 없다
실패
없다

한계

  • retain이 코드에 적어 두는 "컴포지션보다 오래 사는 값"이라는 의도가 iOS 에서는 실행되지 않는다. skiko 쪽에 저장소 구현이 생기면 코드를 고치지 않고 동작이 켜진다.

검증

같은 코드가 컴파일되고 화면이 정상 동작하는 것까지 skiko UI 테스트가 본다. 보관 여부는 확인할 대상이 아니다(보관하는 저장소가 없다).

앱 정보 구현

공통 스펙: 앱 정보 카드

기술 조사

UIDevice.currentDevice가 systemName("iOS" 또는 "iPadOS")과 systemVersion("18.0")을 제공한다.

기기 이름·식별자(공통 R5·R6) 후보. 시뮬레이터는 xcrun simctl 이 앱 프로세스에 자기 정보를 환경 변수로 넣어 준다.

후보결과
환경 변수 SIMULATOR_DEVICE_NAME / SIMULATOR_UDID채택(시뮬레이터). NSProcessInfo.processInfo.environment 로 읽는다. 값이 simctl list·device_list 의 이름과 UDID 그대로라 카드와 기기 목록이 같은 글자를 보여준다. 실물에는 없다
UIDevice.currentDevice.name채택(실물 이름). iOS 16 부터 com.apple.developer.device-information.user-assigned-device-name 엔타이틀먼트가 없으면 사용자 이름 대신 "iPhone" 같은 모델 종류를 준다. 엔타이틀먼트는 Apple 승인이 필요해서 받지 않았다
sysctl hw.machine(iPhone16,2)버림. 기기 목록의 이름과 다르고 사람이 읽기 어렵다. 시뮬레이터에서는 Mac 의 값(arm64)이 나온다
UIDevice.currentDevice.identifierForVendor채택(실물 식별자). 같은 개발 팀의 앱이 모두 지워지기 전까지 같은 UUID. 시뮬레이터에서도 값이 있지만 UDID 가 아니라 환경 변수를 먼저 본다

기기 목록·화면·제스처 조건부

공통 스펙: 기기 목록·화면·제스처

기술 조사

  • iOS 는 서드파티 앱에 프로세스 실행 API 를 주지 않는다. adb 도 simctl 도 부를 수 없다(에뮬레이터 개수와 같은 이유).
  • 시뮬레이터에서는 127.0.0.1 이 이 Mac 이라 데스크톱 앱의 에이전트에 닿는다. 실물 기기에서는 자기 자신이라 닿지 않는다.
  • NSURLSession.dataTaskWithURL 이 주는 NSData 를 readBytes 로 읽으면 PNG 바이트가 그대로 나온다. 개수 응답에서 UTF-8 로 디코딩하던 것과 같은 경로이고, 프레임은 디코딩만 건너뛴다.
  • 제스처는 NSMutableURLRequest 에 HTTPMethod = "POST", HTTPBody 를 실어 dataTaskWithRequest 로 보낸다.
  • 실물 기기를 목록에 넣는 것은 여기서 할 일이 없다. 호스트에 무엇이 연결됐는지는 JVM 이 판정해서 능력 플래그와 함께 내려준다. 이 앱이 실물 iOS 기기에서 돌 때와, 호스트에 실물 iOS 기기가 꽂혀 있을 때는 서로 다른 이야기다.

기술 조사

후보결과
xcodebuild -scheme iosApp -configuration Release -destination generic/platform=iOS archive채택. Compile Kotlin Framework 단계가 CONFIGURATION=Release 를 보고 :shared:embedAndSignAppleFrameworkForXcode 가 release 프레임워크(LTO)를 링크한다. -allowProvisioningUpdates 로 자동 서명이 프로필을 받는다
-exportArchive + method = debugging채택. 이 머신에 있는 인증서는 Apple Development 하나이고, 팀 4TV6L66XZ8 의 와일드카드 개발 프로필이 등록 기기 4대를 담는다. 그 기기들에 설치할 수 있는 ipa 가 나온다. 옵션은 iosApp/ExportOptions.plist
method = app-store-connect / release-testing(ad hoc)불가. Apple Distribution 인증서가 키체인에 없다(security find-identity -v -p codesigning 에 개발 인증서만 있다). 자동 서명이 계정에서 인증서를 새로 발급할 수는 있지만 계정에 흔적을 남기는 일이라 사용자가 한다
Gradle 이 MARKETING_VERSION 을 쓰게 하기버렸다. Xcode 가 빌드 설정을 Kotlin 단계보다 먼저 확정하므로 빌드 중에 xcconfig 를 바꿔도 그 빌드에는 들지 않는다. 대신 checkIosAppVersion 이 어긋나면 check 를 실패시킨다
Info.plist 의 CADisableMinimumFrameDurationOnPhone = true추가했다. 없으면 Compose Multiplatform 1.12.1 의 PlistSanityCheck 가 120Hz iPhone(iPhone 18 Pro 시뮬레이터에서 확인)에서 시작하자마자 IllegalStateException 으로 앱을 죽인다. Release 에서 새로 생긴 문제가 아니라 이전부터 이 키가 없었다. enforceStrictPlistSanityCheck = false 로 검사를 끄는 안은 버렸다 — 앱이 60Hz 로 묶인다
UISupportedInterfaceOrientations~ipad 네 방향추가했다. TARGETED_DEVICE_FAMILY = 1,2 라 iPad 도 대상이고, 멀티태스킹을 지원하는 iPad 앱이 네 방향을 다 선언하지 않으면 App Store 업로드 검증에서 막힌다
Release 구성을 시뮬레이터로 빌드Release 는 ONLY_ACTIVE_ARCH = NO 라 x86_64 도 요구하는데 Kotlin 은 iosSimulatorArm64 만 있어서 "Xcode Requested Architecture Not Configured in Gradle" 로 실패한다. 검증용 빌드에는 ARCHS=arm64 ONLY_ACTIVE_ARCH=YES 를 준다
kotlin.native.jvmArgs=-Xmx12g저장소 gradle.properties 로 옮겼다. release 링크(LTO)가 기본 힙에서 OutOfMemoryError 로 죽는데 이 값이 사용자 홈에만 있었다(R7)
